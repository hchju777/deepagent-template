# 9c단계 — 블록과 HTML 렌더링

> **목적**: 팩트시트의 숫자를 **메일 본문 HTML**로 만든다. 차트(9d)와 LLM 코멘트(9e)는
> 자리만 잡아 둔다.

```bash
python -m src report render --out output/report.html
python -m src report render --stub-seeds seeds.json --out /tmp/r.html   # 대상 없이
```

## 블록은 HTML을 모른다

```
facts.py     숫자를 센다
   ↓
blocks.py    숫자를 **사람이 읽는 텍스트**로 (1,234건 · ▲ 29.3% · —)
   ↓
report_html.py   텍스트를 table·인라인 스타일로
```

이 경계가 있어서 "숫자가 틀렸다"와 "표가 깨졌다"를 다른 파일에서 찾는다. 숫자 서식은
HTML 없이 단독으로 검사할 수 있다(`tests/report/test_blocks.py`).

## 섹션 하나 추가하기

```python
def _my_section(facts: Facts) -> Block:
    return Block(key="내_섹션", title="내 섹션", table=Table(columns=..., rows=...))

BLOCKS = (..., _my_section)
```

그게 전부다. 렌더러는 `BLOCKS`를 순회할 뿐이므로 블록을 더하거나 빼도 나머지는
모른다. **`BLOCKS`가 단일 진실 소스**이고, 순서가 곧 리포트의 순서다. 테스트가
블록 하나씩 단독으로 만들어 보며 서로를 모르는지 확인한다.

## 비어 있는 섹션은 사라지지 않는다

데이터가 0건이라고 섹션을 감추면 읽는 사람은 "그 항목은 원래 없는 리포트"라고
읽는다. `required=True`인 블록은 내용이 없어도 `empty` 문구로 남는다. 사라질 수
있는 것은 **있을 때만 의미가 있는 것**(경고 배너)뿐이다.

`조회 범위` 표도 정상일 때 남는다. 이상할 때만 나타나는 표는, 없을 때 "괜찮다"인지
"확인을 안 했다"인지 구별해 주지 않는다.

## Outlook이 제약을 전부 정한다

Outlook 데스크톱은 HTML을 브라우저 엔진이 아니라 **Word 엔진**으로 그린다. 2026년에도
그렇다. 그래서:

| | |
|---|---|
| 배치 | 중첩 `<table role="presentation">` |
| 스타일 | 전부 `style="..."` 인라인 |
| 폭 | `width="720"`을 **속성으로도** (Word는 CSS width를 무시할 때가 있다) |
| 금지 | `<style>` 블록 · `class=` · flex · grid · float · position · `@media` |

테스트가 금지 목록을 생성된 HTML에서 직접 찾는다. 구식 HTML을 쓰는 게 아니라
**대상 렌더러에 맞춘 코드**다 — 브라우저에서 예쁜 것을 고르면 받는 사람의
Outlook에서 무너진다.

## 다크모드는 지원하지 않는다. 대신 망가지지 않게 만든다

메일 다크모드는 우리가 켜는 게 아니라 **클라이언트가 색을 강제로 반전**시키는
것이고, Outlook 데스크톱은 CSS로 막을 수 없다. `prefers-color-scheme`은 상당수
클라이언트에서 지워지고, 되는 곳에서도 강제 반전과 겹쳐 더 이상해진다.

그래서 세 가지로 대응한다:

1. **의미를 색에만 싣지 않는다.** 증감은 `▲`/`▼`와 부호가 말한다. 빨강이 초록처럼
   보여도 화살표는 화살표다.
2. **거의 흰 배경 + 거의 검은 글자.** 반전되면 거의 검정/거의 흰색이 되어 대비가
   유지된다. 중간 회색끼리 쓰면 반전 후 뭉개진다.
3. **투명 배경을 남기지 않는다.** 명시하지 않으면 클라이언트가 칠한 어두운 바탕
   위에 어두운 글자가 앉는다.

`<meta name="color-scheme">`은 넣는다 — 막아 주지는 않지만 이걸 보는 클라이언트는
자체 반전을 덜 공격적으로 하고, 비용이 0이다.

## 주입 — 라인 이름은 대상 시스템의 데이터다

`<`가 태그가 되고 `"`가 스타일 속성을 끊는다. 속성이 끊기면 그 뒤의 모든 스타일이
**데이터에 조종된다.** 모든 텍스트가 `html.escape(quote=True)` 한 문을 지난다.
테스트가 `<script>alert(1)</script>" style="display:none`을 라인 이름에 넣어
확인한다.

## 급증 기준을 바꿨다

9b는 **전주 동요일 하루**를 기준으로 삼았는데, 승인된 포맷의 정의대로
**직전 평일 평균**으로 바꿨다. 이유:

- 전주 그 하루가 마침 이상했으면 비교가 통째로 거짓이 된다.
- 검사 대상인 날은 기준에서 **뺀다**. 넣으면 그날이 튈수록 기준도 올라가 신호가
  둔해진다(어제 3배가 터졌는데 기준이 1.3배 올라가 버린다).

전주 동요일은 `GBM별 요약`의 한 열로 **계속 보여 준다** — 요일 효과를 보는 데는
그쪽이 맞다. 둘은 다른 질문에 답한다. `spike_ratio` 기본값도 2.0 → **1.5**로
내렸다(기준이 평균이라 하루 비교보다 덜 출렁인다).

## 이미지가 막혀도 읽을 것이 남는다

`일별 알람 추이`는 9d에서 차트가 붙지만 **표로도 남는다.** 메일 클라이언트가
이미지를 막는 일이 흔하고, 그때 그림만 있으면 읽을 것이 없다.

## 검토 포인트

1. **`report-clean.html`과 `report-warned.html`을 실제로 열어 보기.** 후자는 한
   법인이 방화벽에 막히고 다른 한 곳은 표본이 잘린 경우다 — 경고가 **숫자보다 먼저**
   보이는지.
2. **사내 Outlook으로 실제 발송.** `report render`로 만든 파일을
   `mail send --file`로 보내서 표가 무너지지 않는지. 이게 이 단계의 진짜 검증이다.
3. **다크모드로 받아 보기.** 반전돼도 증감 방향이 읽히는지.
4. `급증 기준`을 평균으로 바꾼 것이 맞는지 — 전주 동요일 기준이 더 낫다면 되돌린다.
5. 섹션 순서(`BLOCKS`)와 `주요 이슈 분석`(LLM) 자리가 맞는지.
