# 9a단계 — 리포트가 볼 기간

> **목적**: "어제부터 과거 7 평일"이 정확히 **어느 날짜들**이고, 대상 Mongo에
> 나갈 **필터가 정확히 무엇인지**를 사람이 눈으로 확인할 수 있게 한다.
> 집계도, 렌더링도, 메일도 아직 없다.

## 왜 기간부터인가

리포트에서 조용히 틀리기 가장 쉬운 곳이 여기다. 집계 로직이 틀리면 숫자가
이상해서 누군가 알아채지만, **기간이 틀리면 리포트는 아무 오류 없이 완성된다.**
월요일 아침 잡이 "어제"를 일요일로 잡으면 그날 모든 숫자가 0이 되고, 사람은
"어제 알람이 없었나 보다" 하고 넘어간다.

그래서 이 단계의 산출물은 코드가 아니라 **`report window` 명령의 출력**이다.

```bash
python -m src report window --today 2026-09-07
```

```json
{
  "기준일(오늘)": "2026-09-07(월)",
  "어제(직전 평일)": "2026-09-04(금)",
  "집계 대상": ["2026-08-27(목)", "2026-08-28(금)", "2026-08-31(월)",
              "2026-09-01(화)", "2026-09-02(수)", "2026-09-03(목)", "2026-09-04(금)"],
  "전주 동요일": ["2026-08-20(목)", "…", "2026-08-28(금)"],
  "조회 범위": { "하한(포함)": "2026-08-20 00:00:00",
              "상한(제외)": "2026-09-05 00:00:00", "달력일수": 16 },
  "몽고 필터": { "occ_date": { "$gte": "2026-08-20 00:00:00",
                            "$lt": "2026-09-05 00:00:00" } },
  "형식 문제": null
}
```

## 네 가지 함정

### ① 월요일의 "어제"는 금요일이다

`today - 1`이 아니라 **직전 평일**이다. 주말 제외는 config
(`window.exclude_weekdays`)가 정한다 — 사내 휴일 달력이 아직 없어서 지금은
주말만 뺀다. 달력이 생기면 여기만 넓히면 된다.

상한이 오늘이 아니라 어제까지인 이유도 같은 계열이다. 아침 8시 잡이 오늘을
포함하면 "오늘"만 8시간짜리 반쪽 막대가 돼서, 추세 그래프가 **매일 급감한
것처럼** 보인다.

### ② `occ_date`가 문자열이라는 것의 무게

대상 컬렉션의 날짜는 `datetime`이 아니라 `"2026-08-21 00:00:00"`이다. Mongo의
`$gte`/`$lt`는 문자열에 대해 **사전순(바이트 순)**으로 비교한다. 형식이
"고정폭 + 큰 자리 우선"이 아니면 범위 쿼리가 조용히 **다른 구간**을 읽는다.

| 형식 | 1999-12-31 | 2000-01-01 | 결과 |
|---|---|---|---|
| `%Y-%m-%d` | `1999-12-31` | `2000-01-01` | ✅ 사전순 = 시간순 |
| `%d/%m/%Y` | `31/12/1999` | `01/01/2000` | ❌ 나중 날짜가 앞선다 |
| `%y-%m-%d` | `99-12-31` | `00-01-01` | ❌ 세기 경계에서 뒤집힌다 |
| `%Y-%m` | `1999-12` | `1999-12`(같은 달) | ❌ 날짜별로 못 나눈다 |

`date_format_problem`이 **기동에서** 이걸 거부한다. 런타임에 발견되면 "숫자가
좀 이상한데"로만 보이고 원인을 아무도 못 찾는다. 검사는 표본 날짜 8개를 찍어
① 플랫폼에서 쓸 수 있는가 ② 되읽어서 같은 날이 되는가 ③ 길이가 고정인가
④ 사전순이 시간순과 같은가를 본다.

### ③ 주말은 쿼리로 못 뺀다

문자열 날짜에서 요일을 뽑는 서버 측 연산이 없다(`$dayOfWeek`는 date 타입
전용). **뺄 수 있어도 안 뺀다** — 대상 시스템에 계산을 미루는 만큼 그쪽 부하다.
범위 하나로 긁어 오고 요일 거르기는 우리가 한다(`window.selected`).

그래서 `조회 범위`의 달력일수(16)와 `집계 대상`의 개수(7)가 다르다. 이건 버그가
아니라 설계다.

### ④ 전주 동요일이 범위 밖으로 나가면 안 된다

"전주 대비"를 별도 쿼리로 또 나가면 대상 Mongo 왕복이 두 배가 된다. 그래서
하한을 `days[0]`이 아니라 **그 전주 동요일**까지 내린다(위 예에서 08-20).
이게 깨지면 비교 칸이 **항상** 비어서 "데이터가 없네"로 오인된다 —
`test_전주_비교값이_조회_범위_안에_있다`가 100일치를 훑으며 지킨다.

보존 기간(TTL) 밖이라 그 구간이 비어 있는 것은 정상이고, 그때는 비교 칸만
비운다(경고를 내지 않는다).

## 시나리오는 왜 사이트 config가 아닌가

리포트는 **사이트를 가로지른다.** `fct/gumi/mx.json`에 두면 사이트마다 잡이
등록돼 같은 리포트가 N번 돌고 메일도 N통 간다. 그래서 층 병합 없이
`config/scenarios/<이름>.json` 한 파일 = 시나리오 하나다. 이름은 **파일
이름**이 정한다(파일 안에 또 적으면 둘이 어긋났을 때 어느 쪽이 맞는지 모른다).

컬렉션 이름과 필드 이름까지 config인 이유: `alarm`을 코드에 박으면 다른
컬렉션으로 같은 리포트를 못 내고, 필드 이름이 법인마다 다를 때 손댈 곳이
코드가 된다. **코드는 "어떻게 집계하는가"만 알고, "무엇을 읽는가"는 config가
안다.**

`scope.gbms`와 `scope.sites`는 registry에서 유추하지 않는다 — 새 사이트를
등록하는 순간 리포트의 분모가 조용히 바뀐다.

## 기동에서 막는 것 / 막지 않는 것

- **막는다**: 사전순이 깨지는 날짜 형식, registry에 **없는** 사이트(오타는
  런타임에 못 고친다), 법인이 하나도 없는 GBM(빈 열은 "0건"과 "대상 아님"을
  구분해 주지 않는다), 모르는 요일 이름, 모든 요일 제외.
- **안 막는다**: registry에서 `enabled: false`인 사이트. 그건 "지금 못 붙는다"는
  정상 상태이고, 리포트는 그런 법인을 본문 하단 제외 목록에 **이름으로** 남긴다.
  분모에서 조용히 사라지는 것만 아니면 된다.

## 검토 포인트

0. `config.example/scenarios/`를 **`config/scenarios/`로 복사**했는가 — 명령은
   `--config-root` 기본값인 `config/`를 본다. 예제 트리는 본보기일 뿐이다.
1. `report window --today`를 월/화/토요일로 각각 돌려 날짜 목록이 상식과 맞는가.
2. 사내 `occ_date` 형식이 정말 `%Y-%m-%d %H:%M:%S`인가 — 다르면
   `scenarios/daily-alarm.json`의 `date_format`만 바꾸면 된다.
3. `unresolved_status`(0·10·1)와 필드 이름 매핑이 실제 문서와 맞는가.
4. ~~`occ_date`에 인덱스가 있는가~~ → **있다**(2026-09 확인). 16일치 범위 스캔이
   인덱스를 타므로 9b는 한 번에 긁는 설계 그대로 간다. 인덱스가 없었다면 하루씩
   쪼개 던지거나 `sample`을 더 조여야 했다.
