# 11a단계 — 대상 코드 확보와 지식 층 (1차)

> **목적**: 리드가 "토픽 179개 중 뭐가 맞나"에 **이름 유사도가 아니라 코드로**
>답할 수 있게 하는 토대. 1차는 지식 층·포트·진단까지다 — 리드가 실제로 부르는 것은
> 2차(등재표에 `code.*`)다.

```bash
python -m src code status     # 읽을 수 있는 상태인가 (네트워크 없음)
python -m src code plan       # 사람이 직접 칠 git 명령 (네트워크 없음)
python -m src code sync       # clone/fetch — 사내에서만
```

```
  mx — 레포 2개 · 서비스 3개

  ✅ dt-core  ../target-code/dt-core
       origin https://git.example.com/team/dt-core
       ✅ processor @ main  (가정)
       ✅ sink @ main  (가정)
```

**`(가정)`을 보라.** 배포 선언이 없어서 `main` 최신이라고 **가정**했다는 뜻이다.
확인된 것과 가정한 것을 같은 모양으로 찍으면, 뒤처진 사이트에서 떠 있지도 않은
코드를 읽고 확신에 찬 오답을 낸다.

## 세 층이 각각 다른 질문에 답한다

| 층 | 답하는 질문 | 어디 | 누가 언제 고치나 |
|---|---|---|---|
| 토폴로지 | 어느 서비스가 어느 레포의 무엇인가 | `knowledge/topology/<gbm>.json` | 구조가 바뀔 때만 |
| config | 그 레포를 어디서 받아 어디에 두는가 | `config/gbm\|fct/*.json`의 `code.repos` | 배치가 바뀔 때 |
| deployment | 이 GBM에 지금 어느 커밋이 떠 있는가 | `knowledge/deployment/<gbm>.json` | 배포할 때마다 |

## 사내 사실이 설계를 두 번 고쳤다

`decisions.md`에 적혀 있던 것이 **둘 다 틀렸다.** 고쳐 적었다.

### ① 단위는 사이트가 아니라 GBM이다

②는 "사이트마다 배포 커밋이 다르다"를 submodule 기각의 결정적 근거로 적었다.
실제로는 **코드가 GBM 단위로 같고** 배포 커밋은 기본적으로 `main` 최신이다.

- deployment가 사이트 28개 → **GBM 4개**가 됐다. 손으로 유지할 양이 1/7이다
- ⑧ "사이트 간 배포 차이는 1급 증거"가 **"GBM 간"**이 됐다. 같은 GBM 안에서는
  비교할 것이 없고, "MX는 되는데 NW는 안 된다"가 살아남은 신호다
- **submodule 기각은 그대로다.** 근거가 바뀌었을 뿐이다 — GBM이 4개라 포인터
  하나로는 여전히 부족하고, 무엇보다 **과거 커밋을 읽는 것**이 조사의 핵심인데
  서브모듈 체크아웃에는 그 객체가 없다

### ② 서비스는 `(레포, 경로)`가 아니라 `(레포, 선택자)`다

③은 `path`로 `git grep`을 좁힌다는 전제였다. 실제로는 한 레포에 서비스가 여럿인
것이 **디렉터리가 나뉜 게 아니라 코드가 하나이고 `.env`가 역할을 고르는** 것이다.
그러면 좁힐 경로가 없다.

`selects`가 "이 env 값이면 이 서비스"를 적고, 디렉터리가 실제로 나뉜 레포만
`path`를 쓴다.

### 그리고 — 이름이 코드에 없다

컬렉션·토픽 이름이 소스에 리터럴로 박혀 있지 않고 **대상의 config 파일**에 있다.
그것도 층 병합 형식이다(우리 `config/`와 같은 구조). 다행히 그 파일들이 **레포 안에
버전 관리돼 있어서** `git show <배포커밋>:config/...`로 닿는다.

그래서 조사의 실제 경로는 "소스를 grep한다"가 아니라 **"config 파일에서 이름을 찾고
어느 층에서 왔는지 본다"**이다. `Topology.config_paths`가 그 층들을 가리키고, **`{gbm}`·`{fct}`를 쓸 수 있다** —
대상 config가 법인별로도 갈리기 때문이다(`config/factories/{fct}/{gbm}.json`).
문법은 우리 `SITE_LAYERS`와 같게 맞췄다.

`KafkaConsumerConfig`에서 템플릿을 기각한 것과는 **다른 경우다.** 거기서 문제는
오타 난 템플릿이 **존재하지 않는 그룹을 조용히 감시**하는 것이었다 — lag 0이 정상과
구별되지 않는다. 여기는 오타가 "그 커밋에 그 파일이 없다"로 **시끄럽게** 드러나고,
게다가 아는 자리 이름(`gbm`·`fct`)만 허용해서 오타 자체가 기동에서 막힌다.

**우리가 그 층을 합쳐서 답을 주지는 않는다.** 대상의 병합 규칙이 우리와 같다는
보장이 없고, 추측으로 합친 값은 틀려도 그럴듯해 보인다.

## `code read` — **읽기가 실제로 되는가**

```bash
python -m src code read --service processor --path config/common.json --gbm mx
```

```
  processor → dt-core @ a3f9c2
  config/common.json

  {"name": "…"}
```

`code status`는 파일이 **있는지**만 본다(`git cat-file -e`). 이 명령이 없으면
**`git show <배포커밋>:경로`가 실제로 내용을 돌려주는가** — 11a의 핵심 계약 — 를
확인할 방법이 없고, 2차에서 문제가 나면 1차 탓인지 2차 탓인지 섞인다.
3b의 `peek redis`가 한 역할과 같고, 2차의 `code.read` action이 같은 포트를 쓴다.

`--path`는 `config_paths`와 **같은 자리표시자**를 받는다(`{gbm}`·`{fct}`) — 그래야
사람이 토폴로지에서 복사해 붙일 수 있다. 배포 선언이 없으면 `(배포 커밋을 가정했다)`가
붙는다.

## 코드 명령은 `--fct`를 요구하지 않는다

코드는 GBM 단위로 같다. 그런데 처음엔 `_resolve_site`를 그대로 써서 **법인을
요구했다** — 답이 뜻이 없는 질문이고, 사람은 매번 의미 없는 값을 타이핑하게 된다.

이제 그 GBM의 활성 사이트 중 하나를 코드가 고른다. `--fct`를 주면 그것을 쓴다 —
`config_paths`의 `{fct}` 해석이 달라지므로 특정 법인의 층을 보고 싶을 때가 있다.
`code status`가 **어느 법인 기준인지 출력에 적는다.**

그리고 같은 GBM의 사이트들이 **다른 레포를 선언하면 경고한다.** 누가 `fct/` 층에
`code.repos`를 적으면 "코드는 GBM 단위로 같다"는 전제가 조용히 깨지고, 우리는
**사이트마다 다른 코드를 읽으면서 같은 것을 읽는 줄 안다.** 그 검사는 `--fct`와
무관하게 GBM 전체를 본다 — 고른 사이트만 보면 갈릴 리가 없어 검사가 아무 일도 안 한다
(처음에 그렇게 썼고, RED 확인에서 드러났다).

## 자물쇠 여섯 (`code status`가 보는 것)

1. **경로가 있나**
2. **`.git`이 있나** — 작업 트리만 복사되면 `git show <커밋>:경로`가 통째로 안 된다.
   우리 설계의 전제가 무너지는 자리다
3. **`origin`이 config와 같나** — 누가 포크를 그 경로에 클론하면 우리는 그럴듯한
   코드를 읽고 그럴듯한 판정을 낸다. **전부 틀린 채로.** "코드를 못 읽었다"보다
   훨씬 나쁘다: 실패가 조용하고 판정은 확신에 차 있다
4. **배포가 가리키는 커밋이 로컬에 실재하나**
5. **`config_paths`가 그 커밋에 실재하나** — 이름이 대상의 config 파일에 살기
   때문에, 경로 앞머리가 틀리면 리드는 아무것도 못 찾는다. 증상은 "조사가 빈손"이라
   원인이 안 보인다. 사람이 손으로 적는 칸이라 오타가 정상적으로 일어난다.

   **층은 선택이다** — 우리 `SITE_LAYERS`와 같다. `fct/{fct}/common.json`이 없는
   법인이 정상이듯 대상도 그렇다. 그래서 없는 층은 적어만 주고, **하나도 없을 때만**
   빨간불이다. 없는 층마다 빨간불을 켜면 사람이 검사를 끈다
6. **그 커밋의 submodule을 읽을 수 있나** — 안 채워진 submodule을 두고 `git grep`은
   **종료코드 1에 출력 없이** 끝난다. 우리는 그걸 "결과 없음"으로 읽으므로, 여기서
   말하지 않으면 2차의 판정이 "코드에 그런 게 없다"를 단정한다. git 자신이 조용해서
   **아무 데서도 안 보이는** 실패다(decisions ②-2).

   "채워졌다"로는 부족하다 — **그 커밋이 박은 버전의 객체가 있나**까지 본다.
   부모만 당겨진 트리가 정확히 그 상태이고, `.git`이 있어서 겉보기엔 정상이다

3번은 `.git` 꼬리와 끝 슬래시만 봐준다. **호스트가 다르면 같게 안 본다** — 관대함이
거기까지 오면 자물쇠가 아니다. 반대로 `.git` 유무로 실패하면 사람이 자물쇠를 끄고
싶어진다. **끌 수 있는 자물쇠는 잠기지 않는다.**

## 대상 레포가 submodule을 품고 있으면

"클론해 둔 코드가 submodule을 포함하면 그것도 최신이 맞다고 하는 거냐"는 물음에서
나왔다. **답은 "최신이라고 가정하지 않는다"가 아니라 "가정할 필요가 없다"다** —
부모의 배포 커밋이 submodule의 SHA를 박아 두기 때문이다(gitlink). 전체 논거는
[decisions ②-2](decisions.md).

위험한 것은 버전이 아니라 **침묵**이었다. 측정해 보니 안 채워진 submodule을 두고
`git grep`은 종료코드 1에 stdout도 stderr도 비어 있다 — 우리가 "결과 없음"으로
읽는 바로 그 모양이다. 2차의 `code.grep`이 그걸 받으면 **"코드에 그런 게 없다"**가
된다. `--recurse-submodules`를 붙여도 똑같이 조용하다.

그래서 방어를 세 층에 나눠 뒀다:

| 층 | 하는 일 |
|---|---|
| `checkout.sync` | clone에 `--recurse-submodules`, 기존 트리엔 `submodule update --init --recursive`. 채우다 실패하면 fetch가 됐어도 `failed` |
| `checkout.submodules_at` / `unpopulated` | `code status`가 신고할 사실 |
| `git_reader` | `show`는 gitlink를 풀어 **박힌 SHA로** 읽고, 못 채워졌으면 "없다"가 아니라 "못 본다"로 실패. `grep`/`ls`는 `complete=False`로 돌아온다 |

세 번째가 핵심이다. **2차의 action이 쓰는 것은 CLI가 아니라 이 포트**라서,
방어를 CLI에만 두면 리드는 그대로 조용한 0건을 받는다.

읽은 버전은 증거에 남는다 — `source`가
`code.show p@main:vendor/libs/x.json (submodule vendor/libs@444be98067a7)`이다.
나중에 "어느 코드를 본 거냐"를 되짚을 수 있어야 판정이 검증 가능하다.

## `git submodule status`를 쓰지 않는다 — 포슬린은 깨질 자리가 많다

"등록됐나"를 `git submodule status`의 앞 글자로 읽었다. 신호는 맞다. 그런데
**그 명령이 사내 Windows에서 실패했다.** `submodule`은 포슬린이고 플랫폼에 따라
셸 스크립트를 타므로, 우리가 예상 못 한 이유로 죽을 자리가 많다.

필요한 사실은 **평범한 읽기 두 개**면 충분하다:

| 묻는 것 | 어떻게 |
|---|---|
| 로컬에 등록됐나 | `git config --get-regexp ^submodule\..*\.url` |
| 내용이 있나 | `<경로>/.git`이 있나 |

네 가지 상태에서 `git grep`의 **실제 동작과 일치**하는 것을 확인했다:

| 상태 | 등록 | `.git` | 우리 판정 | grep 실제 |
|---|---|---|---|---|
| 안 채움 | ✗ | ✗ | 못 봄 | 조용히 0건 |
| 내용만 직접 넣음 | ✗ | ✓ | 못 봄 | 조용히 0건 |
| `init`만 함 | ✓ | ✗ | 못 봄 | 조용히 0건 |
| 제대로 채움 | ✓ | ✓ | 읽을 수 있음 | 본다 |

### 등록은 **경로가 아니라 이름**으로 걸린다

`submodule.<이름>.url`의 이름은 `.gitmodules`의 섹션 이름이다. 대개 경로와 같지만
`git submodule add --name`을 쓴 저장소에서는 다르고, 경로로 찾으면 멀쩡히 채워진
submodule을 **"등록 안 됨"으로 오판한다** — 그러면 조사가 읽을 수 있는 코드를
"못 본다"고 적는다. 그래서 `parse_gitmodules`가 **이름 → 경로**를 돌려준다.

### 거짓 초록 하나를 RED가 잡았다

"config를 못 읽으면 안전하게 전부 못 본다고 답한다"는 분기를 따로 뒀는데, RED를
걸어 보니 **지워도 결과가 같았다** — 읽기에 실패하면 등록 목록이 어차피 비고,
그러면 전부 "못 봄"이 된다. 방어가 아니라 무동작이었다. 지우고 그 성질을
주석으로 남겼다. 불변식을 재는 테스트는 남겼다(실패를 낙관적으로 바꾸면 빨개진다).

## 테스트는 git으로 네트워크를 타지 않는다 — 물리적으로

픽스처가 `origin`에 `https://git.example.com/...`을 적는다. `status_of`의 origin
대조가 볼 값이 필요해서고, **그 주소에는 아무도 접속하지 않는다.** submodule url은
로컬 경로다.

그런데 "안 한다"는 주장과 "못 한다"는 사실은 다르다. 그래서 전역 픽스처가
`GIT_ALLOW_PROTOCOL=file`을 건다 — git이 http/https/ssh를 **아예 거부한다.**
누가 네트워크를 타는 픽스처를 넣으면 그 자리에서 빨개진다(https를 타는 테스트를
넣어 `fatal: transport 'https' not allowed`가 나는 것까지 확인했다).

## 픽스처가 **실물과 다르게** 만들고 있었다

앞의 둘을 고치자 실패가 반대로 뒤집혔다: `assert ['vendor/libs'] == []` —
채웠는데도 "안 채워졌다"고 나온다.

원인은 내가 submodule을 채우는 방식이었다. `git clone`으로 그 자리에 직접 받고
`git submodule init`으로 등록했는데, 그러면 `.git`이 **파일이 아니라 디렉터리**가
된다. 진짜 submodule은 `.git`이 `../../.git/modules/…`를 가리키는 파일이다.
Linux에서는 둘 다 `git submodule status`가 정상으로 읽혔지만, **모양이 다르면
어느 플랫폼에서 어떻게 갈릴지 우리는 모른다.** 픽스처가 실물과 다르면 그 차이
자체가 버그의 근원이 된다.

이제 `git submodule update --init`을 쓴다 — git이 하는 바로 그 명령이다. 손으로
만든 gitlink 위에서도 그대로 동작한다(확인함). 여기만 file 프로토콜 허락이
필요하고, **만드는 쪽**은 여전히 허락을 안 탄다.

### 그리고 픽스처가 자기 결과를 확인한다

`populate_submodule`이 끝나고 `git submodule status`를 직접 본다. 안 채워졌으면
**거기서** 죽는다:

```
submodule을 채웠는데 git이 아직 '등록 안 됨'이라고 한다 — [-dc164b6… vendor/libs]
  이 상태에서는 `git grep --recurse-submodules`가 조용히 0건을 준다
```

안 그러면 "채웠다고 믿었는데 아니었다"가 **세 단계 뒤의 엉뚱한 assert**로
나타난다 — 실제로 그렇게 한 라운드를 썼다.

### 물어보지 못한 것과 "안 채워진 것"을 구별한다

`git submodule status`가 실패하면 `unpopulated`는 안전하게 "전부 못 본다"고
답한다. 그건 맞다. 그런데 화면에 그 이유가 안 나가면 사람은 submodule을 채우려고
애쓰는데 원인은 다른 데 있다. `submodule_marks`가 이유를 따로 돌려주고
`code status`가 그걸 찍는다 — ⑪(`ok`/`finding`/`unreachable`)과 같은 구별이다.

## 사내(Windows)에서만 터진 것 둘 — 둘 다 재현해서 잡았다

`cwd=C:\...`가 단서였다. Linux에서는 절대 안 나는 실패가 둘 있었다.

### ① `text=True`는 로캘로 디코딩한다 — git은 UTF-8로 뱉는다

한국어 Windows의 ANSI 코드 페이지는 cp949다. `tmp_path`에 한글이 들어간
디렉터리에서 `git show main:.gitmodules`를 부르면:

```
UnicodeDecodeError: 'cp949' codec can't decode byte 0xec ...
```

그리고 `_git`의 `except Exception`이 그걸 **`code=1`로 흡수한다.** 결과:

| 부른 것 | 나온 답 | 진짜 |
|---|---|---|
| `submodules_at` | `[]` | "이 커밋엔 submodule이 없다" ← 거짓 |
| `status_of` | origin을 못 읽음 | "origin이 config와 다르다" ← 거짓 |

**제품 코드 버그다.** 대상 레포에 한글 경로·브랜치·커밋 메시지가 하나라도 있으면
사내에서 `code status`가 조용히 틀린 답을 낸다. `encoding="utf-8"`로 고정했다.

`tests/test_portability.py`가 이미 **똑같은 함정을 `open()`에 대해** 막고 있었는데
(`Windows의 기본 인코딩은 로케일이다`), `subprocess`에는 그 규율이 없었다. AST
검사기를 하나 더 넣어서 `text=True`인데 `encoding`이 없는 호출을 전부 잡는다 —
새로 생기는 호출부까지 같이 지킨다.

### ② `.gitmodules`의 `\`는 이스케이프 문자다

픽스처가 submodule url로 `str(Path)`를 적었는데, Windows에서는
`C:\Users\t\libs`다. git config는 `\`를 이스케이프로 읽어서 `\t`가 **탭**이 되고:

```
fatal: bad config line 3 in file .gitmodules
```

증상은 `git submodule init` 실패라 원인이 그 한 줄에 있다는 게 안 보인다.
구분자를 `/`로 바꾼다(git은 Windows에서도 `/`를 받는다).

### 남는 규율

> **Linux에서 초록인 것은 Windows에 대해 아무것도 증명하지 않는다.**
> 자식 프로세스의 출력도 파일과 똑같이 인코딩을 명시하고, git config에 들어가는
> 값은 경로라도 그냥 적지 마라.

## 내가 여기서 실제로 틀린 것 — 검증 환경을 내가 고쳐 놓았다

submodule 작업을 시작하면서 **첫 명령으로 `git config --global
protocol.file.allow always`를 켰다.** 로컬 경로를 submodule로 붙이려면 필요한
설정이고, 그래야 픽스처가 세워졌다. 그리고 그 기계 위에서 전부 통과시켰다.

그러면 **내 트리는 항상 초록이고 남의 기계에서만 깨진다.** 두 라운드 동안
원인을 못 찾고 `GIT_CONFIG_*`·능력 검사 같은 장치를 덧댔는데, 전부 내가 만든
문제를 내가 막는 코드였다.

보통 버그보다 나쁘다. 코드가 틀린 것이 아니라 **검증이 무의미해진 것**이고,
그동안 내가 "1073 통과"라고 보고한 것들이 전부 그 위에서 나온 숫자다.

### 그래서 픽스처가 허락을 아예 안 타게 바꿨다

`.gitmodules`는 그냥 파일이고 gitlink는 트리 항목(mode 160000)이다. 둘 다 손으로
만들 수 있고 **전송이 일어나지 않으므로 어떤 허락도 필요 없다.** 채우는 것도
평범한 `git clone` + `git submodule init`이면 된다 — 막히는 것은 submodule
전송이지 사람이 직접 하는 로컬 클론이 아니다.

`git submodule add`가 필요한 자리는 이제 **한 테스트뿐**이다(`sync`가 진짜로
채우는지 보는 것 — 거기서 도는 것이 제품 코드라 우회할 자리가 없다).

그리고 그 규율을 테스트로 박아 뒀다:
`test_submodule_픽스처가_file_프로토콜_허락을_안_탄다`가 git의 **기본값(`user`)**
을 명시적으로 박고 픽스처를 세운다. 누가 `submodule add`로 되돌리면 거기가 먼저
빨개진다 — 되돌려서 실제로 빨개지는 것까지 확인했다.

### 남는 규율

> **환경을 고쳐서 초록을 만들었다면, 그 초록은 증거가 아니다.**
> 전역 설정·환경변수·`~/.gitconfig`를 건드렸다면 원래대로 돌려놓고 다시 재라.

## 사내가 실제로 submodule을 쓴다 — 측정한 것들

"실제로 쓴다"는 답을 받고 git 2.43에 대고 일곱 가지를 직접 재 봤다. 추측으로 적었으면
두 개는 틀렸을 것이다.

| # | 잰 것 | 결과 |
|---|---|---|
| 1 | `-c` 설정이 submodule 하위 프로세스로 가나 | **간다.** 인증 헤더도 따라 내려간다 → 호스트로 묶어야 한다 |
| 2 | `cat-file -e <커밋>:<서브>/경로` | **채워져 있어도 실패**(`exists on disk, but not in 'main'`) |
| 3 | 옛 부모 커밋의 submodule 읽기 | **된다.** gitlink를 풀면 그 시점 내용이 나온다 |
| 4 | `fetch`의 기본값 | `fetch.recurseSubmodules=on-demand`가 기본이라 대개 알아서 따라온다 |
| 5 | 객체가 진짜 없을 때 | `show`는 128, `grep`은 128 + `unable to read tree` — **조용하진 않지만 말이 오해를 부른다** |
| 6 | 지금 `sync` 순서가 5를 고치나 | **고친다**(fetch → `submodule update --init --recursive`) |
| 7 | `http.<url>.extraHeader` 문법 | git이 받고, **다른 호스트엔 안 붙는다** |
| 8 | `grep --recurse-submodules`가 보는 범위 | **등록된 것만.** `.git`이 있어도 등록이 없으면 조용히 건너뛴다 |

2번이 실제 오진을 만들고 있었다. 이름이 사는 config 층이 공용 라이브러리 submodule에
있으면 `code status`가 "config_paths가 그 커밋에 하나도 없다 → 경로를 고쳐라"라고 한다.
**경로는 맞았는데** 사람은 맞는 경로를 고치게 된다. 지금은 경계를 넘어서 확인하고,
submodule이 안 읽히는 상태면 "먼저 위의 submodule부터"라고 말한다.

5번이 **세 번째 상태**를 드러냈다. `.git`이 있으니 `unpopulated`는 "채워졌다"고
말하는데, 그 커밋이 박은 버전의 객체가 없다. 상태가 셋이다:

| 상태 | 어떻게 보이나 |
|---|---|
| 등록 안 됨(`git submodule status`가 `-`) | `grep`이 **조용히** 0건 — `.git`이 있어도 그렇다 |
| 채워졌지만 그 버전이 없음 | 128 + `unable to read tree` — 시끄럽지만 말이 틀리게 읽힌다 |
| 읽을 수 있음 | 옛 커밋까지 정상 |

## 토큰은 디스크에 안 남는다

`https://<토큰>@호스트/…`로 클론하면 git이 그 URL을 **`.git/config`에 평문으로
저장한다.** 토큰이 디스크에 남고, 그 파일은 백업·이미지·로그 어디로든 따라간다.

- config의 `url`은 **토큰 없는 깨끗한 주소**다. 섞여 있으면 스키마가 거부한다
- 인증은 `git -c http.extraHeader=...`로 **명령마다** 넘긴다
- `code plan`이 출력하는 명령에도 토큰을 안 찍는다 — 사람이 복사해 붙이면 셸
  히스토리에 남는다
- git이 뱉은 오류에서도 지운다(`_scrub`)

덤으로 `origin` 대조가 비밀값 비교가 되지 않는다.

### 토큰에 줄 권한

fine-grained token에 필요한 것은 **둘뿐이다.**

| | |
|---|---|
| Repository → **Contents** | **Read-only** — `git clone`·`fetch`를 허용하는 것이 이것이다 |
| Repository → **Metadata** | **Read-only** — 다른 권한을 고르면 자동으로 켜진다. 끌 수 없다 |
| **Organization permissions** | **전부 없음.** org 소유 레포를 클론하는 데 관여하지 않는다 |

**Contents를 write로 주지 않는다.** 포트에 쓰기 메서드를 안 만든 것과 같은 이유다 —
권한도 같은 성질이어야 한다. 표현 불가능한 것은 사고도 못 낸다.

발급할 때 틀리기 쉬운 것: Resource owner를 **조직**으로 골라야 org 레포가 보인다 ·
Repository access는 `Only select repositories`(등재제와 같은 성질) · 많은 org가
**관리자 승인**을 요구해서 승인 전까지 403이다 · SAML SSO면 토큰에 SSO 승인이 따로 필요하다.

**submodule을 쓰면 그 레포들도 토큰 범위에 넣어야 한다.** `Only select repositories`에
부모만 골라 두면 submodule 클론이 403으로 죽고, `code sync`는 (지금은) `failed`로
말하지만 그 전까지는 "부모만 받아지고 조용히 반쪽"이 될 수 있었다.

그리고 **헤더를 호스트로 묶었다**: `http.extraHeader`가 아니라
`http.<스킴://호스트>/.extraHeader`다. 측정해 보니 `-c`로 준 설정이 **submodule
하위 클론까지 전파된다**(`-c protocol.file.allow=never`를 주니 submodule 클론이
막혔다 — 즉 우리 인증 헤더도 똑같이 내려간다). 묶지 않으면 `.gitmodules`가 가리키는
**아무 호스트에나 우리 토큰이 날아간다.** 공용 라이브러리가 다른 호스트에 있는 것은
흔한 일이다. ssh url에는 헤더를 아예 안 붙인다 — 거기선 뜻이 없고, 얹으면 "되는 줄
알고 안 되는" 설정이 된다.

**만료가 조용한 실패를 만든다.** 토큰이 만료되면 `code sync`는 403으로 실패하지만
**`code status`는 못 잡는다** — 네트워크를 안 타기 때문이다. 이미 클론된 레포는 계속
읽히므로 증상이 "코드가 점점 낡는다"가 되고, 그건 알아채기 어렵다. 만료일은 사람이
보는 곳에 적어 둬야 한다.

## 배포가 컨테이너이고 **재시작마다 사라진다면**

체크아웃이 디스크 상태라는 것이 여기서 값을 치른다. 확인된 배포 모양이 그렇다.

| | |
|---|---|
| 디스크 | 문제 아니다 — 레포가 GB 단위가 아니다 |
| **기동 때 `code sync` 한 번이 필수** | 안 돌리면 `code.*`가 전부 "`.git`이 없다"로 실패한다 |
| 클론 시간만큼 첫 조사가 늦다 | 그 사이 케이스가 열리면 **코드 증거 없이** 돈다 |
| 토큰이 기동 경로에 온다 | 만료되면 기동부터 막힌다 — 조용히 낡는 것보다 낫다 |

**"코드를 아직 안 받았다"와 "코드에 그런 게 없다"는 같은 모양이면 안 된다.**
어댑터가 `.git이 없다 — code status를 보라`로 구별해 말한다.

### 누가 `code sync`를 부르나 — **아직 아무도 안 부른다**

14단계의 데몬이 생기기 전까지는 컨테이너 entrypoint가 맞다:

```bash
python -m src code sync --gbm mx && python -m src ...
```

`&&`인 것이 뜻이 있다. **sync가 실패하면 기동을 막는 쪽을 권한다** — 코드를 못 읽는
조사는 "이름 유사도로 찍는" 상태로 되돌아가는데, 그건 조용히 나쁜 답을 내는 것이라
안 도는 것보다 나쁘다. 가용성을 택하겠다면 그건 **명시적 판단**이어야 한다.

### shallow clone은 **재 본 뒤에** 넣는다

재시작마다 클론하니 `--depth`로 얕게 받고 싶어진다. 레포가 GB 단위가 아니므로
**재 보기 전의 최적화다.** 클론 시간이 실제로 아프면 그때 넣는다.

넣을 때를 위해 구분 하나: `--depth`(shallow)는 `--filter=blob:none`(partial)과 **다른
물건이다.** shallow는 가진 커밋이 완전해서 **읽기가 네트워크를 안 탄다** — ②가 기각한
것은 후자다. 대신 창 밖의 오래된 배포 커밋이 로컬에 없어지는데, 그건 `code status`의
④가 미리 잡는다(`git fetch --deepen`으로 푼다).

## 기동은 **선언끼리의 어긋남**만 본다

디스크 상태(체크아웃이 실제로 있는가)는 `code status`의 일이다. 기동이 거기서
막히면 개발 환경에서 늘 빨간불이고, **그러면 사람이 기동 검증을 통째로 끈다.**

기동이 잡는 것: 토폴로지가 없는 레포를 가리키나 · 배포가 없는 서비스를 가리키나 ·
레포를 선언해 놓고 토폴로지가 없나. 전부 증상이 **"코드 증거가 조용히 안 나온다"**라
런타임에는 원인이 안 보인다.

## 2차 — 리드가 서비스 이름으로 코드를 읽는다

1차는 CLI로만 읽혔다. 2차는 등재표에 `code.*` 넷을 올린다.

| action | 리드가 대는 것 | **코드가 정하는 것** |
|---|---|---|
| `code.services` | (없음) | — |
| `code.config` | `service` | 레포 · 커밋 · 법인 · 층 경로 · 병합 규칙 |
| `code.grep` | `patterns`, `service?` | 레포 · 커밋 |
| `code.read` | `service`, `path` | 레포 · 커밋 |

**레포도 커밋도 인자에 없다.** 리드는 SHA를 모르고, 모르면 지어낸다 — 그러면 떠
있지도 않은 코드를 읽고 확신에 찬 오답을 낸다(규율 3과 같은 계열). `read`의
`path`도 지어내는 자리가 아니라 **`grep`이 돌려준 경로**다.

### `config`가 `read`와 따로 있는 이유

이름이 사는 config는 층으로 갈린다. gumi면 셋:

```
config/gbm/mx.json → config/factories/gumi/common.json → config/factories/gumi/mx.json
```

층 하나만 읽으면 **위 층이 덮어쓴 값을 사실로 단정한다.** 그래서 `config()`는 층
전부를 읽어 `merge_target`으로 합치고, **어느 층을 읽었는지 `source`에 남긴다.**

실제로 돌린 결과(`code config --service processor`):

```
code.config processor @ main (가정)
  [config/gbm/mx.json → config/factories/gumi/common.json → config/factories/gumi/mx.json]

{"kafka": {"topic": "GUMI_ALARM_EVENT",   ← 맨 위 층이 덮었다
           "group": "G"},                 ← 밑바닥이 살아남았다
 "mongo": {"collection": "gumi_docs"}}    ← 가운데 층이 덮었다
```

같은 커밋인데 `--fct sevt`면 답이 갈린다. **법인은 케이스의 사이트에서 온다** —
리드가 고르는 값이 아니다.

### 사내에서 바로 터진 것: **우리가 자르고 대상을 탓했다**

첫 사내 실행에서 이렇게 나왔다:

```
config/gbm/mx.json: JSON이 아니다 — JSONDecodeError: Expecting ',' delimiter:
  line 400 column 35 (char 16846) — 합친 값이 실제와 다를 수 있다
```

**line 400**이 단서다. 리더의 기본 상한이 `_MAX_LINES = 400`이다. 파일은 멀쩡했고
**우리가 잘랐다.** 그리고 잘린 조각을 파싱해서 "JSON이 아니다"라고 말했다 —
원인은 우리인데 **대상이 지목된다.** 사람을 멀쩡한 파일 고치러 보내는 메시지다.
`unreachable`을 `finding`으로 적는 것과 같은 거짓말이다(⑪).

내 잘못이 둘이다:

1. **봉투가 이미 말하고 있었다.** `complete=False`가 붙어 있는데 그걸 안 보고
   파싱부터 했다. 이제 **파싱 전에** 본다.
2. **config는 통째로 읽어야 한다.** 소스 파일은 앞부분만 봐도 쓸모가 있지만
   잘린 JSON은 쓸모가 0이 아니라 마이너스다. `show(..., whole=True)`를 만들었다 —
   줄 수로 안 자르고, 상한은 1MB로 둔다(무한 읽기는 안 만든다).

덤으로 하나 더: 층이 전부 실패하면 예전엔 "하나도 없다 — 찾은 자리: …,
`code status`를 보라"라고만 했다. 그것도 **경로를 고치라는 말로 읽힌다.**
이제 실패한 이유를 그대로 싣는다.

### `DeployedCodePort`를 만든 이유

`tests/domain/test_actions.py`가 "등재표는 **포트에 있는 메서드**만 가리킨다"를
단정한다. `code.*`를 올리자 그게 빨개졌다 — 좋은 신호다. 포트를 만들어
`tests/domain/test_ports.py`의 **쓰기 동사 금지**까지 같이 받게 했다.

### 코드가 없으면 목록에 안 나온다

`code`의 가용 여부만 `site.infra`가 아니라 **knowledge**에서 온다. 없는 문을 열라고
적어 두면 리드가 거기로 가고, 매 라운드가 "미등재 action"으로 날아간다.

그리고 목록에 **서비스 이름을 박는다** — 사내 모델은 완결된 구체값을 그대로
복사하고 지시문 모양은 바꿔 넣는다(10b에서 측정). 안 적으면 `service="..."`를
진짜로 조회한다.

### 예시가 리드를 코드로 보낸다

등재만 해서는 아무 일도 안 일어난다. 사내 모델은 **예시를 그대로 복사하고 `goal`만
바꾼다**(10b에서 측정). 그래서 예시에 없는 action은 존재하지 않는 것과 같다.

| 라운드 | 첫 수 | 왜 |
|---|---|---|
| frame(발견) | `code.config {"service": "<진짜 이름>"}` | **이름은 대상 config에 있다.** 추측할 이유가 없다 |
| integrate | `code.grep {"patterns": ["위 증거에서 본 이름"]}` | 진단에서 제일 많던 위반이 "찾지 않고 이름을 댔다"였다 |

`service` 자리에 **진짜 이름을 박는다.** 완결된 구체값은 그대로 복사되고 지시문
모양은 바뀐다 — 그래서 `code.services`를 먼저 부르게 시키는 2단계보다 훨씬 잘 먹는다.
`patterns`는 반대로 증거에서 와야 하므로 일부러 지시문 모양이다.

카탈로그의 이름 힌트도 **`code.*` 바로 밑에** 붙인다. 목록 맨 끝에 두면 알파벳
순서상 한참 떨어지고, 순서대로 읽는 모델에게는 그만큼 안 보인다.

### 코드가 없는 사이트에서 조사가 죽으면 안 된다

토폴로지를 안 적은 사이트가 정상이다 — 코드 확보는 선택이다. `_code_if_ready`가
못 읽으면 `(None, ())`을 돌려주고, 그러면 `code.*`가 **목록에도 예시에도 안 나간다.**
리드가 없는 문을 두드릴 일이 없다. 반대로 지식이 멀쩡한데 비었다고 하면 그것도
안 되므로, 둘을 나눠 단정하는 테스트가 있다.

## 사내 측정 — 11a가 값을 했다, 그리고 새 구멍이 하나 드러났다

`case investigate --trace` 결과를 10b 때와 나란히 놓으면:

| | 10b (2차) | 11a 2차 |
|---|---|---|
| 읽기 | 5회 | **9회** |
| 계약 위반 | **3건** (`찾지 않고 이름을 댔다` 포함) | **1건** (중복 — 방어가 잡았다) |
| 가설 | open만 | **refuted 1 / supported 1** |
| 코드 읽기 | 없음 | t-1 `code.config` · t-4·t-8 `code.grep` |

리드가 낸 마지막 질의가
`mongo.find {'$or': [{'sent_yn': {'$exists': False}}, {'sent_yn': False}]}` —
**미발송 알람을 찾는 질의다.** 10b에선 나온 적 없는 모양이다.

**다만 과대해석하지 않는다.** `GUMI_ALARM_EVENT_MAIN`이 `code.config`에서 왔는지
`kafka.list_topics`에서 왔는지는 이 숫자로 구별되지 않는다. "위반 0건"은 사실이지만
"코드를 읽어서"라고는 아직 못 한다.

### 그리고 10b의 그 버그가 **내가 만든 자리에서** 되살아났다

진단의 "잘린 것 2건"을 파고들다 나왔다. 재현:

```
body 길이: 1206  (상한 1200)
complete: True                        ← 우리가 잘라 놓고 완전하다고 적었다
body에 mongo/collection 있나: False   ← 조사가 찾던 이름이 잘려 나갔다
```

`ProbeRunner`가 `complete`를 **봉투에서만** 가져왔다. 어댑터가 안 잘랐으면
`True`인데, 그 뒤에 우리가 `detail(limit=1200)`으로 자른다. `code.config`가 큰
dict를 돌려주기 전까지는 이 구멍이 안 드러났다.

세 군데를 고쳤다:

1. **우리가 자른 것도 잘린 것이다.** `detail`이 "잘랐나"를 돌려주고
   `complete = 봉투 and not 우리`가 된다. 요약에도 "(예산에서 잘렸다 — 없는 것이
   아니다)"가 붙는다.
2. **dict는 키 목록이 먼저다.** 목록에서 필드를 먼저 보여 주는 것과 같은 이유다.
   중첩 config를 `repr`로 눕혀 자르면 뒤쪽 키가 통째로 사라진다.
3. **큰 키 하나가 뒤의 키를 가리지 않는다.** 목록은 첫 초과에서 멈추지만(문서
   `[1]` 다음에 `[5]`가 나오면 헷갈린다) dict는 건너뛰고 계속한다. config는
   거대한 하위 트리 하나와 작고 중요한 키 여럿인 것이 보통이다.

고친 뒤 같은 상황:

```
complete: False
  키 3개: kafka, rules, mongo
  kafka: {'topic': 'GUMI_ALARM_EVENT_MAIN'}
  mongo: {'collection': 'alarm'}
  … 1개 키는 예산에서 빠졌다 (위 키 목록에는 있다)
```

진단도 이제 **무엇이** 잘렸는지 적는다(`✂ code.config api`). "잘린 것 2건"만
보고는 다음 라운드가 짐작이 되고, 실제로 그것 때문에 왕복이 한 번 더 들었다.

### 두 번째 측정: 진단이 원인을 그대로 짚어 줬다

`✂`를 붙이자마자 답이 나왔다. **잘린 셋과 리드가 반복한 셋이 정확히 같았다.**

```
증거 6건 · 잘린 것 3건
  ✂ code.config service='api'
  ✂ kafka.list_topics
  ✂ mongo.find collection='alarm' filter={} limit=5
리드 계약 위반 3건 — 3× 이미 한 읽기를 또 냈다
  t-7 mongo.find collection='alarm' filter={} limit=5   (= t-5 그대로)
  t-7 code.grep patterns=['GUMI_ALARM_EVENT_MAIN']      (= t-4 그대로)
  t-8 mongo.find collection='alarm' filter={} limit=5   (= t-5 그대로)
→ 낼 것이 없어져 라운드 3에서 `no_runnable`
```

**이건 모델의 실패가 아니라 우리의 모순이다.** `evidence_block`이 이렇게 적고
있었다:

```
(내용은 예산에서 빠졌다 — 필요하면 다시 읽어라)     ← 우리가 시키고
t-7: 이미 한 읽기를 또 냈다 — 받지 않는다            ← 우리가 거부한다
```

프롬프트에는 "같은 것을 또 읽는 것은 더 볼 것이 아니다"라는 산문 규칙이 이미
있었다. **졌다.** 증거 블록의 구체적인 한 줄이 산문 규칙을 이긴다 — 10b에서 측정한
성질("예시가 곧 명세")이 이번엔 반대로 작동한 것이다.

그리고 **거부됐다는 사실이 리드에게 안 돌아갔다.** `INTEGRATE_SLOTS`에 그 자리가
없어서, 리드는 자기 태스크가 버려진 줄 모른 채 같은 상태를 다시 보고 같은 답을
냈다. 피드백 없이 같은 입력을 주면 같은 출력이 나오는 것이 당연하다.

고친 것:

| | 전 | 후 |
|---|---|---|
| 잘린 증거 | `'없다'를 주장할 수 없다` | + `같은 질의는 같은 답이다 — 좁혀서 물어라` |
| 예산에서 빠진 내용 | `필요하면 다시 읽어라` | `같은 질의를 또 내지 마라. 더 좁혀서 물어라` |
| 거부된 태스크 | 리드가 모름 | `<버려진 태스크>` 자리로 돌려준다 |

통제 경계는 그대로다 — **무엇을 받을지는 여전히 코드가 정한다**(규율 6).
돌려주는 것은 결정권이 아니라 결과다.

덤으로 자물쇠 하나: `test_프롬프트가_모든_자리를_실제로_쓴다`가 **선언한 자리를
템플릿이 실제로 쓰는지** 본다. 자리를 만들어 놓고 안 쓰면 그 정보는 영영 리드에게
안 간다 — 이 리포가 config에서 이미 당한 실패다.

### 세 번째 측정: 반복이 사라졌다

| | 1차 | 2차 | 3차 |
|---|---|---|---|
| 계약 위반 | 1건 | **3건** (전부 반복) | **0건** |
| 끝난 이유 | max_rounds | `no_runnable` | **`decision`** (리드가 스스로 골랐다) |
| 가설 | refuted 1 / supported 1 | open 1 / supported 1 | refuted 2 |

모순을 지우고 거부를 돌려주자 반복이 0이 됐다. 리드가 처음으로 스스로
`conclude`를 골랐다.

### 그런데 잘린 것이 5건 중 4건이었다 — 개별 상한이 총 예산을 놀리고 있었다

감으로 숫자를 올리기 전에 예산이 실제로 어떻게 쓰이는지 쟀다:

| 증거 | 개별 상한 × 건수 | 총 예산 | |
|---|---|---|---|
| 3건 | 3,600 | 12,000 | 8,400자가 논다 |
| 5건 | 6,000 | 12,000 | 6,000자가 논다 |
| 9건 | 10,800 | 12,000 | 1,200자가 논다 |

**어느 건수에서도 총 예산이 병목이 된 적이 없다.** 개별 상한(1200) 혼자
자르고 있었다. 그래서 총 예산의 1/5인 2400으로 올렸다 — **최근 5건은 온전히
보이고**, 그 이상부터 총 예산이 정한다. 숫자가 아니라 관계를 테스트가 지킨다.

같이 고친 것: 예시의 `limit`을 5→3, 10→5로 줄였다. **읽을 수 없는 5건보다
읽을 수 있는 3건이 낫다** — 예산은 증거 하나당 고정이라 건수를 늘리면 건당
글자가 그만큼 줄고, `limit=5`의 문서 다섯 건이 한 건도 온전히 안 들어갔다
(10b의 258자 제조 문서와 같은 일이다).

### 네 번째 측정: **예시가 중복을 만들고 있었다**

예산을 올리자 잘린 것은 4→3으로 줄었는데 계약 위반이 0→2로 돌아왔다.
둘 다 반복이었고, 반복된 것이 **예시에 적힌 모양 그대로**였다:

```
t-8  code.grep patterns=['GUMI_ALARM_EVENT_MAIN']   ← 예시: patterns: ["위 증거에서 본 이름"]
t-9  mongo.find collection='alarm' filter={} limit=3 ← 예시: filter: {}, limit: 3
```

찍어 보니 **integrate 예시가 라운드마다 완전히 똑같았다.** 모델은 예시를
복사하고 같은 증거에서 같은 이름을 채우므로, 같은 질의가 나오는 것이 당연하다.
**중복을 우리가 만들고 있었다** — 예시가 곧 명세라는 성질(10b)이 또 한 번
반대로 작동한 것이다.

두 가지를 고쳤다:

1. **예시가 이미 한 읽기를 뺀다.** `used`(이 케이스에서 낸 action들)를 받아서
   안 해 본 것부터 보여 준다. 전부 써 봤으면 그래도 보여 준다 — 빈 예시는
   형식 자체를 못 보여 주므로 더 나쁘다.
2. **좁히는 모양을 예시가 보여 준다.** `filter: {}`가 리드가 가진 유일한
   `mongo.find` 본보기였다. 그래서 "좁혀서 물어라"는 말을 읽고도 **좁히는 모양을
   몰라서** 같은 질의를 그대로 다시 냈다. 이제 예시의 `filter`가 비어 있지 않다.

산문으로 시키는 것과 예시로 보여 주는 것은 이 모델에게 전혀 다르다 — 이 단계에서
같은 교훈을 세 번 확인했다(발견의 첫 수, 거부 피드백, 좁히기).

고친 뒤 라운드별 예시:

```
라운드 2  code.grep …           mongo.find {… "filter": {"위 증거에서 본 필드 이름": …}}
라운드 3  kafka.tail …          redis.get …
라운드 4  redis.get …
```

### 다섯 번째 측정: 반복은 0, 이번엔 **인용 형식**이었다

예시 수정으로 `이미 한 읽기를 또 냈다`가 사라졌다. 남은 위반 하나는 성격이 달랐다:

```
h-1: 없는 증거를 인용했다 — t-5, t-6, t-4 (판정을 supported→open으로 되돌렸다)
```

`t-5`는 **태스크 id**다. 증거 id는 `t-5.e1`이다. **환각이 아니라 형식을 몰랐던
것이고, 그건 우리가 안 보여 준 탓이다** — 예시의 그 자리가
`["위 <모은 증거>에 실제로 있는 id"]`라는 지시문뿐이었다. 모델은 id처럼 생긴
것을 넣었고, 눈앞의 `<지금까지의 태스크>`에서 가져왔다.

**값이 아니라 모양을 보여 준다**: `"… — \`t-3.e1\` 같은 모양"`. 진짜 id를 박으면
모델이 그대로 베끼는데, 그건 통과하지만 **엉뚱한 근거를 단 supported**가 된다 —
거부되는 것보다 나쁘다. 거부 메시지에도 맞는 모양을 실어서 `<버려진 태스크>`로
돌아가게 했다. "틀렸다"만 알려 주면 같은 형식으로 다시 틀린다.

**같은 교훈 네 번째다** — 발견의 첫 수, 거부 피드백, 좁히기, 그리고 인용 형식.

### 도구가 스스로를 망가뜨린 두 가지

이 라운드에서 `red_sweep`이 두 번 사고를 냈고, 둘 다 **원인이 안 보이는** 종류였다.

1. **끊기면 변형을 남긴다.** `finally`는 프로세스가 죽으면 안 돈다. 인터럽트 한 번에
   `checkout.py`가 망가진 채 남아 전체 테스트가 빨개졌다. 이제 건드린 파일을 전부
   기억하고 `SIGINT`/`SIGTERM`/종료에서 되돌린다.
2. **`__pycache__`를 오염시킨다.** 파이썬은 `.pyc`가 최신인지 소스의 **mtime과
   크기**로 판단한다. `1200` → `2400`은 **길이가 같고**, 같은 초 안에 되돌리면
   mtime도 그대로다. 그래서 `git status`로 트리가 깨끗한데 런타임 값은 1200이었고,
   테스트 둘이 이유 없이 빨간불이었다. 되돌린 뒤 그 소스의 `.pyc`를 지운다.

그리고 스윕에 케이스를 붙이던 문자열 치환이 **조용히 아무것도 안 한** 적이 있어
(패턴이 더는 안 맞았다) 다섯 개가 누락돼 있었다. 이제 스윕이 자기 케이스 수를
기대값과 대조한다.

### RED 스윕이 거짓 초록을 둘 더 잡았다

- `전부 썼을 때 예시가 빈다` — `rest.query` 하드코딩 폴백이 가리고 있었다. 그리고
  그 폴백 자체가 버그였다: **REST가 없는 사이트에도 `rest.query`가 나간다.**
  이제 마지막 수단도 `_free_rest_entry`로 **실재하는 항목**만 쓴다.
- `마지막 수단에 지시문을 박는다` — 그 자리가 도달 가능한 경우는 **REST만 있는
  사이트** 하나뿐이라, 테스트를 그쪽으로 다시 겨눴다.

### 왕복의 진짜 원인은 **측정값이 안 건너온 것**이었다

다섯 라운드 동안 매번 결함을 하나씩 찾아 고쳤고 전부 실재하는 결함이었지만,
수렴하지 않았다. 원인은 추론이 아니라 **데이터**였다 — 사내에서 건너온 것은 진단
요약뿐이었고, **리드가 무엇을 보고 무엇을 뱉었는지는 한 번도 안 건너왔다.**
그래서 매번 코드에서 역추적했다.

`case trace`가 그걸 붙여넣을 수 있는 크기로 줄인다. 만들자마자 **내 진단 하나를
뒤집었다**: 나는 "리드가 자기가 뭘 물었는지 볼 수 없다"고 적었는데, 증거 줄의
`source`가 곧 그 질의라 **보인다.** 안 보이는 것은 증거를 못 만든 태스크의 질의뿐이다.
그래서 요약이 그 둘을 가른다:

| 표시 | 뜻 |
|---|---|
| `**이미 한 질의 — 증거에 보이는데도 또 냈다**` | 모델 쪽 |
| `이미 …에서 한 질의(증거엔 안 보였다)` | 우리가 안 보여 준 것 |

그리고 같은 도구가 `redis.get` 발명의 경로를 그대로 보여 줬다:

```
예시가 보여준 것 : … redis.get{key:위 증거에서 본 키 이름}
리드가 낸 것 : t-7 redis.get{key:pipeline:alarm:stats}   ← 증거에 없는 이름
```

**증거에 키 이름이 하나도 없는데 `redis.get`을 보여 줬다.** 없는 것을 채우라고 하면
지어낸다 — 예시가 요구하는 이름이 증거에 있는지부터 봐야 한다.

### 첫 전체 트레이스 — 하네스는 더 이상 리드를 넘어뜨리지 않는다

`case trace`로 처음 다섯 라운드(r0~r4)가 통째로 건너왔다. 그동안 다섯 번 고친
것들이 실제로 어떻게 작동하는지가 처음으로 데이터로 보였다:

| | 보였다 |
|---|---|
| 계약 위반 | **0건.** 버려진 태스크도 매 라운드 0 |
| 발견 첫 수 | r0 `code.config{service:api}`·`mongo.list_collections`·`kafka.list_topics` — 예시 그대로 |
| 이름 찾기 | r1 `code.grep{GUMI_ALARM_EVENT}`·`mongo.find{collection:alarm}` — 증거에서 본 이름을 채웠다 |
| 좁히기 | **끝까지 `filter={}`**(t-5, t-7) |
| r4 | 프롬프트 13,616자 뒤에 **응답을 JSON으로 못 읽었다** |

두 가지가 남았고, 둘의 성격이 다르다.

**① 좁히는 본보기가 r1에만 보였다.** 예시 회전이 `mongo.find`를 **action 이름**으로
뺐다. r1엔 아직 채울 필드가 없어서 `filter={}`가 나왔고, r2부터는 문서를 읽어 필드를
아는데 그때는 `mongo.find`가 예시에서 사라진 뒤였다(예시는 `kafka.tail`·`redis.get`,
r3엔 `redis.get`뿐). 리드가 좁히지 않은 게 아니라 **좁히는 모양을 딱 한 번, 쓸 수 없을
때만 봤다.** 이건 우리 것이다.

고침: `_refinable` — **`filter`가 있는 읽기는 이미 썼어도 다시 보여 준다.** 같은
action이어도 좁힌 질의는 새 질의고, 그게 조사가 나아가는 방향이다. `code.grep`·
`kafka.tail`·`redis.get`은 아는 이름이 하나면 다시 내는 순간 중복이므로 전처럼 뺀다.

**② r4가 13.6K에서 깨졌다.** 프롬프트는 r2부터 13.3K→13.4K→13.6K로 **평평하다** —
증거 예산 12,000이 묶여 있어서다. 그러니 r4에서 갑자기 커진 것이 아니라, 같은
크기에서 넷 중 하나가 깨진 것이다. 표본 하나로 예산을 줄이면 **짐작으로 고치는 것**이
된다 — 그래서 예산은 건드리지 않고, 요약이 다음 실행에서 결정적이게 만들었다:

- 프롬프트를 **블록별로 센다**: `증거 + 태스크 + 가설 + 버려진 + 예시 + 나머지`.
  13K가 어디로 가는지 모르면 어느 예산을 줄일지도 모른다
- 못 읽은 응답의 **크기와 앞머리**를 찍는다: 빈 답인지, 산문인지, 잘린 JSON인지가
  거기서 갈린다(내용 전체는 안 찍는다 — 증거를 되뇌었을 수 있다)
- 가설 줄에 **인용 수와 `decision`**을 찍는다: "전부 refuted인데 conclude"(아래)를
  다음엔 이 줄에서 바로 읽는다
- 같은 라운드가 두 번이면 **재시도**라고 적는다: 못 읽은 답을 다시 물은 것을 새
  라운드처럼 찍으면 "라운드가 하나 더 돌았다"로 읽힌다

다음 실행에서 볼 것: r2 이후 `mongo.find`가 **비어 있지 않은 `filter`**로 나오는가,
그리고 13K 중 증거가 얼마인가.

**그리고 스윕이 이 고침의 회귀를 바로 잡았다.** `mongo.find`가 늘 남게 되자 "전부 써
봤으면 다시 보여 준다"는 폴백에 도달할 길이 사라졌다 — 폴백을 지워도 그 테스트가
초록이었다(`지웠는데 통과`). 실제 회귀이기도 했다: **mongo가 없는 사이트**에서는 전부 쓴
뒤 예시가 빈다. 폴백 판단을 "`fresh`가 비었나"에서 "**이 사이트에서 쓸 수 있는 것**이
남았나"로 옮기고, 테스트를 mongo도 없는 사이트로 다시 겨눴다. 고친 줄이 스윕의
자리를 옮기면 스윕 케이스도 같이 고쳐야 한다 — 이번에 셋이 `자리 못 찾음`이었다.

### 두 번째 전체 트레이스 — 좁히긴 하는데, 늘 한 라운드 늦다

| | 보였다 |
|---|---|
| 계약 위반 | 하네스가 잘못 거부한 것 0. 지어낸 이름 0(`pipeline:alarm:status`는 증거에 있었다) |
| 좁히기 본보기 | r2·r3·r4 내내 예시에 있었다(`_refinable`이 맞았다) |
| 리드의 `mongo.find` | r1 `{}` → r2 **`{}` 또**(거부) → r3 `{'o…}` → r4 `{"sent_yn": false}` |
| r4 | 16,595자, 멀쩡히 읽혔다 — **13.6K 크기 가설은 죽었다** |
| 잘림 | 8건 중 4건, 증거 11,449자로 총 예산에 닿았다 |

**리드가 좁힌 계기는 하나뿐이었다.** r2와 r3 사이에 달라진 것은 `<버려진 태스크>`의
한 줄(`t-6: 이미 한 읽기를 또 냈다 — 받지 않는다 (mongo.find … filter={} …)`)이고, 그
직후 좁혔다. 예시의 자리표시자도, "좁혀서 물어라"는 산문도 아니었다 — **자기 질의가
그 값 그대로 버려졌다는 사실**이다. 완결된 구체값(증거 줄의 `source`)이 자리표시자를
이긴다는 것의 다섯 번째 확인이기도 하다: r2의 t-6은 예시가 아니라 자기 t-5를 베꼈다.

그런데 그 신호가 늘 **한 라운드 뒤**에 갔다. 이 실행에서 두 번(r2→r3, r4→다음), 매번
실행 한 사이클과 라운드 하나를 태웠다.

**고침: 거부가 있으면 그 자리에서 한 번 되묻는다.** integrate 노드가 `_accept_tasks`·
`_accept_hypotheses`의 **거부**(중복 id·중복 질의·없는 증거 인용)를 받으면, 같은
프롬프트의 `<버려진 태스크>`에 `방금 낸 답의 t-6: …` 줄을 얹어 리드에게 한 번 더 묻는다.
되물은 답이 첫 답을 통째로 대신한다(JSON 재시도와 같은 규칙). 통제 경계는 그대로다 —
무엇을 받을지, 되물을지, 몇 번인지는 코드가 정한다.

- "찾지 않고 이름을 댔다"로는 **안 되묻는다.** 그건 받았다는 기록이지 거부가 아니다 —
  되물으면 "받았는데 왜 다시 묻나"가 되고 증거가 없는 라운드마다 되묻게 된다.
  그래서 `_accept_tasks`가 거부와 기록을 따로 돌려주게 갈랐다.
- 마지막 라운드에는 안 한다(어차피 상한으로 끝난다). 되묻기 자체가 실패하면 첫 답으로
  간다 — 한 번 더 물어본 것이 라운드를 죽이면 안 된다.
- 대본 경로(`dryrun`)는 끈다(`redo_on_rejection=False`). 되물으면 대본의 다음 라운드를
  당겨 먹는다. `build_deps`를 직접 보는 테스트가 지킨다.
- 첫 답의 거부는 State에 `(그 자리에서 다시 물었다)`를 붙여 남는다 — 진단의 "리드 계약
  위반 N건"은 그대로 세고, 되물음이 몇 번이었는지도 셀 수 있다.

**그리고 요약이 r3를 잘못 보여 줬다.** r3가 `decision=conclude`·태스크 0으로 찍혔는데
r4가 돌았다. `route_after_integrate`는 `conclude`면 그래프를 끝내므로 r4가 있다는 것은
**채택된 r3 답이 `continue`였다**는 뜻이다 — 즉 찍힌 답은 `IntegrateReply`가 거부한
첫 시도였고 재시도가 `continue`를 냈다. 요약은 제 눈으로 JSON을 다시 읽을 뿐 트레이스
파일 머리의 우리 판정(`결과: 못 읽었다 — 사유`)을 안 봤고, 그래서 거부된 답이 결론처럼
보였다. 이제 시도마다 `결과:`를 찍고, 같은 라운드의 두 번째 파일이 JSON 재시도인지
거부 뒤 되물음인지도 가른다(`<버려진 태스크>`의 머리말로 안다).

다음 실행에서 볼 것: `(거부 뒤 다시 물음)` 블록에서 리드가 **바로 그 자리에서** 좁히는가,
그리고 r3 첫 시도의 `결과:` 사유.

### 로컬 대역 측정 — 사내 없이 같은 배선을 세 번 돌렸다

9월 20일에 "사내 LLM은 claude 모델 haiku, effort 낮음 수준으로 생각하고 해야 한다"는
말을 들었고, 나는 그걸 **설계 전제로만** 썼다. 예시를 스펙처럼 만들고 산문을 믿지 않는
식으로. 실제로 haiku급 모델을 리드 자리에 세워 돌려 본 적은 없었다. 그래서 측정이 전부
사내로 갔고, 결과를 사람이 손으로 옮겨야 했다 — 11a 후반의 왕복 전부가 그 비용이었다.

**측정을 여기로 옮겼다.** `LlmConfig`에 `adapter: "file"`(파일 턴 — 프롬프트를 파일로 내고
답 파일을 기다린다)을 더하고, `tools/local_case.py`가 케이스 하나를 통째로 만든다: config
사본(LLM만 파일 턴), knowledge 사본, 대상 config 층이 든 가짜 git 레포 둘, stub seed, 케이스
레코드. 이름은 전부 지어낸 것이다(decisions ⑮). 심은 고장은 하나 — **sink 컨슈머 그룹이
멈춰 lag 1,830, `alarm_events`에 4시간째 새 문서 없음, 토픽엔 새 메시지가 계속 옴.** 리드
자리에는 haiku 에이전트를 세웠고, 호출마다 새 에이전트다(사내 모델도 호출 간 기억이 없다).

| 실행 | 계약 위반 | 되물음 | 결론(4라운드) |
|---|---|---|---|
| 1차 | 2 (대기 중 id 재발행 거부) | 1 | **sink** 컨슈머 정지 — 정답. `code.services`로 역할을 보고 sink 그룹 오프셋까지 갔다 |
| 2차 | 2 | 1 | processor — **오답.** 첫 답의 결정적 읽기(sink 오프셋)가 되물음에서 사라졌다 |
| 3차 | 1 (기록만) | 0 | "processor 또는 sink" — 절반. sink 그룹 오프셋을 끝내 안 봤다 |

세 번이 드러낸 **하네스** 결함, 전부 고쳤다:

- **대기 중인 태스크가 굶는다.** 새 라운드의 태스크가 늘 앞 순위(10·20·30)라 frame에서
  40·50으로 낸 t-4·t-5는 폭 3에서 영원히 안 돌았다. 리드가 그걸 눈치채고 같은 id로 다시
  냈더니 "이미 있는 id"로 거부됐고(1차), 새 id로 냈더니 "이미 한 읽기"로 거부됐다(2차).
  `taken`이 막을 것은 **끝난** id의 부활이다. 이제 아직 안 돈 태스크는 같은 id로도, 같은
  질의의 새 id로도 **갱신**이다 — 우선순위와 목표만 바뀐다.
- **되물음이 첫 답의 받은 것까지 버렸다.** JSON 재시도처럼 통째로 바꿨는데, 2차에서 첫
  답의 `kafka.group_offsets gumi-mx-sink`가 되물은 답에 없어서 사라졌고 리드는 끝까지
  processor를 팠다. 되물음은 거부된 것을 고쳐 받으려는 것이다 — 첫 답에서 받은 것은
  남기고, 같은 id는 되물은 쪽이, 같은 질의는 하나만, 가설은 되물은 쪽(최신 판단)이다.
- 요약이 되물음 앞의 버려진 답의 질의를 "이미 한 질의"로 찍었고, 대기 태스크의 갱신도
  그렇게 찍었다. 둘 다 정상 동작이 반복으로 읽히는 표시였다.
- 로컬 측정판의 REST stub이 seed 없는 항목에 404를 냈고, 리드는 그걸 "API 장애"로 읽었다.
  등재된 항목 전부에 답을 둔다.

**haiku급으로도 잘 도는가 — 절반만 예다.** 엔진은 깨끗하게 끝까지 돈다: 3차는 위반 0·
되물음 0·중복 0, 좁히기(`occ_date $gte`)와 `conclude`가 스스로 나온다. 그러나 정확한
부품을 짚은 것은 셋 중 하나다. 서비스 역할을 목록에 붙였어도(`processor — 원천 이벤트를
받아 가공한다 / sink — 가공된 결과를 저장한다`) 리드는 "processor가 저장을 못 한다"고 썼다 —
역할 문장을 읽고도 저장을 processor에 붙였다. 이건 하네스가 아니라 모델의 추론이고,
**이 케이스로 튜닝하지 않는다**(⑮). 12a의 verify가 "supported"에 **그 부품을 실제로 확인한
증거**를 요구해야 하는 이유가 여기서 데이터로 나왔다.

한 가지 주의: haiku 에이전트는 frame에서 가설 셋·태스크 다섯을 냈고 `code.services`를
스스로 불렀다. 사내 모델은 예시를 베낀다. **로컬 결과는 사내의 상한이지 예측이 아니다.**

| | 사내 모델 | haiku 대역(3회) |
|---|---|---|
| frame | 예시 그대로 3개, 가설 2 | 가설 3, 태스크 5~6, `code.services`를 스스로 부름 |
| 라운드당 새 읽기 | 2 (예시의 두 action 그대로) | 3~4, 예시 밖 action(`group_offsets`, `count`, `scan`) |
| 좁히기 | r1부터 `filter` 있음 — 단 `{"type": {"$exists": true}}`처럼 **모양만** 좁힘, r2엔 `{}`로 되돌아감 | 날짜 조건(`occ_date $gte`)으로 실제로 좁힘 |
| 가설 | h-1 하나 supported, h-2는 r2 이후 사라짐 | 셋을 끝까지 갱신, refuted를 냄 |
| 이름 | r3 `alarm_counts`, r4 `code.read path=redis_key` — 지어냄 | 증거에서 가져옴(예외 1회) |
| 다른 서비스 | api만 봄. processor·sink를 한 번도 안 봄 | 역할을 보고 sink까지 감(3회 중 1회 정답) |
| 결론 | 4라운드 상한, `conclude` 안 냄 | 4라운드에 `conclude` |

**사내 모델의 한계로 보이는 것:** 예시의 action을 그대로 베끼고, 가설을 하나만 유지하고,
`$exists`로 좁히는 시늉을 하고, 3라운드부터 이름을 지어낸다. 역할을 목록에 붙여 줬어도 다른
서비스를 보지 않았다. 이건 프롬프트 산문으로 고칠 수 있는 종류가 아니다 — 예시에 없는 것은
안 낸다는 성질 그대로다.

**버그로 확인된 것 둘, 고쳤다:**

- **되물음이 좁힌 읽기를 또 잃었다** — 이번엔 id 충돌로. 첫 답에서 받은 것을 되물음 State에
  안 실어서 예시의 다음 번호가 그대로(`t-8`)였고, 리드는 `t-8`로 **다른** 읽기(`redis.scan`)를
  냈고, 합칠 때 같은 id라 첫 답의 `mongo.find {"status": …}`를 덮었다. r4 증거 목록에 그
  질의가 없는 것으로 확인된다. 이제 첫 답의 받은 것을 대기 태스크로 실어서 되묻는다 — 번호가
  앞으로 가고, 리드는 그것들이 남아 있음을 본다.
- **게이트웨이 403을 모델의 잘못처럼 다뤘다.** 되물음이 앞 호출 직후에 나가자 403이 왔고,
  재시도는 "앞의 답을 읽을 수 없었다: OpenAIPermissionDeniedError…"를 붙여 다시 물었다 —
  모델에게 오류 문자열을 고치라고 시킨 셈이다. 전송 오류는 같은 프롬프트로, 2초 쉬고 다시
  부른다. (403 자체는 연달아 두 번 부른 것에 게이트웨이가 반응한 것으로 보인다.)

되물음 기계 하나에서 나온 결함이 넷이다(통째 교체, 버려진 답의 질의 오표시, id 충돌, 전송
오류 수리). 어제 급하게 넣은 대가다. 이제 되물음 State는 "첫 답을 받은 뒤의 State"와 같다 —
그게 처음부터 맞는 정의였다.

**손으로 옮기는 비용:** `case trace --brief`가 "이미 물은 것"·"예시가 보여준 것" 줄을 뺀다.
둘은 라운드마다 제일 길고, 둘 다 코드에서 다시 만들 수 있다. 그리고 전체 pytest는 **여기서
돈다** — 사내에서는 `case investigate`·`case trace --brief` 둘이면 된다.

### 12a로 넘기는 것: 가설이 전부 기각됐는데 `conclude`다

3차에서 리드가 가설 둘을 **둘 다 `refuted`**로 적고 `conclude`를 골랐다.
남은 가설이 없다 = 원인을 못 찾았다는 뜻인데 조사를 끝냈다. 게다가 증거
5건 중 4건이 잘린 상태였다 — ⑪대로면 **잘린 표본으로 "아니다"를 단정할 수 없다.**

conclude 게이트와 "판정이 인용할 수 있는 우주"는 12a(conclude/verify)의 것이다.
여기서 막으면 그 설계를 선점하게 되므로 **기록만 남기고 넘긴다.**

## 이 단계가 드러낸 구조 문제 다섯

### ① 테스트가 **운영이 채우는 칸**을 붙잡고 있었다

`code status`의 CLI 테스트가 리포의 `config/`·`knowledge/`를 통째로 베껴 쓰고,
서비스 목록을 `repo == "dt-core"`로 걸렀다. 사내에서 **진짜 레포 이름을 적는 순간
테스트가 깨졌다.**

`dt-core`는 자리표시자다 — 운영이 바꾸라고 둔 값이다. **운영이 자기 값을 적었다고
우리 테스트가 빨간불이면 사람은 그 테스트를 안 믿는다.**

테스트가 자기 트리를 세우도록 고쳤다. 여기서 보려는 것은 `code status`의 **배선**이지
리포 설정의 내용이 아니다 — 설정이 온전한지는 `boot`과 env 참조 테스트가 본다.

되살아나지 않게 `tests/test_portability.py`가 **`knowledge/`를 `copytree`하는 것**을
막는다. `config/`는 베껴도 된다 — 내용을 안 읽으면 그만이고, CLI 테스트 넷이 이미
그렇게 쓴다. 처음엔 문자열로 훑게 썼다가 **검사기의 설명문 자체가 걸려서** AST로 바꿨다.

확인은 실제 편집으로 했다: 레포 이름 둘, 서비스 열 개, config 층 경로를 사내에서
할 법한 값으로 전부 바꾸고 전체 테스트를 돌렸다 — 1034개 그대로 통과했다.

### ② CLI 테스트가 실패해도 **이유를 안 알려 줬다**

`assert main() == 0`은 실패할 때 `assert 1 == 0`만 말한다. 진짜 이유는 stderr에
있는데 테스트가 그걸 버렸다. 사내에서 여섯 개가 한꺼번에 이렇게 깨졌고, 출력만으로는
**원인을 한 톨도 알 수 없었다.**

이제 전부 `assert code == 0, err` 꼴이다. `assert`의 메시지는 **실패할 때만**
평가되므로 통과 경로의 `capsys`를 건드리지 않는다.

확인은 일부러 깨뜨려서 했다 — config에 없는 env 참조를 넣으니:

```
AssertionError: ❌ mx/gumi가 참조하는 env가 비어 있다 — 없는_환경변수. .env에 값을 넣어라
```

**진단 코드가 진단을 못 하면 없는 것보다 나쁘다.** 있다고 믿고 안 찾게 되기 때문이다.
같은 이유로 `subprocess` 출력을 `None`일 수 있는 것처럼 다룬다 — `capture_output`이
빠진 채로 돌면 `.strip()`이 `AttributeError`로 죽는데, **하필 죽는 자리가 "왜
실패했나"를 말해 줘야 할 함수다**(handover의 Windows 함정, 이 리포가 이미 한 번 물렸다).

### ③ 테스트가 **사내에 없는 파일**을 붙잡고 있었다

`set_real_config_env`가 `.env.example`에서 키 목록을 읽었다. "config가 참조를 늘리면
자동으로 따라온다"는 이유였는데, **사내 트리에는 그 파일이 없다** — 운영은 `.env`만
둔다. 그래서 CLI 테스트가 무더기로 깨졌고, 사람이 **매번 테스트 코드를 고쳐 쓰고
있었다.** 고쳐 쓴 테스트는 다음 이관에서 다시 덮이고, 그 반복이 테스트를 죽인다.

이제 **`config/`에서 직접 뽑는다.** 참조의 진실 소스가 거기이므로 어떤 트리에서도
같게 돈다. `.env.example` 대조는 **템플릿 리포의 문서 검사**로 남기고, 파일이 없으면
건너뛴다. README가 그 파일을 링크하는 것도 같은 취급이다(`TEMPLATE_ONLY`).

확인은 `.env.example`을 **실제로 지우고** 전체를 돌려서 했다 — 1039 통과 1 스킵.

### ④ 재현이 안 되면 **실패가 스스로 말하게** 만든다

사내에서 `test_url에_토큰이_섞이면_거부한다`가 `DID NOT RAISE`로 깨졌는데 개발
기계에서는 재현이 안 됐다. "안 걸렸다"만으로는 **트리가 낡은 것인지 환경이 다른
것인지** 구분할 수 없어서 한 번 더 물어봐야 했다 — 그 왕복이 낭비고, 사람이 매번
같은 값을 타이핑해 옮겨야 한다.

이제 실패가 **그 트리에서 실제로 돌고 있는 validator 본문**을 찍는다:

```
Failed: 토큰이 섞인 url이 통과했다 — 'https://ghp_tok@git.example.com/…'
  파일: …/src/config/schema_site.py
  지금 돌고 있는 validator:
    def _clean(cls, v: str) -> str:
        …
```

**진단기를 처음엔 틀리게 썼다.** "오류 메시지 문자열이 소스에 있나"로 봤는데, 검사를
꺼도 그 문자열은 `raise` 본문에 남아 있어서 **항상 "있다"가 나왔다.** 검사기가 검사를
못 하는 것이 여기서 고치려던 바로 그 문제다 — 일부러 깨뜨려 보고서야 드러났다.

같은 이유로 `outcome == "failed" and why`처럼 묶어 단정하지 않는다. 어느 쪽이 틀렸는지
안 보인다.

### ⑤ 같은 선언이 네 곳에 복사돼 있었다

`.env.example`에 `GIT_TOKEN`을 더했더니 **관계없는 CLI 테스트 8개가 깨졌다.** 원인은
같은 env 키 목록이 **네 파일에 복사**돼 있었던 것이다. 그리고 실패 모양이 "설정이
치환 안 됐다"가 아니라 "CLI가 1을 돌려준다"여서 원인이 안 보였다.

`tests/support.set_real_config_env`로 한 곳에 모았고, **`.env.example`의 키에서
만든다** — config가 참조를 늘리면 자동으로 따라온다.

## 검토 포인트

1. **`knowledge/`가 `config/` 옆에 있어야 한다.** `--knowledge-root` 기본값을 고정
   경로로 뒀다가 테스트가 tmp 트리를 검증하면서 **리포의 진짜 knowledge를 읽었다.**
   지금은 `--config-root` 옆을 본다 — 사내 이관 때 둘이 같이 가야 한다
2. **`config_paths`를 사람이 유지해야 한다.** 대상의 config 층이 바뀌면 여기도
   바뀐다. `code status`가 배포 커밋에서 실재를 확인하지만, **경로가 맞는데 내용이
   다른 것**은 못 잡는다. 그리고 지금은 GBM 하나에 목록 하나다 — 레포마다 층이
   다르면 레포별로 쪼개야 한다
3. **`code sync`를 기동에 어떻게 묶나.** 지금은 사람이 친다. 14단계 데몬이
   생기면 거기로 옮기고, 그때 "sync 실패 시 기동을 막을지"를 명시적으로 정한다
4. **토큰 만료를 무엇이 알려 주나.** 지금은 아무것도 안 알려 준다 —
   `code sync`를 부를 때만 드러난다. 14단계의 데몬이 주기적으로 `sync`를 돌리면
   거기서 잡히고, 안 돌리면 사람이 만료일을 기억해야 한다
5. **`deployed_at`을 누가 채우나.** 배포 파이프라인이 쓰면 제일 좋고, 사람이
   쓰면 썩는다. 14단계에서 데몬이 붙을 자리이기도 하다
6. **11c(graphify)는 보류다.** 사람이 직접 받아 보니 얻을 것이 딱히 없었다.
   `git grep`으로 흡수하거나 로드맵에서 뺀다 — README·step-00의 표를 같이 고쳐야 한다
