# 11a단계 — 대상 코드 확보와 지식 층 (1차)

> **목적**: 리드가 "토픽 179개 중 뭐가 맞나"에 **이름 유사도가 아니라 코드로**
>답할 수 있게 하는 토대. 1차는 지식 층·포트·진단까지다 — 리드가 실제로 부르는 것은
> 2차(등재표에 `code.*`)다.

```bash
python -m src code status     # 읽을 수 있는 상태인가 (네트워크 없음)
python -m src code plan       # 사람이 직접 칠 git 명령 (네트워크 없음)
python -m src code sync       # clone/fetch — 사내에서만
```

```
  mx — 레포 2개 · 서비스 3개

  ✅ dt-core  ../target-code/dt-core
       origin https://git.example.com/team/dt-core
       ✅ processor @ main  (가정)
       ✅ sink @ main  (가정)
```

**`(가정)`을 보라.** 배포 선언이 없어서 `main` 최신이라고 **가정**했다는 뜻이다.
확인된 것과 가정한 것을 같은 모양으로 찍으면, 뒤처진 사이트에서 떠 있지도 않은
코드를 읽고 확신에 찬 오답을 낸다.

## 세 층이 각각 다른 질문에 답한다

| 층 | 답하는 질문 | 어디 | 누가 언제 고치나 |
|---|---|---|---|
| 토폴로지 | 어느 서비스가 어느 레포의 무엇인가 | `knowledge/topology/<gbm>.json` | 구조가 바뀔 때만 |
| config | 그 레포를 어디서 받아 어디에 두는가 | `config/gbm\|fct/*.json`의 `code.repos` | 배치가 바뀔 때 |
| deployment | 이 GBM에 지금 어느 커밋이 떠 있는가 | `knowledge/deployment/<gbm>.json` | 배포할 때마다 |

## 사내 사실이 설계를 두 번 고쳤다

`decisions.md`에 적혀 있던 것이 **둘 다 틀렸다.** 고쳐 적었다.

### ① 단위는 사이트가 아니라 GBM이다

②는 "사이트마다 배포 커밋이 다르다"를 submodule 기각의 결정적 근거로 적었다.
실제로는 **코드가 GBM 단위로 같고** 배포 커밋은 기본적으로 `main` 최신이다.

- deployment가 사이트 28개 → **GBM 4개**가 됐다. 손으로 유지할 양이 1/7이다
- ⑧ "사이트 간 배포 차이는 1급 증거"가 **"GBM 간"**이 됐다. 같은 GBM 안에서는
  비교할 것이 없고, "MX는 되는데 NW는 안 된다"가 살아남은 신호다
- **submodule 기각은 그대로다.** 근거가 바뀌었을 뿐이다 — GBM이 4개라 포인터
  하나로는 여전히 부족하고, 무엇보다 **과거 커밋을 읽는 것**이 조사의 핵심인데
  서브모듈 체크아웃에는 그 객체가 없다

### ② 서비스는 `(레포, 경로)`가 아니라 `(레포, 선택자)`다

③은 `path`로 `git grep`을 좁힌다는 전제였다. 실제로는 한 레포에 서비스가 여럿인
것이 **디렉터리가 나뉜 게 아니라 코드가 하나이고 `.env`가 역할을 고르는** 것이다.
그러면 좁힐 경로가 없다.

`selects`가 "이 env 값이면 이 서비스"를 적고, 디렉터리가 실제로 나뉜 레포만
`path`를 쓴다.

### 그리고 — 이름이 코드에 없다

컬렉션·토픽 이름이 소스에 리터럴로 박혀 있지 않고 **대상의 config 파일**에 있다.
그것도 층 병합 형식이다(우리 `config/`와 같은 구조). 다행히 그 파일들이 **레포 안에
버전 관리돼 있어서** `git show <배포커밋>:config/...`로 닿는다.

그래서 조사의 실제 경로는 "소스를 grep한다"가 아니라 **"config 파일에서 이름을 찾고
어느 층에서 왔는지 본다"**이다. `Topology.config_paths`가 그 층들을 가리키고, **`{gbm}`·`{fct}`를 쓸 수 있다** —
대상 config가 법인별로도 갈리기 때문이다(`config/factories/{fct}/{gbm}.json`).
문법은 우리 `SITE_LAYERS`와 같게 맞췄다.

`KafkaConsumerConfig`에서 템플릿을 기각한 것과는 **다른 경우다.** 거기서 문제는
오타 난 템플릿이 **존재하지 않는 그룹을 조용히 감시**하는 것이었다 — lag 0이 정상과
구별되지 않는다. 여기는 오타가 "그 커밋에 그 파일이 없다"로 **시끄럽게** 드러나고,
게다가 아는 자리 이름(`gbm`·`fct`)만 허용해서 오타 자체가 기동에서 막힌다.

**우리가 그 층을 합쳐서 답을 주지는 않는다.** 대상의 병합 규칙이 우리와 같다는
보장이 없고, 추측으로 합친 값은 틀려도 그럴듯해 보인다.

## 자물쇠 넷 (`code status`가 보는 것)

1. **경로가 있나**
2. **`.git`이 있나** — 작업 트리만 복사되면 `git show <커밋>:경로`가 통째로 안 된다.
   우리 설계의 전제가 무너지는 자리다
3. **`origin`이 config와 같나** — 누가 포크를 그 경로에 클론하면 우리는 그럴듯한
   코드를 읽고 그럴듯한 판정을 낸다. **전부 틀린 채로.** "코드를 못 읽었다"보다
   훨씬 나쁘다: 실패가 조용하고 판정은 확신에 차 있다
4. **배포가 가리키는 커밋이 로컬에 실재하나**
5. **`config_paths`가 그 커밋에 실재하나** — 이름이 대상의 config 파일에 살기
   때문에, 경로 앞머리가 틀리면 리드는 아무것도 못 찾는다. 증상은 "조사가 빈손"이라
   원인이 안 보인다. 사람이 손으로 적는 칸이라 오타가 정상적으로 일어난다.

   **층은 선택이다** — 우리 `SITE_LAYERS`와 같다. `fct/{fct}/common.json`이 없는
   법인이 정상이듯 대상도 그렇다. 그래서 없는 층은 적어만 주고, **하나도 없을 때만**
   빨간불이다. 없는 층마다 빨간불을 켜면 사람이 검사를 끈다

3번은 `.git` 꼬리와 끝 슬래시만 봐준다. **호스트가 다르면 같게 안 본다** — 관대함이
거기까지 오면 자물쇠가 아니다. 반대로 `.git` 유무로 실패하면 사람이 자물쇠를 끄고
싶어진다. **끌 수 있는 자물쇠는 잠기지 않는다.**

## 토큰은 디스크에 안 남는다

`https://<토큰>@호스트/…`로 클론하면 git이 그 URL을 **`.git/config`에 평문으로
저장한다.** 토큰이 디스크에 남고, 그 파일은 백업·이미지·로그 어디로든 따라간다.

- config의 `url`은 **토큰 없는 깨끗한 주소**다. 섞여 있으면 스키마가 거부한다
- 인증은 `git -c http.extraHeader=...`로 **명령마다** 넘긴다
- `code plan`이 출력하는 명령에도 토큰을 안 찍는다 — 사람이 복사해 붙이면 셸
  히스토리에 남는다
- git이 뱉은 오류에서도 지운다(`_scrub`)

덤으로 `origin` 대조가 비밀값 비교가 되지 않는다.

### 토큰에 줄 권한

fine-grained token에 필요한 것은 **둘뿐이다.**

| | |
|---|---|
| Repository → **Contents** | **Read-only** — `git clone`·`fetch`를 허용하는 것이 이것이다 |
| Repository → **Metadata** | **Read-only** — 다른 권한을 고르면 자동으로 켜진다. 끌 수 없다 |
| **Organization permissions** | **전부 없음.** org 소유 레포를 클론하는 데 관여하지 않는다 |

**Contents를 write로 주지 않는다.** 포트에 쓰기 메서드를 안 만든 것과 같은 이유다 —
권한도 같은 성질이어야 한다. 표현 불가능한 것은 사고도 못 낸다.

발급할 때 틀리기 쉬운 것: Resource owner를 **조직**으로 골라야 org 레포가 보인다 ·
Repository access는 `Only select repositories`(등재제와 같은 성질) · 많은 org가
**관리자 승인**을 요구해서 승인 전까지 403이다 · SAML SSO면 토큰에 SSO 승인이 따로 필요하다.

**만료가 조용한 실패를 만든다.** 토큰이 만료되면 `code sync`는 403으로 실패하지만
**`code status`는 못 잡는다** — 네트워크를 안 타기 때문이다. 이미 클론된 레포는 계속
읽히므로 증상이 "코드가 점점 낡는다"가 되고, 그건 알아채기 어렵다. 만료일은 사람이
보는 곳에 적어 둬야 한다.

## 배포가 컨테이너이고 **재시작마다 사라진다면**

체크아웃이 디스크 상태라는 것이 여기서 값을 치른다. 확인된 배포 모양이 그렇다.

| | |
|---|---|
| 디스크 | 문제 아니다 — 레포가 GB 단위가 아니다 |
| **기동 때 `code sync` 한 번이 필수** | 안 돌리면 `code.*`가 전부 "`.git`이 없다"로 실패한다 |
| 클론 시간만큼 첫 조사가 늦다 | 그 사이 케이스가 열리면 **코드 증거 없이** 돈다 |
| 토큰이 기동 경로에 온다 | 만료되면 기동부터 막힌다 — 조용히 낡는 것보다 낫다 |

**"코드를 아직 안 받았다"와 "코드에 그런 게 없다"는 같은 모양이면 안 된다.**
어댑터가 `.git이 없다 — code status를 보라`로 구별해 말한다.

### 누가 `code sync`를 부르나 — **아직 아무도 안 부른다**

14단계의 데몬이 생기기 전까지는 컨테이너 entrypoint가 맞다:

```bash
python -m src code sync --gbm mx && python -m src ...
```

`&&`인 것이 뜻이 있다. **sync가 실패하면 기동을 막는 쪽을 권한다** — 코드를 못 읽는
조사는 "이름 유사도로 찍는" 상태로 되돌아가는데, 그건 조용히 나쁜 답을 내는 것이라
안 도는 것보다 나쁘다. 가용성을 택하겠다면 그건 **명시적 판단**이어야 한다.

### shallow clone은 **재 본 뒤에** 넣는다

재시작마다 클론하니 `--depth`로 얕게 받고 싶어진다. 레포가 GB 단위가 아니므로
**재 보기 전의 최적화다.** 클론 시간이 실제로 아프면 그때 넣는다.

넣을 때를 위해 구분 하나: `--depth`(shallow)는 `--filter=blob:none`(partial)과 **다른
물건이다.** shallow는 가진 커밋이 완전해서 **읽기가 네트워크를 안 탄다** — ②가 기각한
것은 후자다. 대신 창 밖의 오래된 배포 커밋이 로컬에 없어지는데, 그건 `code status`의
④가 미리 잡는다(`git fetch --deepen`으로 푼다).

## 기동은 **선언끼리의 어긋남**만 본다

디스크 상태(체크아웃이 실제로 있는가)는 `code status`의 일이다. 기동이 거기서
막히면 개발 환경에서 늘 빨간불이고, **그러면 사람이 기동 검증을 통째로 끈다.**

기동이 잡는 것: 토폴로지가 없는 레포를 가리키나 · 배포가 없는 서비스를 가리키나 ·
레포를 선언해 놓고 토폴로지가 없나. 전부 증상이 **"코드 증거가 조용히 안 나온다"**라
런타임에는 원인이 안 보인다.

## 검증

`pytest tests/` — 1039개. 11a 1차가 더한 것은 57개.

**진짜 git 레포를 만들어서** 검증한다(`git init` + 커밋 둘). 목을 세우면 목이
그렇게 답하도록 우리가 정해 놓고 "된다"고 확인하는 꼴이 된다 — `ScriptedAdapter`로
이미 당한 거짓 초록이다. git이 없는 환경에서는 skip하고 **사유가 찍힌다.**

### 거짓 초록 셋이 나왔다

| | 왜 |
|---|---|
| url의 토큰 검사 | **그 테스트를 안 썼다.** 스키마를 만들고 테스트를 빼먹었다 |
| 오류 메시지의 토큰 제거 | 통합 경로만 봤는데 **git이 우연히 토큰을 안 뱉었다** — 방어를 지워도 초록이었다. `_scrub`을 직접 부르게 고쳤다 |
| 기동의 어긋남 검사 | **내 RED 패치가 무동작이었다**(`[] or x`는 `x`다) |

그리고 픽스처 버그가 하나 더 있었다. `git init`을 레포가 아니라 **부모에서** 했고,
그래서 "없는 커밋" 테스트가 ".git이 없다"로 실패하면서 **통과로 읽혔다.** 이유까지
단정하도록 고쳤다.

## 이 단계가 드러낸 구조 문제 셋

### ① 테스트가 **운영이 채우는 칸**을 붙잡고 있었다

`code status`의 CLI 테스트가 리포의 `config/`·`knowledge/`를 통째로 베껴 쓰고,
서비스 목록을 `repo == "dt-core"`로 걸렀다. 사내에서 **진짜 레포 이름을 적는 순간
테스트가 깨졌다.**

`dt-core`는 자리표시자다 — 운영이 바꾸라고 둔 값이다. **운영이 자기 값을 적었다고
우리 테스트가 빨간불이면 사람은 그 테스트를 안 믿는다.**

테스트가 자기 트리를 세우도록 고쳤다. 여기서 보려는 것은 `code status`의 **배선**이지
리포 설정의 내용이 아니다 — 설정이 온전한지는 `boot`과 env 참조 테스트가 본다.

되살아나지 않게 `tests/test_portability.py`가 **`knowledge/`를 `copytree`하는 것**을
막는다. `config/`는 베껴도 된다 — 내용을 안 읽으면 그만이고, CLI 테스트 넷이 이미
그렇게 쓴다. 처음엔 문자열로 훑게 썼다가 **검사기의 설명문 자체가 걸려서** AST로 바꿨다.

확인은 실제 편집으로 했다: 레포 이름 둘, 서비스 열 개, config 층 경로를 사내에서
할 법한 값으로 전부 바꾸고 전체 테스트를 돌렸다 — 1034개 그대로 통과했다.

### ② CLI 테스트가 실패해도 **이유를 안 알려 줬다**

`assert main() == 0`은 실패할 때 `assert 1 == 0`만 말한다. 진짜 이유는 stderr에
있는데 테스트가 그걸 버렸다. 사내에서 여섯 개가 한꺼번에 이렇게 깨졌고, 출력만으로는
**원인을 한 톨도 알 수 없었다.**

이제 전부 `assert code == 0, err` 꼴이다. `assert`의 메시지는 **실패할 때만**
평가되므로 통과 경로의 `capsys`를 건드리지 않는다.

확인은 일부러 깨뜨려서 했다 — config에 없는 env 참조를 넣으니:

```
AssertionError: ❌ mx/gumi가 참조하는 env가 비어 있다 — 없는_환경변수. .env에 값을 넣어라
```

**진단 코드가 진단을 못 하면 없는 것보다 나쁘다.** 있다고 믿고 안 찾게 되기 때문이다.
같은 이유로 `subprocess` 출력을 `None`일 수 있는 것처럼 다룬다 — `capture_output`이
빠진 채로 돌면 `.strip()`이 `AttributeError`로 죽는데, **하필 죽는 자리가 "왜
실패했나"를 말해 줘야 할 함수다**(handover의 Windows 함정, 이 리포가 이미 한 번 물렸다).

### ③ 같은 선언이 네 곳에 복사돼 있었다

`.env.example`에 `GIT_TOKEN`을 더했더니 **관계없는 CLI 테스트 8개가 깨졌다.** 원인은
같은 env 키 목록이 **네 파일에 복사**돼 있었던 것이다. 그리고 실패 모양이 "설정이
치환 안 됐다"가 아니라 "CLI가 1을 돌려준다"여서 원인이 안 보였다.

`tests/support.set_real_config_env`로 한 곳에 모았고, **`.env.example`의 키에서
만든다** — config가 참조를 늘리면 자동으로 따라온다.

## 검토 포인트

1. **`knowledge/`가 `config/` 옆에 있어야 한다.** `--knowledge-root` 기본값을 고정
   경로로 뒀다가 테스트가 tmp 트리를 검증하면서 **리포의 진짜 knowledge를 읽었다.**
   지금은 `--config-root` 옆을 본다 — 사내 이관 때 둘이 같이 가야 한다
2. **`config_paths`를 사람이 유지해야 한다.** 대상의 config 층이 바뀌면 여기도
   바뀐다. `code status`가 배포 커밋에서 실재를 확인하지만, **경로가 맞는데 내용이
   다른 것**은 못 잡는다. 그리고 지금은 GBM 하나에 목록 하나다 — 레포마다 층이
   다르면 레포별로 쪼개야 한다
3. **`code sync`를 기동에 어떻게 묶나.** 지금은 사람이 친다. 14단계 데몬이
   생기면 거기로 옮기고, 그때 "sync 실패 시 기동을 막을지"를 명시적으로 정한다
4. **토큰 만료를 무엇이 알려 주나.** 지금은 아무것도 안 알려 준다 —
   `code sync`를 부를 때만 드러난다. 14단계의 데몬이 주기적으로 `sync`를 돌리면
   거기서 잡히고, 안 돌리면 사람이 만료일을 기억해야 한다
5. **`deployed_at`을 누가 채우나.** 배포 파이프라인이 쓰면 제일 좋고, 사람이
   쓰면 썩는다. 14단계에서 데몬이 붙을 자리이기도 하다
6. **11c(graphify)는 보류다.** 사람이 직접 받아 보니 얻을 것이 딱히 없었다.
   `git grep`으로 흡수하거나 로드맵에서 뺀다 — README·step-00의 표를 같이 고쳐야 한다
