# 9f단계 — `report run`: 집계에서 발송까지 한 명령

> **목적**: `render` → `mail send` 두 단계를 **한 명령**으로 묶어 평일 아침
> 스케줄에 걸 수 있게 한다.

```bash
python -m src report run                       # 집계 → 서술 → HTML → 파일 → 메일
python -m src report run --dry-run             # 나갈 요청만 보여주고 보내지 않는다
python -m src report run --no-mail             # 파일만 만든다
python -m src report run --today 2026-09-07 --stub-seeds s.json   # 대상에 안 붙고
```

## 왜 두 줄이 아니라 한 명령인가

스케줄러에 두 줄을 걸면

```
python -m src report render --out output/report.html
python -m src mail send --subject "일일 알람" --file output/report.html
```

**앞줄이 실패해도 뒷줄이 돈다.** 그러면 어제 만든 파일이 오늘 제목으로 다시 나가고,
받는 사람은 그것을 오늘 숫자로 읽는다. 이 시스템이 낼 수 있는 거짓말 중 알아채기가
제일 어려운 쪽이다 — 메일은 정시에 왔고 형식도 정상이다.

한 명령이면 그 틈이 없다. 집계가 실패하면 발송도 없다.

두 명령 자체는 남겨 둔다. `render`는 **사람이 눈으로 확인할 때**, `mail send`는
**연결을 확인할 때** 쓰는 도구다. 스케줄에 거는 것은 `run` 하나다.

## 조립은 `publish()` 한 곳뿐이다

```python
published = await publish(html, scenario=..., window=facts.window,
                          output_dir=..., mail=..., clock=..., dry_run=...)
```

발행 경로는 앞으로 늘어난다(재발송, 순찰에서의 자동 발행, 웹 UI의 "지금 보내기").
각 경로가 "파일 쓰고 메일 보내기"를 따로 베끼면 **언젠가 하나가 빠뜨린다** — 원본
템플릿에서 `case resume`이 실제로 그랬고, 한동안 아무도 몰랐다.

`tests/report/test_publish.py::test_메일_발송_호출은_정해진_곳에만_있다`가 그것을
구조로 지킨다: `src/` 안에서 `.send(`를 부를 수 있는 파일은 `publish.py`와
`__main__.py`(사람이 직접 부르는 `mail send`) 둘뿐이다. 산문 규율은 읽지 않으면
무력하다.

## 파일이 먼저, 메일이 나중

메일이 실패하는 이유는 많다 — 게이트웨이 점검, 키 만료, 방화벽 규칙 변경. 그때
**파일이라도 남아 있으면** 사람이 열어 보거나 직접 첨부해 보낼 수 있다. 순서를
뒤집으면 발송 실패가 곧 "아무것도 없음"이 된다.

"파일이 존재한다"만 검사하면 순서를 못 본다(메일이 성공하면 둘 다 있다). 그래서
테스트는 **`send`가 불린 그 순간** 파일이 있었는지를 본다.

반대 방향도 정해 뒀다: **파일을 못 써도 메일은 나간다.** 파일은 보관이고 메일이
목적이다 — 디스크가 가득 찼다고 발송을 멈추면 사람이 오늘 리포트를 아예 못 본다.
대신 종료 코드로 시끄럽게 말한다.

## 제목과 파일 이름의 기준일은 **어제**다

```
[운영리포트] 일일 알람 리포트 2026-09-11(금)
output/daily-alarm-2026-09-11.html
```

돌린 날을 쓰면 재실행·지연 실행에서 **같은 데이터가 다른 제목으로 두 번** 간다.
그리고 매일 같은 제목이면 받는 쪽 메일함에서 어제 것과 구분이 안 되고 검색도 안
된다. 파일 이름도 같은 이유다 — 매일 덮어쓰면 "어제 리포트를 다시 보고 싶다"가
불가능해진다. 같은 날 두 번 돌리면 **같은 파일을 덮어쓴다**(그건 의도다. 재실행이
파일을 늘리면 어느 것이 최신인지 모른다).

## 종료 코드가 스케줄러의 유일한 신호다

cron·스케줄러는 콘솔을 읽지 않는다. 0을 돌려주면 "잘 돌았다"로 보고, 리포트가 몇 주
안 나가도 아무도 모른다. 무엇을 1로 셀지는 **"사람이 오늘 봐야 하는가"**로 갈랐다:

| 상황 | 종료 코드 | 왜 |
|---|---|---|
| 파일을 못 썼다 | 1 | 보관이 끊겼다 |
| 메일이 실패했다 | 1 | 받는 사람이 오늘 리포트를 못 본다 |
| 법인을 못 읽었다 | 1 | 리포트가 반쪽이다 — 합계가 말 없이 줄어든다 |
| `mail.enabled=false` | 0 | **안 보내도록 설정한 것은 실패가 아니다** |
| `--dry-run`·`--no-mail` | 0 | 사람이 그렇게 부른 것이다 |
| LLM 서술이 폐기됐다 | 0 (경고만) | 리포트는 이미 나갔고 본문에 그 자리가 비어 보인다. 경보가 잦아지면 아무도 안 본다 |

## 무raise

발행 전 층은 예외를 던지지 않는다. 스케줄러가 예외를 받으면 **그 잡을 조용히
스케줄에서 뺄 수 있고**, 그러면 리포트가 안 나가는 것을 아무도 모르는 상태가 된다.
디스크가 가득 차도(`OSError`), 어댑터가 계약을 어기고 던져도(최외곽
`try/except Exception`) `Published`라는 값으로 돌아온다.

## `--dry-run`은 본문을 콘솔에 쏟지 않는다

본문은 HTML 리포트 전체(수만 자)다. 그대로 찍으면 정작 봐야 할 **수신자와 제목**이
화면 위로 밀려 올라간다. 그리고 본문은 같은 실행이 이미 파일로 써 뒀으므로 그것을
열어 보면 된다. 그래서 미리보기는 요청의 머리만 보여주고 본문 자리에는 길이를
남긴다.

`--dry-run`과 `--no-mail`은 다르다:

| | 하는 일 |
|---|---|
| `--dry-run` | 메일을 **조립하고** 나갈 요청을 보여준다. 수신자·제목·무력화된 줄 수를 확인하는 용도 |
| `--no-mail` | 메일을 **조립조차 하지 않는다.** 파일만 만든다 |

## 주기적으로 돌리는 법

`report run`은 **한 번 돌고 끝나는** 명령이다. 주기는 [9g단계](step-09g-schedule.md)의
`schedule`이 쥔다 — 떠 있는 프로세스가 스스로 시간을 재고, 그 프로세스가 매 발사마다
여기 있는 것과 같은 일을 한다.

바깥 스케줄러(cron·작업 스케줄러)에 `report run`을 직접 거는 것도 여전히 된다.
그때는 종료 코드를 감시해야 의미가 있다.

## 검토 포인트

1. **`report run --dry-run`을 먼저 돌려 보기.** 수신자가 맞는지, 제목의 기준일이
   어제인지. 실제 발송은 그다음이다.
2. **사내에서 실제로 한 번 보내 보기.** Outlook 데스크톱에서 표와 차트가 깨지지
   않는지 — 브라우저 미리보기로는 알 수 없다.
3. **종료 코드 감시.** 스케줄러가 0이 아닌 코드를 사람에게 알리도록 걸어야 이 단계의
   설계가 값을 한다. 걸지 않으면 종료 코드는 아무것도 아니다.
4. **`output/`의 보관 기간.** 지금은 무한히 쌓인다. 얼마나 남길지는 운영이 정할 일이다.
