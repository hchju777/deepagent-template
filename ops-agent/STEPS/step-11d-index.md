# 11d단계 — 전역 심볼 인덱스 (2-pass)

> **목적**: 레포 전체의 함수·클래스를 한 번에 세고(심볼) **누가 누구를 부르는가**를 확신 등급과
> 함께 잇는다(엣지). 11b의 추적기는 끝점에서 앞으로만 걷는다 — "이 컬렉션에 누가 쓰나", "이
> 함수를 누가 부르나" 같은 **역질문**과 끝점이 없는 서비스(컨슈머·배치)의 출발점은 전진 BFS로는
> 답이 없다. 인덱스가 있으면 둘 다 조회다.
>
> 상태: **6a~6d-4a 끝** — 인덱서·진단·공유 라이브러리·질의·calls.html·리드 연결(역질문 action·사다리 다섯 칸)·
> 끝점 사슬을 인덱스에서. **11b 추적기는 6d-4a에서 지웠다 — 엔진은 하나다.** 남은 것: 6d-4b(측정 T8~T10).
> 앞: [11b](step-11b-trace.md) 커밋 4 ✅, 5a(서비스 추적) **되돌림**. 결정의 근거는 [decisions ⑱](decisions.md).

## 왜 5a(서비스 추적)를 되돌렸나

5a는 서비스마다 사람이 `entries`(`파일:함수`)를 적게 했다. 두 가지가 걸렸다:

1. **하드코딩이다.** 레포 하나에 서비스가 여럿이고(한 레포가 프로세서·컨슈머·배치를 다 품는다)
   서비스마다 출발점이 여럿이면 적을 수가 없고, 적어도 코드가 바뀌면 조용히 썩는다. 11c에서
   "리드에게 대상 데이터의 이름을 알려 주지 않는다"([⑮](decisions.md))고 정한 것과 같은 이유로,
   **코드에서 유도할 수 있는 것은 사람이 적지 않는다.**
2. **구조 진단이 달랐다.** 커밋 4 측정에서 리드가 sink 코드를 `grep`·`read`로 더듬은 것은
   출발점이 없어서가 아니라 그래프에 **함수→함수 엣지가 없어서**였다. 끝점 전진 추적은 "끝점이
   있는 코드"만 닿고, 나머지는 그래프에 구멍이다. 출발점은 인덱스가 있으면 **in-degree 0인
   뿌리와 콜백 등록**에서 나온다 — 적는 것이 아니라 세는 것이다.

사내에서 다른 팀이 같은 문제를 2-pass 전역 심볼 인덱스로 푼 분석을 받았고, 그 설계를 기반으로
방향을 다시 잡았다. 되돌린 커밋은 히스토리에 있다(`git log --oneline -S"trace_service"`).

## 사내 분석의 여섯 답과 우리 결정

사내 도구를 만든 쪽에 여섯을 물었다. **그 답을 무조건 수용하지 않는다** — 받은 것, 바꾼 것,
미룬 것을 나눈다.

| 질문 | 사내 답 | 우리 결정 |
|---|---|---|
| 추적기와 인덱스를 둘 다 두나 | 인덱스만. 둘이면 불일치가 난다 — 불일치는 Gap으로 | **엔진 하나로 수렴**하되 당장은 추적기를 둔다. 6c에서 `code.trace`를 인덱스 위 BFS로 옮기고, 둘의 답이 다르면 Gap으로 적는다. 패리티가 확인되면 추적기를 뺀다 |
| 동명 포트·구현체 | 메서드 단위 exact, 레포 전체 범위(한 레포에 도메인이 여럿이면 다른 도메인의 동명이 걸린다 — 약점으로 인정) | 수용 + 순위. 포트와 **모듈 경로를 가장 길게 공유하는 쪽**, 그다음 메서드를 더 갖춘 쪽, 동점이면 전부 candidate |
| 호출 지점 역전파(힌트 없는 주입) | 안 한다 | **한다.** `self.repo = repo`에 힌트가 없으면 `Cls(...)` 생성 지점의 그 인자를 본다 — 하나거나 전부 같으면 확실, 갈리면 추정. 11b의 `_callees` 좁히기가 사내 코드에서 이게 흔하다는 증거를 줬다 |
| 어느 커밋을 인덱싱하나 | main만(핀 검사 없음). gitlink SHA를 권고 | 수용. **배포 핀 SHA마다** 인덱싱한다. 공유 라이브러리는 따로 등재하지 않는다 — 리더가 서브모듈 안을 **부모가 박은 gitlink SHA로** 읽으므로 레포마다 자기 핀의 사본이 그 레포의 인덱스에 든다(6b-2). 안 채워졌거나 버전이 없으면 못 봤다고 말한다 |
| 서비스 귀속 | 레포 단위 합집합 | 수용. impact 질의는 합집합·역할 미구분, 흐름 질의만 `owner()`로 좁힌다(6c) |
| 이름 짓기 | LLM 없이. 짧은 이름 + 후보, `repo:file:qualname` 인용, hop 30~50자 | 조정. 표시는 `qualname (file:Lline)`, 입력은 `qualname` 또는 `file:qualname`, 모호하면 후보를 나열한 오류, 리드 출력은 경로 ≤3 · hop ≤12(6c·6d) |

공유 라이브러리의 모양도 확인했다: 각 레포가 같은 라이브러리를 **서브모듈로 `src`와 같은 깊이**에
두고(`.gitmodules`의 `[submodule "<dir>"] path = <dir>`), 레포마다 핀이 다를 수 있다. 그래서
"공유 라이브러리를 한 번 인덱싱"이 아니라 **레포가 가리키는 핀마다** 인덱싱해야 한다. 처음엔 공유 레포를 따로
등재하는 설계였는데, 11a가 이미 서브모듈 안을 핀 SHA로 읽고 있어 빠진 것은 목록(`ls`) 하나였다(6b-2).

## 인덱스가 무엇인가 (`src/knowledge/index.py`)

**pass 1 — 수집.** 모듈마다 AST를 한 번 훑어 심볼(module/class/function/method)과 그 함수의
원재료(호출 체인, 인자로 넘긴 이름, 데코레이터, 지역 대입, `self.x = …`, import, 어노테이션)를
모은다. **파싱 실패도 모듈 심볼로 남는다**(`parse_error`) — 커버리지 `.py 수 == module 수`를
말하려면 못 읽은 파일도 세야 한다.

**pass 2 — 해석.** 심볼 id는 배열 위치, 외부 키는 `(repo, qualname)`. 엣지는
`calls · inherits · imports · overrides · implements` 다섯에 확신 `exact · candidate` 둘.
같은 엣지는 **candidate → exact로만 승격**하고 반대는 없다(한 번 확실했던 것을 추정이
끌어내리지 않는다). 호출 해석의 순서가 전부다 — 위에서 걸리면 거기서 끝:

| | 모양 | 어떻게 | 확신 |
|---|---|---|---|
| (a) | `f()` | 파라미터·지역이 모듈 이름을 **가린다** → 모듈 정의 → import 별칭 → builtin은 버림 → 레포 전체 최상위 동명 | exact / candidate |
| (b) | `self.m()` | 자기 클래스와 조상에서. 없으면 **하위 클래스로만** 좁힌 candidate(`restricted`, 템플릿 메서드) | exact / candidate |
| (c) | `x.m()` | 타입 표(파라미터 힌트·지역 대입·모듈 싱글턴·`Depends` 제공자·생성 지점 역전파)로 수신 클래스를 안다 | exact |
| (c′) | `Cls().m()` · `super().m()` · `f(...).m()` | 생성자 호출을 받는 쪽 / 직접 베이스들의 MRO에서(베이스마다 다르면 그 조상들만 후보) / f의 반환 클래스에서 | exact / candidate |
| (d) | `a.b.c()` | import·모듈·클래스 접두사를 **긴 것부터** | exact |
| (e) | 그 밖 | 같은 이름 메서드 전부에 candidate — `STOPLIST`(`get`·`update`·`info`…)와 상한 12. 상한을 넘으면 **재정의 뿌리로 접는다**(전부가 `Base.save`를 재정의하면 뿌리 하나에 candidate, via `root`) | candidate |

어노테이션은 `Optional`·`Annotated`·`Final`·`Type`·`X | None`·문자열을 벗기고 **컨테이너는 안
벗긴다**(`list[X]`의 원소에 대한 호출이 아니다). `Annotated[T, Depends(g)]`는 g가 돌려주는
클래스가 진짜 타입이다(포트 뒤의 구현체).

그 밖에: 인자로 넘긴 이름이 **확정으로** 함수를 가리키면 `calls`(via `callback`) — 등록처에서
실행된다. 데코레이터 호출도 `calls`(via `decorator`). `inherits`·`overrides`(던더 제외).
포트(Protocol/ABC)와 **이름이 같은** 클래스는 메서드 단위 `implements`, 없는 메서드는 gap.
함수마다 11b의 `_collect_reads`로 자원 참조(`Resource(kind, name, direction, line, via)`)를 달아
`writers(kind, name)`·`readers`가 조회다.

**미해석을 분류해서 센다** — 이 숫자가 인덱서의 거울이다:

| 분류 | 뜻 | 정상인가 |
|---|---|---|
| `builtin` | `len()`·`print()` | 정상 |
| `external` | 머리가 import인데 어느 레포에도 없다(서드파티) | 정상 — 동명 후보로 떨어뜨리면 거짓이 된다 |
| `stoplist` / `too_many` | (e)에서 걸러진 것 | 정상 |
| `variable_call` | 파라미터·지역을 부른다(`clock()`) | 정상 |
| `field_call` | `self._clock()` — 메서드가 아니라 호출 가능한 필드 | 정상 |
| `method_missing` | 수신 클래스는 아는데 그 메서드가 없다(외부 베이스의 메서드) | 많으면 의심 |
| `unknown` | 수신 타입을 모르고 동명도 없다(stdlib 객체의 지역) | 많으면 의심 |

## 검증 하네스 — `python -m src code check`

예고에서는 `tools/index_check.py`라 했으나 CLI 하위 명령으로 넣었다 — 번들을 읽고 코드 리더를
조립하는 길이 CLI에 이미 있어, 별도 도구면 설정 읽기를 베끼게 된다. 로직은
`src/knowledge/index_check.py`에 있고 CLI는 배선만 한다.

- **A 불변식** — id가 배열 위치, 엣지 범위·self-loop·중복·어휘, method의 `class_id`, 줄 범위가 파일
  안, **커버리지 `.py == module`**(레포마다). 하나라도 깨지면 종료 코드 1.
- **B 정밀도 표본** — exact `calls` N건(기본 100, `--sample`·`--seed`)을 뽑아 호출자 **본문 줄
  범위 안 또는 데코레이터**에 대상 이름이 있는지 본다. 생성자는 클래스 이름으로.
- **C 재현율 표본** — 함수 본문을 다시 파싱해 같은 모듈 최상위 함수를 이름 그대로 부르는 호출
  (틀릴 여지가 없는 것)이 전부 엣지로 있는지. 정밀도만 재면 아무것도 안 잇는 인덱서가 100%다.

보고는 일곱 줄 — 사람이 옮겨 적는다. **B의 한계**: "이름이 본문에 있나"만 보므로 **동명
오해석은 못 잡는다**(아래 `clock` 버그가 정밀도 100%에서도 숨어 있었다). 그건 미해석 분류를
읽어서 찾았고, 6b의 하네스 D(동명이 여럿인 표본의 수동 대조)가 그 자리다.

## 사내 첫 `code check` — 레포 전부, 모듈 980

| 줄 | 사내 |
|---|---|
| 1 심볼 | 9668 (module 980 · class 1816 · function 2537 · method 4335) · 파싱 실패 0 |
| 2 엣지 | calls 8224/1809 · inherits 816 · imports 2437 · **overrides 3741** · implements 82 |
| 3 불변식 | OK — 전 레포가 빠짐없이 들어갔다 |
| 4 정밀도 | 96/100 — 틀린 넷이 전부 `테스트 함수 → 어떤 베이스.__init__` |
| 5 재현율 | 330/330 |
| 6 미해석 | builtin 4172 · external 4387 · stoplist 4827 · **too_many 1235 · unknown 1904** · variable_call 105 · method_missing 18 · field_call 3 |

읽은 것과 한 것(**6a 후속 커밋**):

- **정밀도의 틀린 넷은 인덱스가 아니라 하네스 버그였다.** 테스트가 하위 클래스를 생성하고 하위에 `__init__`이
  없어 베이스의 `__init__`으로 풀렸다 — 실제로 실행되는 생성자가 그것이니 엣지는 맞다. 하네스가 본문에서
  베이스 이름만 찾았다. 하위 클래스 이름도 맞은 것으로 센다.
- **테스트 파일은 입구에서 건너뛴다.** 후보 풀·재현율에서만 빼고 심볼·엣지는 만들던 것을, 아예 읽지 않는다
  (`tests/`·`test/`·`test_*.py`·`*_test.py`·`conftest.py`). 테스트가 어떤 함수를 부르는지는 "누가 부르나"의
  답이 아니다. 커버리지 불변식은 **같은 술어**(`is_indexed`)로 센다 — 둘이 갈리면 `.py == module`이 영원히
  안 맞는다. `is_test` 필드는 뜻이 없어져 뺐다.
- **overrides 3741은 조상 전부에 걸어서다.** 메서드 4335개에 재정의 3741은 베이스 40 × 구현 30 꼴의 곱이다.
  파이썬 의미대로 **가장 가까운 조상 하나**로 줄였다. 여기 `src/`는 계층이 얕아 68 그대로지만 사내 수치는
  크게 줄어야 한다.
- **too_many 1235 / unknown 1904가 6b의 우선순위다.** 수신 타입을 모르는 `x.m()`이 3천 건이고 그중 1235건은

## 6b-2 — 공유 라이브러리는 레포마다 자기 핀으로

**설계가 작아졌다.** 원래는 공유 레포를 `code.repos`에 한 항목으로 등재하고 `.gitmodules`의 url로 이어, 소비
레포마다 gitlink SHA로 따로 읽을 생각이었다(선택 `module_prefix`까지). 짓기 전에 11a가 이미 해 둔 것을 확인했다:
`code sync`는 `--recurse-submodules`로 받고, 리더의 `show`는 서브모듈 안 파일을 **부모가 박은 SHA로** 읽고,
`grep`은 채워진 서브모듈 안까지 보고, `code status`는 안 채워진·뒤처진 서브모듈을 말한다. 빠진 것은 **목록(`ls`)
하나**였다 — `ls-tree -r`가 서브모듈을 이름 하나로만 내서 인덱서의 파일 목록에 그 안이 없었다.

그래서 리더의 `ls`가 채워진 서브모듈로 **한 단계** 내려가 gitlink SHA의 파일들로 그 이름을 바꾼다(서브모듈의 지금
HEAD가 아니다). 그러면 `<서브>/x.py`의 모듈 이름이 경로에서 `<서브>.x`로 나오고 `from <서브>.x import f`가 **같은
레포 안에서** 풀린다. 레포 다섯이면 공유 심볼도 다섯 벌인데, 그게 맞는 모양이다 — 레포마다 다른 핀을 돌린다.
공유 레포 등재·`module_prefix`·별도 인덱스는 **안 만든다.** 안 채워진 서브모듈은 지금처럼 "못 봤다"로 남고 그쪽
import는 `external_shared`로 계속 세어진다.

같이 고친 것:

| | 무엇 | 왜 |
|---|---|---|
| 추정 후보 풀을 **부르는 쪽 레포 안으로** | 같은 이름 함수·메서드 후보가 레포를 건너 전역이었다 | 다른 레포의 함수는 이 프로세스에 없다(레포 사이는 HTTP·Kafka, 흐름 그래프의 몫). 공유 라이브러리가 레포마다 들어오면 같은 이름 후보가 레포 수만큼 겹친다. 측정판에서 dt-api의 맨 이름 `now()`가 dt-core의 공유 `now`를 후보로 잡아 드러났다. 사내의 `too_many`도 일부는 이것이었을 것이다 |
| 버전 없는 서브모듈을 `ls`가 말한다 | 부모만 당겨지고 서브모듈은 안 당겨진 트리에서 `ls`는 "완전하다"고 했다 | `show`·`grep`은 이미 "`code sync`가 고친다"고 말한다 — 목록만 빠져 있었다 |
| gitlink·"그 버전이 있다"를 담는다 | 인덱서는 서브모듈 안 파일을 하나씩 읽는다 — 파일마다 subprocess 여섯이었다 | 사내는 레포 다섯 × 수백 파일이라 Windows에서 수천 개다. gitlink는 커밋이 SHA일 때만 담고(참조는 움직인다), "있다"는 한 번 참이면 참이다. 파일당 둘로 줄었다 |

측정판에도 같은 모양을 심었다: dt-core가 공유 라이브러리를 서브모듈로 쓰고, processor가 import 없이 부르던
`normalize`·`now`가 거기서 온다. `code check --unresolved`: 심볼 15 · calls 확실 5 · 불변식 OK · 정밀도 5/5 ·
8번 공유 0, processor → 공유 라이브러리 **확실** 둘. 레포를 건너던 후보는 사라졌다.

사내 기대(`code graph` → `code check --unresolved`): 1번 심볼 수가 공유 라이브러리 크기 × 레포 수만큼 늘고, 8번
공유 라이브러리 738 → **0**(남으면 그 레포의 서브모듈이 안 채워졌거나 뒤처진 것 — `code status`가 말한다), 2번
inherits·calls 확실이 늘고, 9번 `self.attr 출처 모름` 42가 줄고, 10번 too_many가 준다(후보 풀이 레포 안으로 좁혀진
몫까지). 그래프 만드는 시간이 눈에 띄게 늘면 알려 달라 — 공유 파일을 레포마다 읽는다.

## 6b-2 후속 — `import *` 재수출·공유 라이브러리 진단·클로저 변수

| | 무엇 | 왜 |
|---|---|---|

## 6c-1 — 질의: `code callers` · `code path` · `code uses`

11d를 시작한 이유였던 역질문에 인덱스로 답한다. 리드에 잇기(6d) 전에 사람이 먼저 쓰고 아는 답과 맞춰 본다.
질의는 `src/knowledge/query.py`의 순수 함수이고 던지지 않는다.

| 명령 | 답하는 것 | 어떻게 |
|---|---|---|
| `code callers <이름>` | 이 함수를 누가 부르나, 어느 진입점에서 오나 | 호출 엣지를 거꾸로 넓이 우선(짧은 경로부터). 진입점은 부르는 쪽이 없는 함수와 라우트 핸들러 |
| `code path <A> <B>` | A에서 B로 어떻게 가나 | 앞으로 넓이 우선, 짧은 것부터 셋. 없으면 반대 방향이 있는지도 말한다 |
| `code uses <자원>` | 이 컬렉션·토픽·키·그룹을 누가 쓰고 읽나 | 함수마다 단 자원 참조(6a)에서. 함수마다 진입점 한 줄. 정확한 이름이 없으면 부분 일치(키 템플릿을 그대로 치기 어렵다) |

- **디스패치를 따라간다.** `overrides`·`implements`(구현 → 베이스·포트)를 뒤집어 "베이스 `=>` 구현"으로 넣는다 —
  베이스 메서드를 부르는 코드는 실행 시점에 구현으로 간다. 재정의 뿌리로 접은 추정 엣지(6b-1)도 이 길로 구현까지 닿는다.
- **디스패치로만 닿은 막다른 곳은 진입점이 아니다.** 부르는 쪽 없는 베이스·포트 메서드는 실행의 시작이 아니라
  프레임워크가 부르는 자리일 수 있다 — 진입점이라 하면 거짓이고, 말을 안 하면 "아무도 안 부른다"로 읽힌다. 따로 말한다.
- **이름 찾기:** `qualname`, 끝부분(`Class.method`), 앞에 `파일:`·`레포:`. 정확한 qualname이 끝부분 일치보다 앞선다.
  여럿이면 후보 다섯을 보여 주고 **멈춘다** — 코드가 고르면 사람이 모르는 사이에 엉뚱한 함수를 본다.
- **표시:** 대상·바로 부르는 곳은 `qualname (파일:L줄) [레포 · 서비스]`(줄은 부르는 자리), 경로는
  `[레포] 모듈.이름 → … => …`. 확실 `→`, 추정 `?→`, 디스패치 `=>`. 서비스는 11c의 `owner()`로 붙이고 못 가르면 레포만.
  기본 열 줄씩 자르고 `--all`로 전부. 상한(12단계·노드 2만)에 걸리면 말한다.

측정판:

```
code uses alarm_events
  alarm_events [collection]
    쓰기 1:
      sink.writer.run (sink/writer.py:L10) [dt-core · sink] — 진입점: 이 함수(부르는 곳 없음)
    읽기 2:
      api.alarms.count_recent (api/alarms.py:L20) [dt-api · api] — 진입점: alarms.summary_badge(라우트 router.post('/badge'))
      …
code path summary_badge count_recent
  [dt-api] alarms.summary_badge → alarms.badge → alarms.count_recent
```

**사내 확인(10-03): `code uses`·`code callers` 둘 다 아는 답과 맞았다.**

사내에서 볼 것 — **아는 답과 맞나**: 잘 아는 컬렉션 하나로 `code uses`, 잘 아는 함수 하나로 `code callers`. 맞다 /
틀리다 / 빠졌다 한 줄씩. 빠진 것이 있으면 그것이 6b-3에서 무엇을 지을지 정한다(예: 진입점이 "못 찾았다"면 프레임워크
등록 모양, 쓰기가 빠지면 자원 참조 수집).

## 6c-1 후속 — 이름이 다른 포트와 구현 · `= Depends(공급자)`

사내 질문: presentation이 `XxxProtocol.get_…`으로 부르고 `Xxx.get_…`이 구현인데 이것도 보이나. 지어낸 이름으로
같은 모양을 만들어 돌려 보니 **주입 모양에 따라 반만** 보였다.

| 주입 모양 | 고치기 전 | 고친 뒤 |
|---|---|---|
| `svc: Annotated[XProtocol, Depends(공급자)]` | 공급자의 반환 클래스로 구현까지 | 같다 |
| `svc: XProtocol = Depends(공급자)` | Protocol 메서드에서 멈춤 — 기본값 자리의 공급자를 안 봤다 | 공급자가 이긴다 — 구현까지 |
| 생성자에 `XProtocol` 타입으로 주입 | Protocol 메서드에서 멈춤 | `XProtocol.m => X.m` 디스패치로 구현까지 |

원인 둘: 인덱서가 **이름이 똑같은** 포트와 구현만 이었고(11b 추적기는 이름 규칙 `XProtocol·XPort·XInterface·XABC·
AbstractX·IX → X`를 봤는데 인덱스로 옮기며 빠졌다), `= Depends(공급자)` 꼴에서는 어노테이션(포트)이 이겼다.

- **이름 규칙 짝도 `implements`로 잇는다**(via `name_rule`). 포트의 메서드를 하나도 안 가진 클래스는 구현으로 보지
  않는다 — 이름만 닮은 클래스가 "구현인데 메서드가 없다"는 거짓 gap을 만들지 않게. 순위는 같은 이름 짝과 같다.
- **포트를 직접 상속한 구현에는 걸지 않는다** — `overrides`가 이미 잇는다. 여기 `src/`에서 `DeployedCode(DeployedCodePort)`가
  두 길로 잡혀 질의에 같은 디스패치가 두 번 나왔다. 질의 그래프도 같은 링크를 한 번만 담는다.
- **`= Depends(공급자)`도 공급자의 반환 클래스**가 수신 타입이다.

여기 `src/`: implements 0 → 6(이름 규칙 짝, 전부 맞음), 정밀도 100/100. 시험 하나가 처음엔 빈틈이 있었다 — 이름만 닮은
클래스를 후보로 넣어도 엣지는 안 생기고 거짓 gap만 생겨서 엣지만 보던 시험이 놓쳤다. 스윕이 잡았고 gap까지 보게 조였다.

사내 확인: 그 구현 메서드로 `code callers`를 돌리면 presentation의 라우트가 진입점으로 나와야 한다. `code check`의
2번 줄 implements(82)가 는다.

| 자원(컬렉션·토픽·키·그룹) | 진입점 → … → **쓰는 함수 → [자원] → 읽는 함수** → … → 진입점(라우트) — 데이터가 어디서 와서 어디로 나가나 |

선: 확실 실선, 추정 점선, 디스패치(베이스 `=>` 구현) 점점선, 쓰기·읽기는 색. 상자: 레포 색 띠, `▶` 진입점, `◇` 부르는 쪽 없는
베이스. 상자를 누르면 거기서 다시 펼치고(뒤로 가기 있음), 오른쪽 칸에 `qualname (파일:L줄)`, 레포·서비스, 라우트, 바로 부르는

브라우저는 단계별로 펼치기만 한다(심볼마다 미리 펼치면 수십 MB). 시험은 실린 인접 목록이 질의 그래프와 **같은지**를 본다.

| 드러난 것 | 고친 것 |
|---|---|
| 함수 화면에서 자원 열이 "단계+1"에 고정돼 대상이 얕으면 빈 열을 건너뛰어 화면 밖으로 밀렸다(선만 길게 빠져나갔다) | 실제로 쓰인 마지막 열 바로 다음에 둔다 |
| 부르는 곳 28개인 함수에서 이미 다른 열에 놓인 상자로 돌아가는 선이 엉켰고, 이름이 뒤에서 잘려 `deployed_code.DeployedCod…`만 남았다 | 함수 사이 선은 바깥으로 한 단계씩만(전부는 오른쪽 목록), 이름은 앞을 자른다(`…DeployedCode.read`) |
| 창이 좁아 머리줄이 접히면 양옆 칸 위쪽이 머리줄에 가렸다(고정 오프셋) | 머리줄 높이를 따르는 배치. 고른 상자가 가운데에 오게 스크롤 |

**사내 확인(10-03): 사람이 훑어 끊긴 곳이 눈에 띄지 않았다.**

사내에서: `code graph` 뒤 `output/graph/<gbm>-<fct>/calls.html`을 브라우저로 연다. 자원 목록에서 잘 아는 컬렉션을 골라
쓰는 쪽·읽는 쪽 사슬이 아는 것과 맞는지, 함수 몇 개를 눌러 끊긴 곳(`▶`인데 진입점이 아닌 것, 이어져야 할 구현이 안 나오는 것)이
있는지 본다. 끊긴 곳의 모양을 알려 주면 그게 다음에 무엇을 지을지 정한다.

## 6c-2 — 추적기와 인덱스의 대조

decisions ⑱의 "엔진 하나"로 가는 길이다. 리드가 받는 `code.trace` 사슬은 아직 11b 추적기가 `code graph` 때 끝점에서
앞으로 걸어 만든 것이고, 리드는 오버레이에서 그것을 읽기만 한다. 인덱스는 그사이 공유 라이브러리·싱글턴·이름 규칙
포트까지 보게 됐다. 추적기를 빼기 전에 **둘이 어디서 다르게 말하나**를 숫자로 본다.

- `code graph`가 인덱스를 만든 뒤 추적된 끝점마다 **사슬 첫 걸음(핸들러 `def` 줄)을 품는 가장 안쪽 함수**를 인덱스에서
  찾고, 거기서 호출·디스패치를 따라 **추적기와 같은 깊이(6)**까지 닿는 자원을 모은다(`query.reach`). 깊이를 맞추지 않으면
  "인덱스만"이 대부분 더 깊이 간 몫이 되어 대조가 뜻을 잃는다. 오버레이에 노드가 없는 자원은 빼고 센다 — 추적기 쪽
  (`add_trace`)도 그렇게 싣는다.
- 추적기의 읽기와 (종류, 이름)으로 대조해 끝점에 `같음 / 다름 / 핸들러 못 찾음`을 적는다(`parity.py` — `flow`와
  `query`를 서로 import하면 `index → flow`와 순환이라 따로 뒀다).
- **다르면 `code.trace` 출력에 한 줄**: `인덱스 대조: 다르다 — 인덱스만 … / 추적기만 …`. 같으면 안 적는다(소음). 리드는
  "인덱스만" 자원을 다음 읽기 후보로 쓸 수 있다. 추적기 사슬 자체는 그대로다.
- `code graph` 진행 줄 `끝점 대조(인덱스): 같음 · 다름 · 핸들러 못 찾음`, `code status`의 그래프 줄 끝에 같은 숫자.

측정판: 추적된 끝점 1개 같음.

사내에서 볼 것: `code graph`의 그 진행 줄(또는 `code status`). 다름이 있으면 그중 하나로 `code trace <끝점 path>`를 돌려
"인덱스 대조" 줄을 옮겨 주면 된다 — "인덱스만"이 맞으면 인덱스가 더 본 것이고, "추적기만"이 맞으면 인덱스가 놓친 모양이다.
같음이 대부분이면 6d에서 `code.trace`를 인덱스로 옮기고 추적기를 뺀다.

### 사내 첫 대조(10-03) — 같음 149 · 다름 7 · 핸들러 못 찾음 0

핸들러 못 찾음 0은 사슬 첫 걸음과 인덱스의 함수 줄 범위가 전부 맞았다는 뜻이다. 다만 **숫자만 찍어서 그 7개가 어느 path인지
알 길이 없었다** — 끝점이 150개 넘는다. `code graph` 끝 요약과 `code status`가 다른 끝점을 path 순으로 열 개까지 나열한다
(`flow.index_diff_lines`):

```
       인덱스 대조가 다른 끝점 7 — 하나씩 `code trace <path>`로 본다:
         /a/b — 인덱스만 x [collection] / 추적기만 y [topic]
```

차이는 종류마다 둘까지만(`외 n`) — 전부는 `code trace`의 "인덱스 대조" 줄에 있다. 다 같으면 목록이 없다.

## 6c-2 후속 2 — 대조 줄이 원인을 말한다 · Git Bash 인자

사내 다름 7을 받고 보니(인덱스만 5 · 추적기만 2) **한 줄만으로는 원인을 가를 수 없었다.** 인덱스만이면 추적기가 놓친
것인지 인덱스가 이름만 같은 후보를 타고 넘어간 것인지, 추적기만이면 인덱스가 그 함수까지 못 간 것인지 가서 못 본
것인지 — 사람이 끝점마다 `code trace`·`code uses`·`code path`를 손으로 옮겨 적어야 했다. `parity.check`가 자원마다
`why`를 적고 `code trace`가 대조 줄 아래에 한 줄씩(쪽마다 셋까지) 찍는다:

```
인덱스 대조: 다르다 — 인덱스만 line_state [collection] / 추적기만 audit_log [collection]
  인덱스만 line_state [collection]: [svc] c.cand ?→ stores.Lines.fetch_rows — 이름만 같은 후보(?→)를 거친다
  추적기만 audit_log [collection]: 인덱스가 못 이은 호출 q.recent → q.lost (api/q.py:L10)
```

| 쪽 | 무엇을 적나 | 읽는 법 |
|---|---|---|
| 인덱스만 | 핸들러에서 그 자원을 건드리는 함수까지의 경로. 확실한 호출만 → 디스패치까지 → 추정까지 순으로 찾아 **처음 닿는 단계의 가장 짧은 길** | `?→`를 거치면 인덱스가 넘어간 것(후보 과대), 전부 `→`면 추적기가 놓친 것 |
| 추적기만 | 추적기 사슬을 뿌리부터 내려가며 인덱스가 **처음 못 닿은 걸음** → `인덱스가 못 이은 호출 부모 → 걸음 (파일:L줄)`. 다 닿으면 `인덱스는 f에 닿지만 거기서 이 이름을 못 본다`. 걸음을 품는 함수가 없으면 그렇게 | 못 이은 호출이면 해석기 구멍, 못 본 것이면 자원 참조 구멍 |

짧은 추정 길보다 긴 확실한 길을 고르는 이유: 짧은 쪽만 보이면 "후보를 거쳐서만 닿는다"로 읽혀 인덱스가 틀렸다고
판정하게 된다. 같은 줄이 리드의 `code.trace`에도 간다 — 인덱스만 경로는 리드가 읽을 함수를 짚어 준다.

측정판 사본으로 실제 빌드를 확인했다: 핸들러가 스톱리스트 이름(`execute`)의 메서드를 타입 모르는 수신자로 부르게 하자
추적기는 후보로 따라가고 인덱스는 멈춰 `추적기만 line_state [collection]: 인덱스가 못 이은 호출 <핸들러> →
LineRows.execute (파일:L줄)`이 나왔다 — 스톱리스트가 끊은 바로 그 호출을 짚는다.

**Git Bash 인자**: 사내에서 `code trace /items/{…}`가 `C:\Program Files/Git/items/{…}`로 와 "끝점에 없다"가 났다.
`code trace`·`code flow`가 드라이브 문자로 시작하는 인자를 가장 길게 맞는 끝점 path로 되돌린다
([windows.md](windows.md) 함정 ⑧).

## 6c-2 후속 3 — 사내 다름 7의 판정 · 같은 path의 핸들러 전부에서 출발

원인 줄로 사내 다름 7을 판정했다(10-03). 셋은 원인 줄 하나로, 나머지는 사람이 코드 한두 줄을 보고 갈랐다:

| 수 | 판정 | 무엇이었나 |
|---|---|---|
| 1 | **대조 버그** | 같은 path에 GET과 PUT이 둘 다 걸려 있었다. 추적기는 그 path의 라우트 선언 **전부**를 사슬 뿌리로 삼는데 대조는 첫 핸들러에서만 출발해, PUT 쪽이 쓰는 토픽이 "추적기만"이 됐다. 원인 줄이 `인덱스가 못 이은 호출 핸들러 → <둘째 핸들러>`로 짚었다 → **고쳤다** |
| 1 | **추적기 오탐** | 검색 끝점의 `Query(..., description="… (ex: <키>)")`. 추적기는 `def` 줄부터 글자를 훑어 설명 문자열 속 예시를 읽기로 잡았고, 인덱스는 본문부터 훑어 안 잡았다 — 인덱스가 맞다 |
| 1 | **인덱스가 맞다** | 요청 본문의 종류 값으로 전략을 고르는 서비스. 인덱스는 수신자 타입 모르는 `process`를 전략 베이스로 접어 하위 전략(그중 하나가 컬렉션 하나를 더 읽는다)까지 갔고, 추적기는 이름이 수백 개인 `process`에서 멈췄다 |
| 1 | **인덱스가 넘어갔다** | 다른 서비스의 함수가 같은 `?→ 전략베이스.process` 후보 엣지를 탄다 — 그 모듈은 전략 모듈을 import하지도 않는다. 이름만 같은 후보 풀이 레포 전체라서다 → 후속 4 |
| 3 | 판정 안 함 | 위 둘과 **같은 후보 엣지**를 거친다(그 메서드를 바로 부르는 곳이 다섯 — 끝점 다섯과 하나씩 맞는다). 전략을 고르는 서비스 쪽이라 인덱스가 맞을 공산이 크다. 후속 4 뒤에 남는지로 본다 |

**고친 것**: 대조가 사슬에서 부모 없는 걸음 전부(= 같은 path의 핸들러 전부)를 품는 함수들에서 함께 출발한다.
측정판 사본에 같은 path로 PUT 핸들러를 하나 더 달자, 고치기 전 대조는 사내와 같은 모양(`추적기만 … 인덱스가 못 이은 호출
핸들러 → alarms.reset_badge`)을 냈고 고친 뒤 같음이 됐다.

**인덱스를 서명부터 훑게 하지 않은 이유**: 추적기와 범위를 맞추면 위 오탐을 인덱스로 옮긴다. 인자 기본값이 진짜 키인 경우
(`key: str = "…"`)는 인덱스가 놓치지만 드러난 사례가 없다 — 열린 것에 둔다.

## 6c-2를 닫는다 — 종료 판정과 멈춤 규칙

6c-2의 목적은 하나였다: **추적기를 빼고 `code.trace`를 인덱스 위로 옮겨도 되는가**를 판단할 숫자(decisions ⑱의
"엔진 하나"). 그 판단은 섰다 — 사내 끝점 156개 중 같음 150 · 다름 6(10-05, 후속 3 뒤). 다름 6은 추적기가 틀린
것 1, 인덱스가 더 본 것 1(+ 같은 모양일 공산이 큰 3), 인덱스가 넘어간 것 1. **인덱스가 추적기보다 못한 지점은
없고**, 유일한 약점(이름만 같은 후보가 모듈을 넘어감)은 모양을 안다 → [backlog ⑨](backlog.md).

후속 1(끝점 나열)·2(원인 줄)는 이 판단에 필요했고, 후속 3은 방금 낸 것의 버그였다. 후속 4(보이는 후보 표시)는
둘 다 아니라 **하지 않는다** — 설계는 backlog ⑨에 그대로 적어 뒀고, 6d 측정에서 리드가 그 자리에서 헛읽기를
하는 것이 잡히면 꺼낸다.

**멈춤 규칙(합의, 10-05)**: 후속은 (a) 방금 낸 것의 버그이거나 (b) 그 단계의 종료 판단에 필요한 것일 때만.
나머지는 backlog에 적고 다음 단계로 간다. 단계를 시작할 때 종료 판단이 무엇인지 먼저 적는다.

## 6d — 리드 연결

**종료 판단(시작할 때 적음, 10-06)**: ① `code.callers`·`code.uses`가 리드 action이고 로컬 측정판에서 리드가 실제로
낸다(T8) ② `code.trace`가 `code graph` 때 인덱스에서 만들어지고 추적기는 돌지 않는다 — 사내 `code graph` 한 번의 두 엔진
대조 줄이 150/6과 맞은 뒤 추적기를 지운다 ③ T8~T10을 한 번 잰다(켬/끔 각 3판, 11b와 같은 하네스). 셋이 되면 닫고,
숫자가 어떻든 개선은 backlog로.

### 6d-1 — action 등재·어댑터 ✅

- `ACTIONS`에 `code.callers(name)`·`code.uses(name)`. 레인은 `code_tracer`(action 접두사로 정해진다, decisions ⑰).
- `DeployedCodePort`에 둘을 추가. `DeployedCode`는 번들의 심볼 인덱스를 **그래프와 같은 신선도**로 붙인다
  (`attach_index` — `_code_if_ready`가 그래프가 신선할 때만 `read_index`를 읽는다. 옛 번들엔 없어 "심볼 인덱스 없음"을
  말하고, 그러면 역질문 둘이 목록에서 빠진다 — `briefing._hidden(flow_graph, code_index)`, `make_lead(code_index=)`).
- **출력 조립은 CLI와 한 함수다** — `query.callers_lines`·`uses_lines`·`ambiguous_lines`·`entry_brief`로 내렸고
  `code callers`·`code uses`가 그걸 부른다. 사람이 사내에서 CLI로 맞춰 본 답이 곧 리드가 받는 답이다(둘로 베끼면 한쪽이
  먼저 어긋난다 — 규율 8과 같은 이유). 이름이 여럿이면 코드가 고르지 않고 후보를 적은 실패로 답한다(CLI와 같다).
- `StubDeployedCode`가 seeds의 `uses`·`callers`도 받는다 — 6d-2의 dryrun 대본용.

측정판에서 리드가 받는 답(`_code_if_ready` → `code.uses("alarm_events")`): 쓰기 1(sink의 `run`, 진입점 없음) · 읽기 2
(api의 `count_recent` — 진입점 `summary_badge`(라우트), `recent_alarms` — 부르는 곳 없음). `code.callers("run")`은 두
후보를 적은 실패. CLI 출력과 글자까지 같다.

### 6d-2 — 사다리 넷째·다섯째 칸 · dryrun 대본 ✅

목록에만 있고 예시에 없는 action은 리드가 안 낸다(11b 측정 — 셋째·넷째 칸이 사내 네 실행에서 0번). 사다리를
rest → trace → recompute.count → **uses** → **callers**로 늘리고 이름은 코드가 앞 증거에서 뽑아 박는다
(`briefing._ladder_step`, 한 라운드에 한 칸, 억제는 "그 이름으로 낸 적이 있나"):

| 칸 | 이름 | 왜 |
|---|---|---|
| `code.uses(name)` | 재집계가 **일치**면 그 컬렉션, **불일치**면 끝점이 읽은 캐시 키(추적 읽기 중 rediskey; 없으면 컬렉션) | 일치 = 컬렉션도 옛것 → 상류 쓰는 쪽. 불일치 = 컬렉션은 최신인데 화면이 옛것 → 캐시를 누가 쓰나. 측정판의 sink-stopped·cache-stale이 정확히 이 둘이다. `match`는 재집계 증거(repr)에 그대로 있다 |
| `code.callers(name)` | uses 증거의 첫 "쓰기" 함수 qualname | 쓰는 함수의 진입점이 고장의 부품(컨슈머·배치)이다. 읽기만 있는 자원이면 칸이 없다 |

`integrate_fields`가 State의 증거와 인덱스 유무를 예시에 넘긴다 — 인덱스가 없으면 두 칸이 없다(action도 목록에 없다).
`examples/case-ladder.json`이 다섯 칸, `stub-seeds.json`의 `code`에 `uses`·`callers` 본문. 측정판에서 실제 CLI로 돌려
t-1~t-5가 한 라운드에 하나씩 ✅로 끝까지 갔다.

### 6d-3 — `code.trace`를 인덱스에서 만든다 · 두 엔진을 같이 돌려 대조 ✅

`code graph`의 끝점 사슬이 **인덱스**에서 나온다(`src/knowledge/index_trace.py` → 같은 `Trace` 모양으로 `flow.add_trace`에).
11b 추적기는 대조용으로 한 번 더 돌고(`parity.check(overlay, index, graph, tracer)`), 사내 `code graph` 한 번의
`끝점 대조(두 엔진)` 줄이 150/6과 맞으면 6d-4에서 추적기와 parity를 지운다. 측정판에서 `code trace /summary/badge`가
추적기 때와 **글자까지 같다**(사슬 셋 · 읽기 둘 config키 · getattr gap 한 줄).

추적기와 맞춘 것과 다른 것:

| | 인덱스 사슬 | 비고 |
|---|---|---|
| 뿌리 | 같은 path의 라우트 선언 **전부**, 선언 줄 바로 아래 첫 함수 | 추적기의 `_handler_at`과 같다. 아래 함수가 인덱스에 없으면 `not_found`(이유에 `파일:L줄`) — 대조는 `핸들러 못 찾음`으로 센다 |
| 깊이·노드 | 6 · 200 | 추적기 상수를 그대로 쓴다 |
| 디스패치 `=>` | **깊이를 안 먹는다** | 추적기는 호출자에서 구현으로 바로 갔다. 베이스·포트 메서드 걸음은 사슬에 보인다(`→ ports.X.get` 다음 구현) |
| 등급 | 리터럴 확실 · config 키·별칭 추정 · 후보(`?→`) 아래 전부 추정 | 구현이 여럿인 디스패치도 추정 + gap "구현체 N개" |
| gap | 후보 수 · getattr · 깊이·노드 상한 | `getattr`은 **함수별 미해석 호출**(`Symbol.unresolved` — 줄·호출식·사유, 내장·stoplist 제외)에서 온다. 추적기가 남기던 T6의 그 자리다 |
| 안 훑는 것 | 클래스 본문 상수 · 모듈 상수표 | 추적기는 훑었다. 사내 150/6에서 드러나지 않았으니 그대로 두고 대조 줄에 새 "추적기만"이 나오면 본다 |

`Symbol.unresolved`는 번들(`symbols.json`)에 같이 저장된다 — 6b-0의 집계(`code check --unresolved`)는 그대로고, 이건
함수 단위다(사내 규모에서 수천 건 — 내장·stoplist를 빼야 읽힌다).

### 6d-4a — 추적기·parity 삭제 ✅

사내 `code graph`의 `끝점 대조(두 엔진)`가 150/6 그대로였다(10-06). 두 번 선 대조라 지웠다:

- `src/knowledge/trace.py` 931줄 → 사슬의 자료형(`Trace·Step·Read·Gap`)·상한·`_collect_reads`(함수 본문의 자원 참조 판정)만
  남겼다. 끝점에서 앞으로 걷던 `Tracer`·`_callees`·`_read_chunks`·포트 뚫기·구조적 구현체 판정은 전부 삭제. 인덱스가
  같은 일을 레포 전체에 대해 한 번에 한다(6b·6c-1 후속).
- `src/knowledge/parity.py` 삭제. `code trace`의 "인덱스 대조" 줄, `code status`의 "인덱스 대조 같음 …" 꼬리, `code graph`의
  대조 진행 줄과 "다른 끝점" 목록, `summary`의 `endpoints_index_*`, `query.reach/reach_tree/path_to`(대조만 쓰던 것) 삭제.
- 테스트: 추적기 테스트 29개·대조 테스트 13개 삭제. 추적기 테스트로 덮여 있던 **자원 참조 판정** 규칙 넷(한 단어 config 키는
  조상 키와 같은 줄, 한 단어 리터럴은 동사와 같은 줄, 템플릿 리터럴은 따옴표 안, 키 템플릿 머리)은
  `tests/knowledge/test_reads.py`로 옮겨 판정 함수에 직접 건다. 측정판 핸들러 테스트는 `test_index_trace.py`에 고정 기대값으로.
- RED 스윕 357 → 310(추적기·대조 사례 48 삭제, 판정 사례 5 재지정, 막힌 끝점 1 복구).
- 측정판: `code graph`·`code trace`·`code status`·`case dryrun` 출력이 삭제 전과 같다(진행 줄에서 대조 한 줄만 빠진다).

인덱스가 **안 하는 것**(추적기는 했다): 클래스 본문 상수·모듈 상수표 훑기. 사내 156개 끝점 대조에서 안 드러났다 — 필요해지면
`attach_resources`에 넣는다(backlog가 아니라 여기 적어 둔다; 증상이 "끝점이 읽는 컬렉션이 사슬에 안 나온다"면 이것부터 본다).

## 사내에서 돌릴 것

```
python -m src code graph
python -m src code check --unresolved
python -m src code uses <잘 아는 컬렉션>
python -m src code callers <잘 아는 함수>
```

두 번째의 열한 줄을 그대로 옮겨 주면 된다(8~10번이 6b-0의 진단이다). 서브모듈이 안 채워졌으면 8번의
공유 라이브러리가 0이 안 된다 — `code status`가 그 레포를 말한다. 보는 것: 3번 줄이 "불변식 OK"인지(= 테스트를 뺀 `.py`
전부가 모듈로 셌는지), 정밀도·재현율, 그리고 6번 줄의 분류 — `unknown`·`method_missing`이 크면 그
모양을 안다(`external`·`variable_call`·`field_call`이 큰 것은 정상이다). 레포가 크면
`--sample 200`. 후속 커밋 뒤 다시 돌리면 1번 줄 심볼 수(테스트 빠짐)와 2번 줄 overrides, 4번 줄
정밀도가 바뀌어야 한다.

## 범위 밖 · 열린 것

- 인자 식 안의 호출(`obj.m(x.y())`)은 수집은 되지만 **인자의 수신 타입**을 안 푼다 — 6c.
- 동명이 아닌 구현체(구조적 매칭), DI 컨테이너, 문자열 디스패치 표 — 6b.
- 심볼 그래프의 graphify 병합과 사람용 보고서 — 6b. 지금 `graph.json`은 11c 그대로다.
- 인자 기본값이 진짜 자원 이름인 경우(`key: str = "…"`)를 인덱스가 못 본다 — 본문부터 훑는다(서명까지 훑으면 `Query` 설명 문자열의 예시가 읽기가 된다, 6c-2 후속 3).
- 인덱스는 **읽기 전용 산출물**이다 — 대상 코드에 쓰지 않고, 대상 시스템에 붙지 않는다.
