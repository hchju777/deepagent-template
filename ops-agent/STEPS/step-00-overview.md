# 0단계 — 무엇을 만드는가

## 한 문장

**대상 시스템(디지털 트윈)을 읽기만 하면서, 이상을 스스로 찾아내고, 원인을
조사해, 증거를 인용한 판정을 내는 에이전트.**

## 왜 "에이전트"여야 하는가

이상 탐지만이면 에이전트가 필요 없다 — 임계값 알람이면 된다. 이 시스템이
LLM을 쓰는 지점은 하나다: **왜 그런지는 미리 적어둘 수 없다.**

> OEE가 512다. 정상 범위는 0~100이다.

여기까지는 규칙이 한다. 그 다음이 문제다. 센서가 틀렸나, 집계 코드가 틀렸나,
설비가 실제로 이상한가, 아니면 계획 데이터가 안 들어왔나? 어느 쪽인지는
**무엇을 더 볼지 정하고, 보고, 다시 정하는** 과정이 있어야 안다. 그 반복이
에이전트다.

## 두 개의 입구, 하나의 엔진

```
사람: "구미 3라인 OEE가 이상해요"  ──┐
                                      ├──▶  [케이스]  ──▶  조사 엔진  ──▶  판정 + 보고서
순찰: 3분마다 점검 → 이상 발견     ──┘
```

입구가 둘인데 엔진은 하나다. **이게 이 설계의 핵심**이다 — 원인을 판정하는
로직이 두 벌이면 둘은 반드시 갈라진다. 사람이 연 케이스와 순찰이 연 케이스는
`origin` 필드 하나만 다르고 나머지 경로는 같다.

## 조사 엔진의 모양

```
frame     가설을 세우고 무엇을 볼지 태스크로 쪼갠다      (LLM)
  ↓
select    실행할 태스크를 고른다 — 병렬 폭·라운드 상한   (코드)
  ↓
execute   서브에이전트가 실제로 데이터를 읽는다          (LLM + 도구)
  ↓
integrate 모은 증거로 가설을 갱신하고 다음을 정한다      (LLM)
  ↓        ├─ continue → select 로 되돌아감 (라운드 반복)
  ↓        ├─ ask      → 사람에게 묻고 멈춤
  ↓        └─ conclude → 판정으로
conclude  인과 사슬(근본 원인 + 기여 요인)을 쓴다        (LLM)
  ↓
verify    인용한 증거 id가 실재하는지 대조한다           (코드, LLM 없음)
```

**LLM이 정하는 것과 코드가 정하는 것이 갈려 있다는 점을 보라.** 라운드를 몇 번
돌지, 몇 개를 동시에 실행할지, 판정이 유효한지는 코드가 쥔다. LLM은 그 울타리
안에서 "무엇이 맞는 판단인가"만 답한다. 재현 가능해야 하고, 상한이 있어야 하고,
감사 가능해야 하는 것은 전부 코드 쪽이다.

## 이 시스템이 절대 안 하는 것

대상 시스템에 **쓰지 않는다**. 이건 정책 문서가 아니라 코드의 성질로 만든다 —
어댑터에 `post`/`put`/`delete` 메서드를 만들지 않으면 "쓰라"고 말하는 것 자체가
표현 불가능해진다. 조치는 사람이 한다. 우리는 권고까지만 한다.

# 15단계 로드맵

각 단계는 **돌아가는 것**으로 끝난다. 문서만 늘고 실행이 안 되는 단계는 없다.

| 단계 | 만드는 것 | 끝나면 할 수 있는 것 |
|---|---|---|
| 1 | 뼈대와 규율 (StrictModel, 시계 주입) | `pytest` 통과 |
| 2 | 도메인 모델과 포트 | 실패를 예외 대신 값으로 표현 |
| 3 | config 스키마·로더·기동 검증 | 잘못된 설정이 기동에서 막힘 |
| 4 | 어댑터 (스텁 + 실구현) | **실제 Redis/REST에서 값을 읽음** |
| 5 | 프로브 + rule 판정 | 이상을 탐지해 finding을 냄 |
| 6 | 케이스 저장소 + 게이트 | 중복 케이스가 안 열림 |
| 7 | **사내 LLM 게이트웨이 연결** | 실제 Gauss가 응답 |
| 8 | 조사 그래프 (State + 노드 배선) | 라운드가 상한까지 돎 |
| 9 | 서브에이전트와 증거 수집 | LLM이 도구로 실제 데이터를 읽음 |
| 10 | conclude + verify | 인용 검증된 판정이 나옴 |
| 11 | 사람 개입 (질문·재개) | 중간에 묻고 답을 받아 이어감 |
| 12 | 보고서와 이벤트 | 마크다운 보고서 파일 |
| 13 | 순찰 데몬 + 워커 + CLI | `python -m src patrol run` |
| 14 | 실데이터 E2E | 실제 이상 → 실제 판정 |
| 15 | 운영 (retention, 학습 루프) | 정확도 측정 |

## 지금 필요한 정보

4단계(실데이터)와 7단계(실LLM)에서 막히지 않으려면 아래가 필요하다.
없으면 그 자리에 스텁을 두고 진행하다가 나중에 갈아끼운다 — 갈아끼우는 지점을
**한 곳**으로 만들어 두는 것이 4단계의 목표다.

**대상 시스템**
- REST: base URL, 실제로 부를 엔드포인트 경로 1~2개, **그 응답 JSON 실물 샘플**
- Redis: 키 이름 패턴과 값의 모양(문자열? JSON? 해시?)
- Mongo: DB/컬렉션 이름, 문서 한 건 실물 샘플
- Kafka: 토픽 이름 (쓴다면)

**사내 LLM (FabriX/Gauss)**
- `base_url`, `pass_key`(X-FABRIX-CLIENT), `client_key`(X-OPENAPI-TOKEN), `model_id`
- 사내 루트 CA 인증서 경로 (TLS 실패 시 필요)
