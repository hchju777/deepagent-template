# 10b단계 — 리드 LLM (frame · integrate)

> **목적**: 10a가 세운 울타리 안에 LLM을 넣는다. **울타리는 한 줄도 안 바꿨다** —
> 10a에서 미리 갈라 둔 자리(`EngineDeps.frame`/`integrate`)에 꽂기만 했다.
> 나중에 얹는 방어는 그 사이에 난 구멍을 못 막는다.

```bash
python -m src case investigate c-1 --stub-seeds examples/stub-seeds.json
```

```
  mx/gumi  c-1 — Operator/Check — 전부 0 — alarm·caution·normal이 모두 0이다
  gauss-o-flash(id=339) → https://… [인증: 헤더 셋(사내 게이트웨이), TLS: 시스템 저장소]
  라운드 2 — 끝난 이유: decision

  가설
    h-1 [refuted] 파생 집계가 비어 있다  (t-2.e1)

  태스크
    ✅ t-1 어떤 컬렉션이 있는지 본다 — mongo.list_collections → 1건 ['bb_state']
    ✅ t-2 찾은 컬렉션을 읽는다 — mongo.find collection='bb_state' filter={} limit=3 → …

  증거 2건
    t-1.e1  mongo.list_collections
    t-2.e1  mongo.find collection='bb_state' filter={} limit=3
```

**`t-1` → `t-2`를 보라.** 리드가 컬렉션 이름을 **모르는 채로** 시작해서, 먼저 목록을
찾고, 찾은 것을 읽었다. `t-2`는 `input_evidence_ids: ["t-1.e1"]`을 달고 나왔으므로
10a의 게이트가 붙잡았다가 2라운드에 풀었다 — 이 단계가 만든 것의 요약이다.

## 무엇을 LLM이 정하고 무엇을 코드가 쥐는가

| | |
|---|---|
| **LLM** | 가설 내용 · 무엇을 볼지 · 라운드마다 continue/conclude |
| **코드** | 라운드 상한 · 병렬 폭 · 실행 가능 판정 · 태스크 개수 상한 · 수명주기 소독 · **증거 인용 검사** · 등재제 |

규율 6의 기준 그대로다: 재현 가능해야 하고, 상한이 있어야 하고, 감사 가능해야 하는
것은 코드가 쥔다. 그 안에서 "무엇이 맞는 판단인가"만 LLM에게 맡긴다.

## 사람이 "무엇을 볼지"를 미리 다 적지 않는다

리드가 `mongo.find(collection=…)`를 부르려면 컬렉션 이름을 알아야 한다. 그걸 사람이
config에 적어 주면 **조사는 우리가 적어 준 곳만 본다** — 우리가 아는 만큼만 아는
에이전트다([decisions ⑮](decisions.md)).

그래서 이름을 주지 않고 **찾는 읽기**를 준다:
`mongo.list_collections` · `kafka.list_topics` · `redis.scan`.
등재된 10가지 중 REST 하나만 사람이 선언한다 — 그건 POST라서 body가 나가기 때문이고,
나머지 9개는 인자가 자유다(규율 9의 "메서드 수준에서 잃은 것의 대체물이 body 수준의
닫힌 스키마다"와 같은 선).

프롬프트에도 이름을 안 적는다. `{actions}` 자리는 **`domain/actions.py`의 등재표와
그 사이트의 `infra.rest.entries`에서 생성한다**(`briefing.action_catalog`). 손으로
적으면 config와 갈라지고, **갈라진 쪽이 곧 LLM이 믿는 세계**가 된다 — 항목을
추가했는데 프롬프트를 안 고치면 리드는 그게 있는 줄도 모른다.

Kafka가 없는 사이트에는 `kafka.*`가 목록에 아예 안 나온다. 실행기가 거부하므로 사고는
안 나지만 **라운드 하나가 통째로 낭비되고**, 상한이 4라운드면 그게 25%다.

## 프롬프트에 접속 정보가 안 섞인다

url·비밀번호·계정은 브리핑에 들어가지 않는다. 리드가 알아야 하는 것은 "무엇을 부를
수 있는가"이지 "어디에 붙어 있는가"가 아니다 — 후자는 어댑터의 일이다.

**사내 게이트웨이가 프롬프트를 어떻게 보관하는지 우리는 모른다.** 모르는 곳에
비밀번호를 보내지 않는 것이 유일하게 지킬 수 있는 규칙이다.
`tests/application/test_briefing.py`가 지키고, 사내에서는
`test_리드_프롬프트에_접속_정보가_안_실린다`가 **진짜 config로** 다시 본다.

## 실패가 조용하면 안 된다

LLM이 죽거나 JSON이 안 나오면 태스크가 0개가 되고, 그러면 10a의 `no_runnable`로
끝난다 — **"조사했는데 아무것도 안 했다"가 "조사할 게 없었다"와 같은 모양이 된다.**
5단계의 `unreachable` 문제와 정확히 같다.

그래서 `stopped_by`에 네 번째 값 `llm_error`를 더하고 `llm_errors`에 사유를 쌓는다.

- `frame`이 실패하면 **라운드를 시작하지 않고 END로 간다**(`route_after_frame`).
  흘려보내면 select가 0건 → integrate가 LLM을 **또** 부르고, 또 죽고, 끝난 이유가
  `no_runnable`로 덮인다.
- `integrate`가 실패하면 그 이유가 **상한보다 먼저** 읽힌다. 순서가 반대면
  "LLM이 죽어서"가 "상한에 걸려서"로 둔갑한다.

12a가 이 값을 보고 "미확정"과 "조사 실패(degraded)"를 가른다.

## 재시도는 한 번뿐이다 (`RETRIES = 1`)

파싱 실패는 모델이 형식을 놓친 것이라 한 번 더 물으면 대개 된다. 두 번 이상은 같은
실패를 반복하며 라운드 시간만 늘린다 — 조사는 라운드마다 LLM을 부르므로 재시도가
길면 전체가 늘어진다. 테스트가 **양쪽으로** 고정한다: 재시도를 지워도 실패하고,
2로 늘려도 실패한다.

## 관용 범위를 한 곳에 모았다 (`schemas.py`)

코드펜스를 벗기고, 앞뒤에 붙은 말이 있으면 첫 `{`부터 마지막 `}`까지 다시 시도한다.
"네, 아래와 같습니다:"는 형식 위반이지 답이 틀린 것이 아니다 — 거부하면 **내용은
정확한 답**이 형식 때문에 버려지고 그 라운드가 빈손이 된다.

리드와 11b의 서브에이전트가 **같은** 범위를 써야 한다. 각자 벗기면 한쪽은 코드펜스를
받아 주고 다른 쪽은 안 받아서, 같은 모델이 같은 응답을 줬는데 노드마다 다르게 동작한다.

검증은 `StrictModel`이므로 모델이 지어낸 필드(`"confidence": 0.9`)는 **응답 전체가
거부된다**(규율 5). 받아 주면 아무도 안 쓰는 값이 State에 섞이고, 보고서에는 실릴 수
있다.

## 새로 세운 경계 — 증거 인용 검사 (규율 3)

리드가 가설에 적은 증거 id는 **환각일 수 있다.** 그냥 들이면 다음 라운드의 브리핑이
`<가설>` 블록에 그 id를 실어 보내고, 리드는 **자기가 지어낸 id를 근거로 다시
추론한다.** 라운드마다 복리로 불어나는 종류의 오류라, 루프가 생긴 지금 막아야 한다.

`_accept_hypotheses`(nodes.py — `_sanitize_task`와 같은 경계)가:

1. State에 실재하지 않는 인용을 걷어낸다.
2. 인용이 **하나도 안 남으면** 판정을 `open`으로 되돌린다 — 근거가 전부 사라진
   "supported"는 근거 없는 단정이고, 그게 12a의 최종 판정 재료가 된다.
   남은 근거가 있으면 판정은 유지한다.
3. 걷어낸 사실을 `llm_errors`에 남긴다. **조용히 고치면 프롬프트가 안 먹히고 있다는
   것을 아무도 모른다.**

`lead.py`가 아니라 `nodes.py`에 둔 이유: 11b의 서브에이전트 경로가 생겨도 같은
경계를 지나야 한다. 소독이 `frame`/`integrate` 구현마다 있으면 언젠가 하나가 빠진다.

## 종료 코드는 등급이 다르다

조사가 아예 못 돈 것(`stopped_by == "llm_error"`)만 `1`이다. "돌긴 했는데 리드가 없는
증거를 인용했다"는 `0`이되 stderr로 시끄럽게 알린다. 후자까지 1로 주면 **"빨간불이
원래 그렇다"가 되고, 그러면 진짜 빨간불도 안 보이게 된다.**

## 프롬프트 자리 검사 — 두 방향 다 막는다

`_load_lead_prompt`가 기동 때 한 번 본다.

- `{case}`·`{actions}`가 **없으면**: 리드는 무엇을 부를 수 있는지 모른 채 지어낸다.
  증상은 "조사가 항상 빈손"이고 원인은 안 보인다.
- 오타 난 `{max_round}`처럼 **우리가 안 채우는 자리**가 있으면: 그 `{...}`가
  치환되지 않은 채 LLM에게 나간다. 9e에서 `{max_chars}`가 실제로 그랬고 **리포트는
  정상으로 보여서 아무도 못 봤다.**

자리 목록(`briefing.FRAME_SLOTS`/`INTEGRATE_SLOTS`)이 실제로 채우는 것과 같은지도
테스트가 본다 — 갈라지면 검사가 거짓말을 한다.

`str.format`은 **쓰지 않는다.** 프롬프트에 JSON 예시가 들어 있어 `{`가 널려 있고,
`format`은 그걸 자리로 읽어 `KeyError: '\n  "hypotheses"'`로 죽는다. 이번에도 실제로
죽었고, 9e가 같은 함정을 겪고 `report/comment.py`에 주석까지 남겨 뒀는데도 다시 밟았다.

## 한 줄이 한 증거다

증거·가설·태스크 블록은 개행을 눕혀서 싣는다. 대상 데이터는 여러 줄이 정상인데 날것
으로 실리면 블록에 **가짜 항목**이 생기고, 리드는 있지도 않은 증거 id를 인용한다.

`runner_probe._summarize`가 `repr`로 이미 이스케이프하지만 블록에서 한 번 더 막는다.
`EvidenceRef`는 어디서나 만들 수 있고(11b가 곧 만든다), **"생산자가 다 지킨다"는
가정은 생산자가 늘어나면 깨진다.**

## 이 단계에서 실제로 걸린 것

### 내가 쓴 docstring이 없는 검사를 주장했다

`fill`의 설명에 "**채운 뒤에 남은 자리를 검사한다**"라고 적어 놨는데 코드에는 그
검사가 없었다. CLAUDE.md가 경고하는 바로 그 형태다 — 문서가 주장하는 배선을 확인
없이 믿으면, 다음 사람은 그게 있다고 믿고 그 위에 얹는다.

검사를 **기동 시점**(`_load_lead_prompt`)에 실제로 만들고 docstring을 사실로 고쳤다.
매 라운드가 아니라 기동인 이유: 오타 난 자리는 라운드마다 똑같이 남으므로 매번 볼
이유가 없고, 조사가 시작된 뒤에 발견해 봐야 늦다.

### 내 테스트 하나가 거짓 초록이었다

"증거 요약에 개행이 없다"를 **이미 이스케이프된 `\n`**(백슬래시 + n 두 글자)으로
검사했다. 그건 아무것도 검사하지 않은 것이다 — 방어를 지워도 통과했다. 진짜 개행을
넣도록 고쳤고, 덤으로 **실행기가 실제로 낸 증거**로도 확인한다(소비자로 직접 검증).

### 코드펜스 테스트가 `strip_fence`를 고정하지 못했다

RED 확인에서 `strip_fence`를 통째로 무력화했는데 **테스트가 전부 통과했다.**
`parse_object`의 "첫 `{`부터 마지막 `}`까지" 재시도가 울타리째 감싼 JSON도 구해
주기 때문이다. 두 겹은 독립이므로 각각 고정하도록 테스트를 더했다.

`pytest tests/` — 933개. 10b가 더한 것은 `tests/application` 44개.
**방어를 하나씩 실제로 지워 전부 RED를 봤다**:

| integrate의 `stopped_by` 우선권 | 1 failed |

것"이고, 그것만으로는 `ask_json`의 try/except를 지워도 전부 초록이다 — 9e에서
같은 거짓 초록이 실제로 났다.

## 사내에서 한 번 돌려야 하는 것

오프라인 테스트가 잠그는 것은 **우리 코드가 무엇을 받아들이나**다. 사내 모델이 그
형식을 실제로 지키는지는 붙어 봐야 안다.

```powershell
.venv\Scripts\python.exe -m pytest tests/live -m live_llm -v
```

| 테스트 | 빨간불이면 |
|---|---|
| `test_리드가_실제로_조사_계획을_낸다` | **10b가 사내에서 안 돈다.** 프롬프트를 고쳐야 한다 |
| `test_리드가_등재된_action만_고른다` | 지어낸 action이 라운드를 낭비한다 — 목록 제시를 강화 |
| `test_리드가_이름을_찍지_않고_먼저_찾는다` | "추측하지 마라"가 안 먹힌다 — ⑮ 설계의 전제가 흔들린다 |
| `test_리드_프롬프트에_접속_정보가_안_실린다` | **진짜 비밀번호가 게이트웨이로 나간다** |

## 검토 포인트

1. **`max_rounds=4` × 라운드당 LLM 호출 1~2회 × 사이트 28개.** 케이스가 몰릴 때의
   비용이 여기 걸린다. 14단계의 워커가 동시 실행을 조일 자리이기도 하다.
2. **인용 환각이 얼마나 나오는가.** `llm_errors`가 매번 차면 프롬프트를 고치는 것이
   맞고, 안 차면 이 경계는 조용히 서 있기만 하면 된다.
3. **`note` 필드.** 모델이 설명을 덧붙이고 싶어 하는 자리로 뒀다(없으면 지어내서 다른
   칸에 넣는다). State에는 안 들어간다 — 12a가 쓸 일이 있는지 봐야 한다.
4. **`role`은 아직 안 읽힌다.** `ProbeRunner`는 `action`만 본다. 11b에서 서브에이전트
   3종이 생기면 그때 갈린다.
