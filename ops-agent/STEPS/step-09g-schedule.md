# 9g단계 — 프로세스 안의 스케줄러

> **목적**: 바깥 스케줄러에 기대지 않고 **떠 있는 프로세스가 스스로 시간을 잰다.**
> 주기는 config가 정하고, cron과 interval 둘 다 쓸 수 있다.

```bash
python -m src schedule --list     # 무엇이 언제 도는지 (돌리지는 않는다)
python -m src schedule            # 스케줄대로 계속 돈다
python -m src schedule --dry-run --no-mail --max-runs 1   # 배선만 확인
```

```json
"schedule": {
  "enabled": true, "kind": "cron", "cron": "0 8 * * *",
  "interval_seconds": 60, "run_on_start": false
}
```

## 왜 cron과 interval을 **둘 다** 두는가

운영은 cron이다("매일 8시"). 그런데 확인할 때는 1분 간격이 필요하다. 칸 하나로
두면 시험하려고 운영 식을 고치게 되고, **고쳐 둔 채 배포하는 사고**가 난다. 칸을
나누면 `kind`만 바꿔서 시험하고, 운영 값은 그대로 남는다.

## 시간대가 이 기능의 절반이다

`0 8 * * *`이 **어느 8시**인가. `datetime.now().astimezone()`은 그 기계의 시스템
TZ를 따르고, 컨테이너 기본값은 UTC다 — 그러면 한국 시각 **오후 5시**에 돈다.

그래서 시계가 `app.json`의 `timezone`을 읽는다. 배포 환경이 무엇이든 같은 시각에
돈다. 같은 버그가 집계 쪽에도 있었다: UTC 파드에서 화요일 아침에 돌면 로컬 날짜가
아직 월요일이라 "어제(직전 평일)"가 **금요일**로 계산되고, 제목의 날짜도 같이
밀려서 **완전히 정상으로 보인다.**

```
  컨테이너 TZ          시스템 TZ를 따를 때          config(Asia/Seoul)를 따를 때
  UTC                2026-09-14(Mon) 03:31      2026-09-14(Mon) 12:31
  America/New_York   2026-09-13(Sun) 23:31      2026-09-14(Mon) 12:31
```

## cron을 직접 읽는다

`croniter`가 표준이지만 사내 PyPI에 없을 수 있다(7단계의 langchain, 9d의
matplotlib과 같은 이유). 대신 **직접 쓴 만큼 테스트가 촘촘해야 한다** — 이 계산이
틀리면 증상은 "리포트가 안 온다"뿐이고, 그때는 이미 며칠 지난 뒤다.

읽는 문법: `*` · `5` · `1-5` · `*/15` · `1-5/2` · `0,30`. 다섯 칸(`분 시 일 월 요일`),
요일은 0~6이고 7도 일요일이다.

**일(日)과 요일이 둘 다 제한되면 OR다.** cron의 유명한 비직관이고 우리가 지어낸
규칙이 아니다 — `0 8 13 * 5`는 "13일 **또는** 금요일"이다. 사람이 cron 식을 다른
데서 복사해 오므로 원래 cron과 같게 읽어야 한다. 우리만 AND로 읽으면 같은 글자가
다른 날에 돌고, 그 차이는 **안 도는 날에만** 드러난다.

읽을 수 없는 식은 **기동에서 거부한다**(`kind`가 interval이어도 검사한다 — 안 하면
잘못된 식이 kind를 바꾸는 날에야 드러나고 그날은 보통 급할 때다). 영원히 안 도는
식(`0 0 30 2 *` — 2월 30일)도 잡는다.

## 밀린 발사를 몰아 쏘지 않는다

1분 간격인데 한 번이 90초 걸리면, "직전 목표 + 간격"으로 다음을 세는 구현은 이미
지난 시각을 가리켜 **즉시 재발사**한다. 실행이 실행을 밀며 붙어 돌고 그 사이 메일이
연달아 나간다.

그래서 다음 시각은 항상 **지금 기준**으로 다시 계산하고, interval은 **기준점 +
N×간격**으로 센다(직전 실행 기준이 아니다 — 그러면 실행 시간만큼 매번 밀려서 며칠
뒤엔 전혀 다른 시각에 돈다). 지나간 슬롯은 건너뛴다.

2초 간격에 한 번이 2.1초 걸리는 상황을 실제로 돌리면 **4초마다** 돈다:

```
  13:12:36 ✅ daily-alarm — …  (3.5초)
  13:12:40 ✅ daily-alarm — …  (2.1초)
  13:12:44 ✅ daily-alarm — …  (2.1초)
```

## 겹치지 않는 것은 구조로 보장한다

잡 하나가 루프 하나이고 그 안은 순차다. 겹칠 방법이 **없다.** "실행 중" 플래그로
막으면 그 플래그를 지우지 못하는 경로가 생긴다(예외로 빠져나가는 길). 시나리오가
여럿이면 잡이 여럿이고 그것들은 서로 독립이다.

## 루프는 죽지 않는다

리포트 한 번이 실패해서 루프가 죽으면 그 뒤로 **영원히 아무것도 안 나간다.** 그리고
조용하다 — 프로세스는 살아 있다. 그래서 발사마다 `try/except Exception`으로 감싸고
실패를 `Fire` 값으로 돌린다. 찍다가 죽는 것(닫힌 파이프)도 스케줄을 멈추게 두지
않는다.

## uvloop — 있으면 쓰고 없으면 만다

```python
install_fast_loop()   # "uvloop 0.22.1" 또는 "asyncio (Windows — …)"
```

Windows는 uvloop 빌드가 없으므로 `requirements.txt`가 `sys_platform != "win32"`
표시로 설치를 건너뛴다(표시가 없으면 Windows에서 `pip install -r`이 통째로 실패한다).
코드도 `ImportError`에 기대지 않고 **플랫폼을 먼저 본다** — 그래야 "Windows에서는
asyncio"가 결정으로 남고, 설치가 우연히 성공한 환경에서도 같은 길로 간다.

무엇을 골랐는지 시작할 때 찍는다. 조용히 정하면 "느린데 왜 느린지 모르는" 상태가 된다.

`set_event_loop_policy`는 파이썬 3.11의 API다(3.14에서 없어진다). 올릴 때
`asyncio.Runner(loop_factory=...)`로 바꿔야 한다.

## 멈추는 법

SIGINT·SIGTERM을 받으면 **자는 중이라도 즉시** 깬다. `asyncio.sleep`으로 자면 매일
8시 스케줄에서 최대 24시간 안 깨고, 컨테이너 종료 유예 시간(보통 30초)을 넘겨 강제
종료된다. Windows에는 `add_signal_handler`가 없으므로 Ctrl+C(KeyboardInterrupt)에
맡긴다 — 못 하는 일을 하려다 죽는 것보다 낫다.

## 확인 순서

```bash
python -m src schedule --list                  # ① cron 식이 맞는가
# scenarios/daily-alarm.json의 kind를 interval·1분으로 바꾸고
python -m src schedule --dry-run --max-runs 2  # ② 실제로 도는가 (메일은 안 나간다)
python -m src schedule                         # ③ 그대로 둬 본다
```

②에서 `run_on_start: true`를 켜면 1분을 기다리지 않고 바로 한 번 돈다.

## 검토 포인트

1. **`--list`로 먼저 본다.** cron 식은 사람이 자주 틀리고, 틀리면 증상이 "안 온다"뿐이다.
2. **`0 8 * * 1-5`(평일)이다.** 매일로 두면 토·일에 같은 금요일 리포트가 두 번 더
   간다 — 리포트가 보는 "어제"는 직전 **평일**이기 때문이다.
3. **프로세스가 죽으면 누가 살리는가.** 이 스케줄러는 자기가 죽는 것은 못 막는다.
   컨테이너면 재시작 정책, Windows면 서비스 등록이 그 자리다.
4. **로그를 어디로 보낼 것인가.** 발사 기록이 표준출력으로만 나간다.
