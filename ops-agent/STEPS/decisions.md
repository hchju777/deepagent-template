# 정해 둔 것 — 아직 안 만든 것들의 설계

`STEPS/step-NN-*.md`는 **만든 뒤에** 쓴다. 이 파일은 그 전에 정한 것들을 담는다 —
조사 엔진(10~13)과 순찰(4~6)의 설계 결정, 그리고 **기각한 선택지와 그 이유**.

[backlog.md](backlog.md)와 짝이다. backlog는 "지금 안 하기로 한 것", 여기는
"하기로 했고 어떻게 할지 정한 것".

각 항목은 **"왜 이렇게 정했는가"와 "이 판단이 언제 바뀌는가"**를 함께 적는다.
바뀌는 조건을 안 적으면, 나중에 보는 사람은 이게 검토된 것인지 관성인지 모른다.

---

## ① 조사 엔진은 LangGraph로 만든다

직접 라운드 루프를 도는 안을 검토했다. `asyncio.gather` 스무 줄이면 되고, 이 프로젝트가
계속 해 온 것(matplotlib 대신 PNG 인코더, croniter 대신 cron 파서)과도 맞는다.

**그래도 LangGraph를 쓰기로 했다.** 직접 만들면 13단계(사람 개입)와 14단계(데몬·워커)에서
**"State를 언제 어떻게 저장하고 어떻게 재개하는가"를 우리가 새로 발명**하게 된다. 이
리포가 실제로 깨진 지점들이 대부분 그런 자리였다 — `round_hint`가 매 호출 0으로
리셋된 것이 그렇다(재개 시의 현재 상태를 호출부가 들고 다니다 틀렸다).

그리고 원본 템플릿(`../src/application/`)이 **작동하는 참조 구현**이다. 다른 모양으로
만들면 그 참조 가치가 사라진다.

**대가와 보험**: 새 의존성 넷이 는다 — `langgraph` + `langgraph-checkpoint` +
`langgraph-sdk` + `langgraph-prebuilt`, 그리고 네이티브 휠인 `ormsgpack`·`xxhash`.
사내 PyPI에 있는지 **확인이 필요하다**(backlog). 보험으로 **노드를
`(CaseState) -> dict` 순수 함수로 두고 LangGraph 타입을 `graph.py` 한 파일에만
가둔다** — 없다는 답이 와도 바꿀 파일이 하나다.

**언제 바뀌는가**: 사내 PyPI에 없고 반입도 안 되면. 그때 `graph.py`만 직접 루프로 바꾼다.

## ② 대상 코드는 submodule로 두지 않는다

조사 대상 서비스의 코드를 우리 리포의 git submodule로 두는 안을 검토했고 **기각했다.**

**결정적인 이유 — 사이트마다 배포 커밋이 다르다.**

```
mx/gumi  →  processor @ a3f9c2     지난주 배포
mx/sevt  →  processor @ b71e04     어제 배포
```

이게 정상이다. 법인마다 배포 일정이 다르다. 그런데 **서브모듈 포인터는 하나뿐이다.**
서브모듈은 "우리가 의존하는 **한** 버전"을 못박는 도구인데, 우리에게 필요한 것은
"대상이 배포했을 수 있는 **모든** 버전을 읽을 수 있는 상태"다. 목적이 반대다.

나머지 셋도 가볍지 않다:

- **`git archive`에 안 담긴다.** 사내 이관 절차가 그것이다([README](../README.md)의
  "사내로 옮기기"). 서브모듈은 아카이브에 안 들어가고, 증상은 "사내에서만 코드 증거가
  조용히 안 나온다"가 된다 — 이 리포가 이미 두 번 당한 형태다.
- 서브모듈 체크아웃에는 보통 그 커밋 하나만 있어 `git show <다른 커밋>:path`가 안 된다.
- 모니터링 도구 리포 안에 운영 서비스 소스가 섞인다(pytest 수집 범위, 보안 심사, 크기).

**대신**: `target.code.repos[]`에 `{name, url, path}`를 두고, 체크아웃은 우리 리포
**밖**에 둔다. 전체 히스토리를 가진 clone 하나가 모든 사이트의 커밋을 읽는다.
레포 크기가 GB 단위가 아니라는 것은 확인됐다 — partial clone(`--filter=blob:none`)은
쓰지 않는다. 그걸 쓰면 `git show`가 필요할 때 네트워크를 타고, **조사가 git 서버에
의존하게 된다.**

**언제 바뀌는가**: 레포가 GB 단위로 커지면 partial clone과 "조사 중 네트워크 의존"의
저울질을 다시 한다.

## ③ 코드의 위치는 세 층이 나눠 답한다

한 곳에 몰면 모노레포(한 레포에 서비스 여럿)와 멀티레포가 다른 모양이 되고, 배포
상태가 바뀔 때마다 구조 정의까지 건드리게 된다. 세 층은 **각각 다른 질문에 답하고
다른 사람이 다른 주기로 고친다.**

| 층 | 답하는 질문 | 어디 | 얼마나 자주 |
|---|---|---|---|
| 토폴로지 | 어느 서비스가 어느 레포의 어느 경로인가 + 무엇을 읽고 쓰는가 | `knowledge/topology/` | 시스템 구조가 바뀔 때만 |
| config | 그 레포를 어디서 받아 어디에 두는가 | `config/gbm|fct/*.json`의 `target.code.repos` | 배치가 바뀔 때 |
| deployment | 이 사이트에 지금 어느 커밋이 떠 있는가 | `knowledge/deployment/<gbm>/<fct>.json` | 배포할 때마다 |

**모노레포 혼재가 여기서 해결된다** — 서비스 이름이 1급이고, `(repo, path)` 쌍이
"그 서비스를 어디서 읽을지"를 말할 뿐이다. 같은 레포의 다른 `path` 두 개면 서비스 둘이다.

`path`가 필요한 이유는 `git grep`을 그 서비스 경로로 좁히기 위해서다. 없으면 A를
조사하는데 B의 코드가 섞여 나온다.

## ④ knowledge는 YAML이 아니라 JSON이다

원본 템플릿은 YAML이다. 우리는 JSON으로 간다 — `config/`가 전부 JSON이라 일관적이고,
**`PyYAML` 의존성이 안 는다**(사내 PyPI 질문이 하나 준다).

**언제 바뀌는가**: deployment를 운영이 매 배포마다 손으로 고치는데 JSON의 따옴표·쉼표가
실제로 사고를 내면. 그때는 주석이 되는 형식(YAML)의 값이 의존성 비용을 넘는다.

## ⑤ `code sync`는 사내에서만 네트워크를 탄다

우리 프로세스가 사내 git에 붙을 수 있는 것은 **사내에 배포됐을 때뿐이다.** 개발
환경에서는 못 붙는다. 그래서 명령을 이렇게 가른다:

| 명령 | 네트워크 | 어디서나 되는가 |
|---|---|---|
| `code status` | 없음 | ✅ 진단 전용 |
| `code plan` | 없음 | ✅ 사람이 실행할 git 명령을 출력 |
| `code sync` | 있음 | 사내에서만. 실패는 error로 흡수하고 `code plan`을 안내한다 |

`code status`가 보는 것 넷:

1. `path`가 존재하는가
2. **`.git`이 있는가** — 작업 트리만 복사되면 `git show <배포커밋>:path`가 통째로
   안 된다. 우리 설계의 전제가 무너지는 자리다
3. **`origin`이 config의 `url`과 같은가** — 누가 포크나 다른 레포를 그 경로에
   클론하면 우리는 그럴듯한 코드를 읽고 그럴듯한 로직 명세를 만들고 그럴듯한 재계산을
   한다. **전부 틀린 채로.** "코드를 못 읽었다"보다 훨씬 나쁘다 — 실패가 조용하고
   판정은 확신에 차 있다. `url`은 문서가 아니라 **자물쇠**다
4. deployment가 말하는 커밋이 로컬에 실재하는가(`git cat-file -e`)

## ⑥ 조사 중에는 코드도 지식 그래프도 갱신하지 않는다

`CodeReaderPort`에 쓰는 메서드를 만들지 않는다(`commit`/`push`/`checkout`/`reset` 없음).
규율 9와 같은 이유다 — 표현 불가능하면 환각으로도 못 부른다.

그리고 **`sync`는 포트 밖, CLI 경계의 별도 명령이다.** 서브에이전트가 fetch할 수 있으면
**조사 도중에 레포가 움직인다.** 라운드 1에서 읽은 코드와 라운드 3에서 읽은 코드가
달라지고, 그러면 증거끼리 모순되는데 원인을 못 찾는다. 조사 중 코드는 정지해 있어야
한다 — as_of 규율과 같은 근거다.

**같은 규칙이 graphify 산출물에도 적용된다**(⑦).

## ⑦ graphify는 `code_tracer`의 두 번째 구현이다 (11c)

[graphify](https://github.com/Graphify-Labs/graphify)로 대상 서비스의 지식 그래프를
만들어 `code_tracer`에 물린다.

**우리 성격에 맞는 이유**: 코드 추출 패스가 tree-sitter AST 파싱이고 **LLM을 안 쓴다** —
로컬·결정론적이다. LLM을 쓰는 것은 문서·PDF의 의미 추출 패스뿐이다.

**개선하는 지점은 하나다** — "어디를 읽을지 찾는" 단계:

```
11b:  code_tracer → git grep "performance"  → 후보 줄들 → git show
11c:  code_tracer → 그래프 질의             → 정확한 위치
```

재계산 대조(조사의 핵심)는 **안 바뀐다.** 그래서 `CodeReaderPort` 뒤에 두고,
11b는 git만으로 완결시킨다 — graphify 반입 심사가 몇 주 걸려도 조사가 멈추지 않게.

**지켜야 할 것**:
- **산출물을 박제해서 읽기만 한다.** 조사 중에 graphify를 돌려 그래프를 넓히면 우리
  읽기 범위가 조사 도중에 커진다 — 규율 9가 막는 fail-open과 같은 형태다
- 그래프는 **커밋 해시와 짝으로** 보관한다. 배포 커밋이 다른 사이트에 다른 사이트의
  그래프를 쓰면 조용히 틀린다
- 그래프 노드를 증거로 인용하려면 **어느 커밋·어느 파일·몇 번째 줄인가**가 남아야
  한다(12a의 verify가 여기 걸린다). `graph.json`이 그걸 담는지 **확인이 필요하다**(backlog)
- 문서 패스를 쓴다면 반드시 사내 게이트웨이로. `--backend openai`가 `OPENAI_BASE_URL`을
  실제로 싣는지 첫 호출로 확인하라 — 안 실으면 사내 문서가 외부로 나간다

## ⑧ 사이트 간 배포 차이는 1급 증거다

"구미만 이상하고 SEVT는 멀쩡하다"일 때, **두 사이트의 배포 커밋이 다르다는 사실 자체가
증거다.** `git diff b71e04..a3f9c2 -- services/processor`가 곧 용의자 목록이다.

그래서 `CodeReaderPort`에 `diff`를 넣는다(원본 템플릿에는 `show`/`grep`/`head`/
`hash_exists`만 있다). `git diff`는 읽기 명령이라 ⑥과 충돌하지 않는다.

같은 이유로 deployment에 **`deployed_at`을 둔다**. "증상이 9월 11일부터인데 processor가
9월 10일에 배포됐다"는 한 줄이 가설 순위를 통째로 바꾼다. 첫 소비자는 `code status`
출력이다 — 읽는 코드 없이 config 항목을 만들지 않는다.

## ⑨ `git grep`의 패턴은 `-e`로 넘긴다

LLM이 만든 패턴이 그대로 들어가는 자리다. `-v`로 시작하는 패턴은 git이 **옵션으로**
읽어(매치 반전) 인자 주입이 된다. 원본 템플릿이 겪고 막은 것이고, 우리도 같은 방식으로
막되 **테스트로 못박는다.**
