# 남은 부채 — 무엇이 열려 있고 왜 아직 안 갚았는가

집행된 계획 25건 중 **인계 절이 있는 것은 12건**(계획 12~23)이고 거기 **99개 항목**이
흩어져 있었다. 계획 문서는 집행 기록이라 읽는 사람이 "지금 뭐가 남았나"를 알 수 없다.
이 문서가 그 답이다.

99개를 넷으로 갈랐다. **분류를 검증할 수 있게 §6에 전부 열거한다** — 개수만 적으면
"내 항목이 어디로 갔나"를 확인할 방법이 없고, 그러면 부채가 판단 기록으로 조용히
사라진다.

| 종류 | 수 | 어디 있어야 하는가 |
|---|---|---|
| **A. 미해결 부채** | 51 | 여기 — §1~§3에 **전부** 적었다(절로 쓴 것 + §3.23의 한 줄짜리 23개, 일부는 한 항목으로 합쳐진다) |
| **B. 이미 갚음** | 14 | 여기(§4) |
| **C. 설계 판단 기록** | 24 | [architecture.md](architecture.md)·[file-map.md](file-map.md)·코드 주석 (§6에 열거) |
| **D. 교훈** | 10 | [for-implementers.md](for-implementers.md)의 집행 전 점검표 (§6에 열거) |

C와 D는 부채가 아니다 — "왜 이렇게 했는가"와 "다음엔 이걸 먼저 의심하라"이지 "할 일"이
아니다. 그것들을 부채 목록에 두면 진짜 부채가 묻힌다.

> **여기 적힌 것은 전부 코드로 확인했다**(2026-09-07, `main` 기준). 그래도 손대기 전에
> 다시 확인하라 — 이 리포는 문서가 주장하는 배선을 믿었다가 여러 번 데였다.

## 1. 규모가 커지면 아픈 것 (성능·용량)

이 셋은 **지금 안 아프다.** 아파지는 시점이 정확히 "이 시스템이 오래 돌아 신뢰를 얻은
뒤"라는 것이 문제다.

### 1.1 `cases` 컬렉션이 영원히 자라고, 그 위에서 무제한 전수 스캔이 아홉 곳 돈다

retention ①은 종결 케이스의 **증거·판정·케이스 파일**을 지우고 레코드에는 `purged_at`만
찍는다 — `mongo_store.py`에 `cases.delete_*`가 **없다**. 그 위에서 `list_by_status`가
무제한·무프로젝션 `find`로 전건을 `CaseRecord`로 만든다.

**지워지지 않는 컬렉션은 `cases` 하나가 아니라 다섯이다**(14개 중): `cases`·`labels`·
`counters`·`code_knowledge`·`ledger_meta`. `labels`는 의도적이고(스냅샷과 짝이라 한쪽만
지우면 대조가 불가능하다), 나머지 셋은 그냥 안 걷힌다 — 특히 **`counters`는 케이스마다
둘씩**(`evidence:{id}`·`events:{id}`) 무한히 자란다.

호출부 아홉(전부 확인):

| 자리 | 빈도 |
|---|---|
| `infrastructure/retention.py`(둘) | 스윕마다 2회 — `:124`가 "①과 별개로 다시 읽는다"고 자인 |
| `application/labels.py`(둘) | `case label --stats` 호출마다 2회 |
| `application/worker.py`(셋) | requeue 틱마다 3회 |
| `api/routes_reads.py` | `GET /cases` 요청마다(사이트 단위 — `gbm`·`fct`가 필수라 전 사이트는 아니다. 다만 페이지네이션이 없다) |
| `__main__.py` | `case list` |

**처방**: id만 내는 포트 메서드 — **다만 retention은 대상이 아니다.** retention은
`thread_ids`·`thread_versions`·`purged_at`을 읽고 레코드를 `model_copy`+`save`로 왕복시키므로
전체 레코드가 필요하다. id만 쓰는 것은 `label_stats`·`calibration`이고, `GET /cases`와
`case list`는 페이지네이션이 답이다.

### 1.2 `MongoLedger._history`가 점검의 실행 이력 **전량**을 검증한다

`_history`가 `find(...).sort("seq", 1)`로 전부 끌어와 문서마다 `CheckOutcome`을 검증한다.
`ledger_runs`는 retention이 걷지만 `ledger_d`(기본 30일) 안에서는 자란다 — 60초 주기면
점검 하나당 43,200건이다.

**주기적으로 도는 소비자는 self-check다**(`selfcheck.py`): `consecutive_errors`가 **점검마다**
`_history`를 탄다(`runs`는 스트릭이 임계를 넘은 점검에서만 돈다 — 뜨거운 경로는 앞의 하나다). `last_run`은 `patrol status` CLI **한 곳**에서만 불린다 —
데몬은 안 부른다(그래서 `last_run`만 고치면 뜨거운 경로가 그대로다).

**처방**: `consecutive_errors`는 첫 비-error에서 멈추므로 **내림차순 커서를 스트리밍하며
조기 종료**하면 된다. **고정 `limit(N)`은 안 된다** — `skipped`가 스트릭을 안 끊고 투명하게
지나가므로 몇 건을 읽어야 하는지 미리 알 수 없다. `last_run`은 `sort(-1).limit(1)`이지만
CLI 전용이라 급하지 않다.

### 1.3 `calibration`이 라벨된 종결 케이스마다 저장소를 두 번 친다

`snapshots.get`과 `labels.list_for`가 케이스당 한 번씩. 게이트가 종결 라벨 30건에서
열리므로 지금은 60왕복이고 사람이 손으로 치는 명령이라 안 아프다. 라벨이 수천 건이 되면
배치 조회가 필요하다.

## 2. 조용히 틀릴 수 있는 것 (정확성 위험)

### 2.1 `_next_seq`가 docstring이 단언한 것을 안 지킨다

모듈 docstring이 "동시 호출에도 **경쟁 없이** 유일한 id/순서를 발급한다"고 적는데,
실제 MongoDB는 아직 문서가 없는 `_id`에 대한 동시 upsert에서 하나를 `E11000`으로
떨어뜨릴 수 있고 `_next_seq`에 **재시도가 없다**. 같은 파일이 `record_send`에서 `DuplicateKeyError`를 잡으므로 패턴을
몰라서가 아니다.

창은 카운터 키가 **새로 생기는 순간**이고 `evidence:{case_id}`는 케이스마다 새로 생긴다 —
데몬이 둘 이상 붙은 배포에서 새 케이스의 첫 쓰기가 드물게 터진다. 규율 1을 저장소가
조용히 어기는 자리다. **mongomock은 단일 스레드라 이 경로가 물리적으로 재현 불가다.**

### 2.2 mongomock이 못 보는 자리 — 초록을 증거로 쓰지 마라

- **인덱스 부재가 완전히 등가로 보인다.** mongomock은 `create_index`를 받아 unique만
  강제하고 질의 계획을 안 세운다. 그래서 `cases`에 `gbm`/`fct` 인덱스가 없다는 사실이
  오프라인에서 안 보인다(§1.1의 사이트 필터가 그 인덱스를 원한다).
- `$limit: 0`(실제는 거부, mongomock은 `[]`), **오름차순** `_id` 동점 키의 효과,
  `$dateFromString`·`$toDate`·`$indexOfCP`·`$substrCP` 미구현, `$substr`의 null·비문자열
  처리(실제와 다르다), `$sort`+`$limit`의 top-k 병합(옵티마이저가 없다).

계획 20이 DB에 맡긴 양을 늘렸으므로 사각지대도 함께 커졌다.

### 2.3 되감긴 시계에서 "마지막 라벨 = 사람의 최종 믿음"이 깨진다

두 저장소 모두 `labeled_at`을 1순위로 정렬한다. 나중에 단 라벨이 더 이른 시각이면 앞으로
간다. **두 백엔드가 같은 답을 내는 것은 계획 20이 보장하지만**, 그 답이 캘리브레이션의
전제와 맞는지는 별개 문제다.

### 2.4 `api` **프로세스**는 워커·데몬을 여전히 끌어온다 (규율 9)

경계 테스트(`tests/api/test_boundary.py`)는 `src/api/`의 **패키지** import 그래프를
AST로 본다. 그건 깨끗하다. 그런데 `python -m src api`가 실행하는 **프로세스**는
`src/__main__.py`가 모듈 수준에서 `InvestigationWorker`(`:26`)와 `PatrolDaemon`(`:33`)을
import한다 — `src/api/app`·`assembly`는 `:121-122`에서 지연 import다.

지금 실해는 없다(라우트가 워커를 안 부른다). 다만 규율 9가 "`api`는 대상에 붙지 않고
조사를 시작하지 않는다"를 **메커니즘으로** 지키자는 것인데, 그 메커니즘이 패키지에만
걸려 있고 프로세스에는 안 걸려 있다.

### 2.5 접기가 두 벌이다 — `history._clean_line`

`one_line`(`briefing.py`)과 `_clean_line`(`history.py`)이 각자 접는다. 계획 21이 존재하는
이유가 "접기가 두 벌이면 언젠가 한쪽만 고쳐진다"인데 본체가 남았다.

**합칠 때의 비협상 제약**: `one_line` 위에 얹되 **evidence id 제거를 끌고 오면 안 된다**.
이력이 지우는 것은 **과거 케이스**의 id이고(규율 3), 그래프 내부 프롬프트가 다루는 id는
**이번 케이스**의 것이라 지우면 조사가 자기 증거를 못 가리킨다.

| P14-6 | 후보가 기여 요인과 같은 컴포넌트여도 안 거른다 — "이것 대신"과 "이것에 더해"가 같은 것을 가리키는 것이 모순인지는 설계 판단 |
| P15-2 | `history_shown`의 소비자가 없다 — "이력이 도움이었나 앵커링이었나"를 물으려면 필요하다 |
| P15-5 | tier 4의 상류가 `upstream_slice(max_depth=3)`에 묶인다 — 더 먼 상류는 안 본다 |
| P15-6 | `_strip_evidence_ids`가 `ev-\d+` 형태만 지운다 — 증거 id 형식이 바뀌면 이 정규식도 바뀌어야 한다 |
| P15-9 | resume 경로가 이력을 계산하고 버린다 — `resume_case`가 `case`를 안 받는다 |
| P17-1 | `question_seq`는 **선택**이다 — 안 보내는 클라이언트는 예전 경합에 그대로 노출된다 |
| P17-2 | `stale_question`은 답을 보관하지 않는다 — 사람이 쓴 답이 버려진다(큐잉은 의도적으로 안 했다) |
| P17-11 | 질문이 `None`인 레코드에 재질문하면 `"(질문 없음)"`을 한 번 묻고 그 답이 버려진다 |
| P18-2 | `rest:<이름>` 표적의 관련성이 케이스 locator와의 **문자열 일치**로만 걸린다 |
| P20-4 | `$sort`가 계산 필드 위에서 돌아 인덱스를 못 쓴다 — 인메모리 정렬 32MB 한도를 넘으면 `status_since` 백필(데이터 마이그레이션)이 필요하다 |
| P20-11 | `_id`를 동점 키로 쓰는 것은 **한 프로세스 안에서만** "삽입 순서"다(ObjectId 중간 5바이트가 프로세스별 난수) |
| P20-12 | 저장소 포트 docstring이 동점 계약을 안 적는다(`DigestStorePort.list`·`CaseRepositoryPort.closed_by_*`) |
| P21-4 | `repr`에 기대는 자리 둘 — 여러 줄 본문을 사람이 읽기 좋게 보이려는 요구가 생기면 접기가 아니라 **들여쓰기**가 답이다 |
| P19-5 | 여러 사람이 같은 케이스를 다르게 라벨하면 마지막이 이긴다 — 합의가 아니라 최신성이다(`labeled_by`가 이미 남아 있다) |
| P14-1 | 후보의 정답 대조가 없다 — `VerdictSnapshot.alternates`와 라벨을 잇는 캘리브레이션(계획 19가 `confidence` 축만 했다) |

## 4. 이미 갚은 것

계획 문서를 읽는 사람이 헛수고하지 않도록 적는다. 전부 코드로 확인했다.

**계획 문서에 갚음 표시가 없어 열린 것처럼 읽히는 것** — 여기가 헛수고를 부르는 자리다.

| 계획 문서의 인계 | 갚은 곳 | 확인 |
|---|---|---|
| P12-1·P13-1·P15-7 접수 `_save` TOCTOU | 계획 17 | `intake.py`가 `update_if`(CAS)를 쓴다. **다만 증거 쓰기는 여전히 CAS 밖이다** |
| P12-2 `sites_for` 프로덕션 소비자 0 | 계획 13 이후 | `routes_reads.py`가 세 곳에서 쓴다 |
| P15-1 캘리브레이션 계산 없음 | 계획 19 | `labels.calibration` |
| P15-4 `MetricsSinkPort` 소비자 없음 | 계획 19 | `patrol status` |
| P15-8 Mongo `closed_by_*` DB 정렬·limit | 계획 20 | `_closed_newest_first` |
| P13-11 `submit_answer`의 포괄 except가 저장소 장애를 404로 | 계획 14 | `submit.py`가 `"error"`(503)를 낸다 |
| P18-8 그래프 내부 프롬프트가 안 접힌다 | 계획 21 | `nodes.py`의 네 렌더러·`llm_judge`가 `one_line`을 탄다 |
| P12-5 `intake_turn`이 lease를 안 잡는다 | 계획 17 | CAS(`update_if`)가 lease 없이 닫았다 — 부채의 내용이 "lease를 잡아라"가 아니라 "동시 요청이 레코드를 망가뜨린다"였다 |
| P20-5 같은 폭 함정이 형제 둘에 살아 있다 | 계획 20 | `MongoDigestStore._rows`·`MongoLabelStore.list_for`가 `_fixed_width_iso`를 탄다 |

**계획 문서에 이미 갚음 표시가 있는 것**(취소선이나 "→ 갚았다") — 헛수고 위험은 없다.

| 계획 문서의 인계 | 갚은 곳 | 단서 |
|---|---|---|
| P13-9 `POST /answers`에 If-Match 없음 | 계획 17 | `question_seq`는 **선택**이라 안 보내는 클라이언트는 무보호(§3의 3.12와 짝) |
| P13-12 중복 큐 항목이 조사를 재시작 | 큐 중복 제거 | `CaseQueue._held` |
| P16-11 집계 지표 검증 비대칭 | 집계 가드 | **부분이다** — `_resolver_problems`는 공유되지만 `response_field_problems`는 여전히 점검 전용이다(사유는 `boot.py` 주석에) |

## 5. 우선순위

부채를 갚을 순서를 정한다면 이렇다. 근거는 **언제 아픈가**다.

1. **§2.1 `_next_seq` 재시도** — 유일하게 프로덕션에서 예외를 던지는 자리다. 한 줄이면
   `DuplicateKeyError`를 잡고 재시도할 수 있고, 같은 파일의 `record_send`가 이미 그
   패턴을 쓴다.
2. **§1.2 `consecutive_errors`의 전량 검증** — self-check가 점검마다 타는 유일한 뜨거운
   경로다. `last_run`(CLI 전용)이 아니라 **이쪽**이다.
3. **§1.1 id만 내는 포트 메서드** — 셋 중 제일 크지만, 이 기능이 실제로 쓰이기 시작하는
   시점이 정확히 아픈 시점이다.
4. **§2.5 접기 통합** — 위험은 낮으나 계획 21의 논거가 스스로를 가리킨다.
5. 나머지는 필요해질 때.

**§2.2(mongomock 사각)는 갚을 수 있는 부채가 아니다** — 실제 Mongo를 요구하는 테스트를
만들지 않는다는 규약과 맞바꾼 것이다. 그 자리를 고칠 때 **초록을 증거로 쓰지 않는 것**이
유일한 방어다.

절단 결함이 안 보인다(P20-6), `getsource`로 구현 표현을 지키지 마라(P21-8) 같은 것.

끝 "인계" 절이다. 분류가 틀린 항목을 찾으면 여기로 옮겨라.
